# UI vs script solver divergence on L26/L92 (2026-05-26)

## What the code-level instrumentation and normalization show

1. **The direct script and UI use different solver purposes by default.**
   - `scripts/run-solver-direct.mjs` defaults `--purpose` to `hint` and forwards that through `Solver.universalSolveLevel(...)`.
   - `Solver.universalSolveLevel` also defaults missing purpose to `'hint'`.
   - The **Edit-mode Solve button** calls `runGameSolver('solve')`, while **New Hint** calls the hint flow.
   - This means script-vs-UI comparisons can accidentally be **hint-vs-solve** comparisons unless the script explicitly sets purpose.

2. **The UI always runs the canonical multi-attempt ladder orchestration with per-attempt callbacks and tier progression.**
   - `runGameSolver(...)` calls `runUnifiedSolverFlow(...)` with `executionMode='referee-with-compat-profiles'`, `resetAttemptHistory='level'`, and hooks (`onAttemptStart` / `onAttemptResult`) that expose attempt sequence and stop conditions.
   - The same flow is available to script callers, but script output usually summarizes only final status unless post-processed.

3. **Normalization paths are now close, but not guaranteed identical in every call site.**
   - UI play path obtains normalized level via `APP.LevelUtils.normalizeLevel(idx)`.
   - Node script path normalizes through `Solver.prepareLevelForSolver(raw, { source: 'raw', levelNumber })`, which routes to `normalizeRawLevelForSolver(...)`.
   - Both map 1-indexed raw coordinates to packed 0-indexed keys, but the UI path depends on the runtime level object currently in engine/editor, while script always starts from raw level source.

4. **UI-side validation trims malformed returned paths before applying hints/solve.**
   - `runGameSolver` normalizes entries and revalidates each candidate with `validateCandidatePath(...)` before applying.
   - For divergence debugging this is useful because a “solver ok” can still become “UI no usable path” if canonicalization/validation filters everything.

## What this implies for L92 and L26 specifically

- The L26/L92 flip pattern is consistent with **policy-ladder and purpose-sensitive ordering**, not just a single deterministic bug.
- For L92 timeouts in script but solves in UI buttons, first suspect a run-mode mismatch (`hint` vs `solve`) and attempt-ladder differences.
- For L26 solves in script but failures in UI, inspect per-attempt telemetry fields (family switching, forbidden first moves, trajectory-duplication penalties) because those can redirect search to help L92 while hurting L26.

## Concrete changes to make script runs converge with UI and improve reproducibility

1. **Always test both purposes in script for target levels (`--purpose=hint` and `--purpose=solve`) and store both outcomes side-by-side.**
2. **Record and diff attempt-history instrumentation per level (`attemptHistory`, `nextAttemptReason`, `trajectorySimilarityPenalty`, `revisitWithPerturbationTriggered`).**
3. **Freeze normalization source for A/B:** run one lane from `prepareLevelForSolver(raw)` and another from UI-normalized snapshots (captured through browser audit harness) to isolate normalization-vs-policy effects.
4. **Adopt dual-level acceptance gate for solver tuning:** reject changes that improve one of {L26,L92} while regressing the other unless both-solved frequency rises.

   - same budget and with/without `forbidden-first-moves`

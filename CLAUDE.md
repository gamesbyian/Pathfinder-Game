# Pathfinder Game — Developer Reference

## Project Overview

Pathfinder is a browser-based grid puzzle game. The player draws a continuous path on a rectangular grid from a starting **gate** to a **goal** cell. A solution is accepted only when all constraints hold simultaneously: exact path length, exact intersection count, and every object-specific obligation (must-pass, must-cross, portals, filters, landmarks, …).

`Solver.ts` generates the hint paths the in-game hint system serves. This file is the **current-state reference**: orientation, game rules, and the non-obvious rules/gotchas that prevent mistakes. Deep per-topic detail lives under [`docs/`](docs/README.md) (indexed in `docs/README.md`); the dated build history is in [`docs/history/development-journal.md`](docs/history/development-journal.md).

## Working in This Codebase

Rules earned by watching the same mistakes twice. The model is fast at producing *plausible* code and slow to notice that plausible ≠ correct, so the discipline lives in the process, not the generation.

- **Read before you write.** This repo is documented on purpose: the [`docs/`](docs/README.md) index + ADRs are the authoritative "why", and [`docs/architecture.md`](docs/architecture.md) says where new code goes. Read the doc *and* the files you're about to touch, then copy the pattern that's already there. Architecture invariants are machine-enforced (AST-based ESLint rules — see the Notes under Repository Layout); don't fight them, understand them.
- **Think, and state assumptions.** Many requests are underspecified ("add a constraint" is several different features). Name the interpretation you picked and the tradeoff. If a mechanic is genuinely ambiguous, ask — don't fill the gap with plausible code that passes a casual read and fails at the win-condition check.
- **Simplicity, minimal diff.** This codebase carries scars from past over-abstraction and haphazard growth. Write the smallest change the task allows; don't reformat untouched code; justify every changed line by the task. Abstract only after the third copy, never "in case we need it."
- **Verify before you claim done — but iterate freely before that.** This bar is a finish line: it gates **claiming a change done, reporting a result as validated, or merging** — it is *not* a per-iteration tax. While exploring a candidate on a branch (chasing a solve, trying a mechanism, tuning a constant), move fast and measure light — a small sample is plenty, skip the full-corpus/timing runs, and revert what you don't keep (see [`docs/testing.md`](docs/testing.md)'s "Iterating vs. gating" and the soft-vs-hard note: soft mechanisms that leave the win-check untouched can't produce a wrong answer, so they're safe to explore loose; only hard prunes/caches keep the soundness rigor *while* iterating). When you *do* claim it done: `npm run ci` must pass (static checks + Vitest + node validators). If you touched the solver's hot search path, `npm run solver:bench -- --check` must show **no regression vs the baseline** — the single hardest level can fail under sandbox CPU-throttling, which is *not* a code regression (confirm by re-running the pre-change code). **`solver:bench --check` only verifies the solved/failed set — it is silent on cost.** A change can pass it cleanly while making the corpus meaningfully slower (more nodes/wall-time per level, same outcome); always also compare `nodesExpanded`/total time before vs. after on the full corpus (a plain before/after `Solver.solve` sweep, ablation-gated if the change has an ablation flag, is enough — no dedicated tool exists yet). See the Solver Architecture gotcha below for the concrete case that caught this. Fixing a bug? Write the failing test first, watch it fail, then fix. Test behavior that can break, not that a constructor sets a field.
- **Debugging: investigate, don't guess.** Read the whole error, reproduce before changing anything, change one thing at a time. Don't silence an unexpected `null`/`undefined` with a guard — find *why* it's there or the bug just moves somewhere quieter.
- **Dependencies and platform constraints are load-bearing.** Every runtime dependency must be **bundled by Vite** (no new CDN `<script>`s) and survive `check:csp` + `check:third-party`. Prefer the stdlib or an existing utility over a new package; when you must add one, say why.
- **Solver strategy is keyed on level *features*, never level *identity*.** `check:no-solver-level-numbers` enforces this over the solver source and its docs — cite the feature regime ("navDensity ≥ 0.82", "≥3 must-pass"), not a level number, in code and comments.
- **New canvas-drawn visuals must be themed.** `check:canvas-theme-coverage` scans `modules/render/*.ts` and fails on any hex color literal that isn't sourced from `theme.colors.*` (see `theme-engine.ts`'s `deriveTokens` + `theme-normalizer.ts` for the fallback pattern) — a hardcoded color is invisible to every other check (not a CSS class, not banned syntax), which is exactly how the landmark objects and turn/satisfied badges shipped fully unthemed before this existed. A literal that must stay fixed regardless of theme (a universal hazard icon like the goose or the false-goal's bomb icon, an object's material cue like a fountain's water highlight, the intentional multi-color "rainbow" path style) needs a `// theme-exempt: <reason>` comment on the same line — the reason is the justification, not a rubber stamp.
- **Communicate precisely, especially uncertainty.** Say what you did and why, flag concerns even when you did exactly what was asked, and report what you did *not* run (e.g. the Playwright e2e/visual suites are not part of `ci`). "I'm not sure this path is CSP-clean" tells the reader what to check; "should be fine" does not.

## Pathfinder Game Rules

### Core Path Mechanics
- Path starts on a **gate** and ends on the **goal** (true goal, not a false goal).
- **Counted length** = number of nodes − 1 − portal jumps. Portals teleport for free.
- **Intersection** = entering a previously visited cell (excluding gate and goal revisits).
- The path must hit **exact** length (`reqLen`) and **exact** intersection count (`reqInt`).
- Moving diagonally or more than 1 step at a time is not permitted.

### Grid Objects
| Object | Behavior |
|---|---|
| **Gate** | Path start. Multiple gates possible (player picks one). Cannot be re-entered once left. |
| **Goal** | Path end (true win condition). Only one true goal per level. |
| **False goal** | Looks like a goal. Entering it triggers a trap (hazard) — path fails. Solver ignores false goals (MoveContext.SOLVER). |
| **Block** | Impassable. BFS distances and neighbors precomputed excluding blocks. |
| **Must-pass** | Cell that the path must visit at least once. Tracked via `mustMask` / `mpVisitedMask`. |
| **Must-cross** | Cell the path must enter from two opposite sides (i.e., cross through it at least twice). Uses `mustCrossMask` + `crossCounts`. |
| **Filter (regular)** | Forces entry along a fixed axis (axis=1 H, axis=2 V). Statically filtered out of `staticNeighbors` for wrong-axis neighbors. |
| **Flipping filter** | Starts with its declared axis; single-use — may be crossed at most once, ever (2026-08-06 design ruling, enforced by `flipperUsedMask`). Its required axis on that one crossing depends on level-wide crossing order, not a per-filter count: if it's the *k*-th distinct flipping filter crossed anywhere on the board, its axis is the declared one when *k* is odd, flipped when *k* is even — so a level with several flippers can require crossing them in a specific designer-intended order for each to demand the axis a solution needs. Cannot turn on it. Fully dynamic — can't be precomputed. |
| **Portal** | Pair of cells. Entering a portal forces an immediate jump to the paired exit at zero path-length cost. Portals cannot be reused. When standing on a portal cell and the last move was NOT a portal jump, `getNeighbors()` returns only the portal destination — bypassing static adjacency entirely. |
| **Goose** | Hazard. Entering a goose cell in PLAY mode fails the path. The solver ignores geese (MoveContext.SOLVER). |
| **Surround landmark** | Impassable. Path must visit all reachable 8-adjacent cells before finishing. Tracked via `surroundMask` + `surroundNeighborRemainingMasks`. |
| **Must-turn landmark** | Passable. Path must make a turn (of required direction: `either`/`cw`/`ccw`, relative to the level's default unrotated/unmirrored orientation) at this cell. Tracked via `mustTurnMask`. |
| **Adjacent-turn landmark** | Impassable. Path must make a required turn at one of its 8-adjacent passable cells. Tracked via `adjTurnMask`. |
| **Decorative landmark** | Impassable. No path constraint — visual only. |

**Cell occupancy is an absolute invariant: every cell holds at most one object.** A portal's `dest` is always another portal terminal, never any other object type — entering a portal moves the line to the paired terminal cell *only*. Enforced by `validateRawLevel` (`domain/level-schema.ts`) — the hard schema gate every level passes through regardless of authoring path (editor export, hand-written JSON, stress-test generation, Firestore import) — and mirrored by `validateLevelDetailed` (`domain/level-validation.ts`) and the editor's own one-object-per-cell placement guard (`getOccupant`/`placeOccupant` in `editor-occupancy.ts`). Move-generation code (`search-state.ts`'s `getNeighbors`, `move-rules.ts`, `step-processor.ts`, `path-state.ts`) defensively re-checks a portal destination against block/goose/false-goal status anyway — that's intentional defense-in-depth, not evidence the invariant is only conventional. Landmark-derived cells legitimately appear twice on the wire (once in `landmarks`, once in the derived `blocks`/`mustPass` bucket via `buildWireLevelData`) — that's the same conceptual object, not a conflict; both validators exclude landmark-derived coordinates from their occupancy checks via `baseLandmarkRole`. Two past gaps in this exact invariant (a generator letting a goal coincide with a portal destination; the landmark exclusion missing from `validateRawLevel` and rejecting legitimate submissions) are in [`docs/history/development-journal.md`](docs/history/development-journal.md#cell-occupancy-schema-gaps-2026-07-11--2026-07-15).

### Win Condition
All of the following must be true simultaneously when the path reaches the goal:
1. Counted length = `reqLen`
2. Intersection count = `reqInt`
3. All must-pass cells visited (`mustMask === 0` or `mpVisitedMask === initialMpMask`)
4. All must-cross constraints satisfied (`mustCrossMask === 0`)
5. All surround neighbor cells visited (`surroundMask === 0`)
6. All must-turn cells turned in required direction (`mustTurnMask === 0`)
7. All adj-turn constraints satisfied (`adjTurnMask === 0`)

### Landmark Wire Format
Landmarks are declared in the raw level JSON as a `landmarks` array; each entry has `x`, `y`, `objectType` (visual asset name), and `role` (`turn` optional for the non-suffixed turn roles):

```js
landmarks: [
  { x: 5, y: 5, objectType: 'park',     role: 'surround' },
  { x: 3, y: 3, objectType: 'library',  role: 'mustTurn',     turn: 'either' },
  { x: 2, y: 7, objectType: 'library',  role: 'mustTurnCcw' },
  { x: 7, y: 2, objectType: 'fountain', role: 'adjacentTurn', turn: 'cw' },
  { x: 9, y: 4, objectType: 'statue',   role: 'decorative' },
]
```

- **Passable** (path may enter): `mustPass`, `mustTurn`, `mustTurnCw`, `mustTurnCcw`.
- **Impassable** (added to `blockSet`): `surround`, `adjacentTurn`, `adjacentTurnCw`, `adjacentTurnCcw`, `decorative`.

`parseRawLevel` normalizes these into `surroundKeys`/`adjacentTurnKeys`/`adjacentTurnDirs` (parallel arrays), `mustPassTurnDirs: Map<key, TurnDir>`, and `landmarkMeta: Map<key, {objectType, role}>`. The coordinate-bearing field set has a single source of truth — `LEVEL_KEY_FIELDS` in `domain/level-codec.ts` (drives `remapLevelKeys`/`forEachLevelKey`), so shifts/resizes/bounds can't silently drop a field. The reverse direction has one too: **`buildWireLevelData()`** (same file) is the only normalized→raw serializer — used by editor export, submission, and review publish — so persisted levels always carry `landmarks` (a hand-rolled submission serializer formerly flattened them to plain `blocks`/`mustPass`, silently downgrading the mechanics on review). Duplicate detection (`domain/level-fingerprint.ts`, fingerprint **v2**) canonicalizes by landmark *mechanics*: landmark-derived coords are excluded from the generic buckets, so equivalent wire shapes fingerprint identically while a plain block ≠ a landmark at the same cell. Design record: [`docs/archive/landmark-submission-serialization-plan.md`](docs/archive/landmark-submission-serialization-plan.md).

**Fingerprint-version-bump gotcha**: the fingerprint doubles as the Firestore document key for Dev-Mode level ratings, and also feeds `scripts/import-published-levels.mjs`'s duplicate detection. Bumping `LEVEL_FINGERPRINT_VERSION` (last done v1→v2, 2026-07-03) therefore has ripple effects beyond the fingerprint module itself: it silently orphans every previously-saved rating unless the reader falls back to a frozen legacy fingerprint, and any script with its own structural-comparison logic (instead of importing `getLevelFingerprintSource`) will silently diverge. `level-rating-manager.ts` handles this via `getLegacyLevelFingerprints` (fall back to the old fingerprint on a miss, migrate forward on read) — treat this as the required pattern for any *future* version bump, not a one-off fix.

`TurnDir` (`'either' | 'cw' | 'ccw'`) is always relative to the level's default (unrotated, unmirrored) orientation — never to the path's travel direction or the currently displayed variant. Two independent transforms touch it, and must treat rotations and reflections differently because a reflection reverses chirality while a rotation preserves it: (1) the **editor's Rotate/Mirror buttons** (`input/editor-toolbar-controller.ts`) permanently rewrite the canonical level's coordinates via `levelUtils.applyCoordMapToLevel` → `remapLevelKeys` (`domain/level-codec.ts`) — Mirror passes `reflect: true`, which flips `mustPassTurnDirs`/`adjacentTurnDirs` values via `flipTurnDir` (`domain/landmark-rules.ts`); Rotate passes no reflect flag, correctly leaving them unchanged. (2) **Play-mode's random-per-load / "Whoa"-button display variant** (`engine/level-flow.ts`, `domain/geometry.ts`'s 8-way `transformPoint`/`transformAxis`) never touches the canonical level — only screen position and click-input are remapped — so the render layer applies `transformTurnDir(dir, variant)` (`domain/geometry.ts`) when drawing the mustTurn/adjacentTurn visual cue, flipping cw↔ccw for the 4 reflecting variants (4–7) so the on-screen arrow matches what's actually required in the displayed orientation.

## Solver Architecture

`modules/Solver.ts` is a thin facade over `modules/solver/*`. Strategy is selected by **level features, never identity** (see the Working rules). The full reference — core flow, archetypes, the declarative `ATTEMPT_POLICY`, DFS/beam mechanics, pruning, `prepLevel` data, plus CLI usage, the audit-JSON format, and debug/perf recipes — is **[`docs/solver-architecture.md`](docs/solver-architecture.md)**.

**Solution-space fingerprints** (`scripts/stress/solution-profile.mjs`/`solution-profile-lib.mjs`/`solution-profile-compare.mjs`, [`docs/solution-profile.md`](docs/solution-profile.md)): analysis tooling — not a production feature — that turns each known-solvable level's *accepted hint corpus* into an aggregate behavioral fingerprint (cell/edge/turn/portal/must-cross distributions, pairwise distinctiveness, discovery-saturation), so an as-yet-unsolved stress-corpus-2 level can be compared against known-solvable families via `npm run stress:solution-profile-compare -- --target-level=<n>` when the production solver fails on it. Distinct from `domain/level-fingerprint.ts` (shape/dedup hash) and `scripts/solver-fingerprint.mjs` (determinism hash) — this one hashes nothing about the level itself, only how its *solutions* behave. The committed libraries (`reports/stress/solution-profile-{published,corpus1}.json`) are **kept fresh automatically**: `solution-profile-compare.mjs` checks each library's stored hint-signature against the live corpus before every comparison and transparently regenerates it in place if stale (see the doc's Freshness section) — there is no separate "remember to rebuild this" step, and no need to hook regeneration into hint-discovery tooling.

**AI-assisted manual solving** ([`docs/ai-assisted-manual-solving.md`](docs/ai-assisted-manual-solving.md)): proposed methodology (one worked demonstration, not yet validated on a genuinely unsolved level) for whether an AI agent reasoning by hand about a level — no solver, no stored hints — can surface new solver heuristics. Verdict: mostly no, since the puzzle's "cleverness" is a property of its combinatorics, not of who's reasoning about it, so an AI's self-described strategy mostly reconstructs techniques the solver's scoring/attempt-policy code already encodes. The one recommended real use is **differential diagnosis**: hand-solve a level the solver currently fails on, then diff the accepted path against the solver's own search trace at each divergence point — the same instrumented-ablation model that found the real R02248/R01465 fixes, not narrative-mining. Includes the exact protocol for verifying (`validateCandidatePath`) and recording (`solver.id`, never reusing `SOLVER_ID`/`HUMAN_PLAYER_ID`; `getLevelFingerprint` not `getLevelFingerprintSource` for `levelRevision`) a manually-found hint's provenance correctly.

**Fast portfolio scheduler experiment** (`schedulerMode: 'portfolio-experiment'` in `modules/solver/orchestration.ts`'s `solveLevel`, config in `data/config/portfolio-experiment.js`, [`docs/fast-portfolio-scheduler-plan.md`](docs/fast-portfolio-scheduler-plan.md)): opt-in, **not the production default** — every live app code path (Play/Editor/Review/hint discovery) uses `schedulerMode: 'legacy'`; `portfolio-experiment` is set only by offline CLI tooling. **Current verdict: not production-ready** — every measured variant is slower than legacy on the published corpus even where it retains full solvability; see `docs/solver-architecture.md`'s "Fast portfolio scheduler experiment" section for the CLI usage, current numbers, and why a legacy-side speed change can silently invalidate a previously-recorded portfolio verdict.

**Batch-testing a solver change against the unsolved corpora** (recurring need, not a one-off): start from `docs/solver-architecture.md`'s "Which tool for a corpus/large-batch solve" table — it's the tool-selection index for every batch/CLI entrypoint (`stress:benchmark` variants, `solver:direct`, `scripts/portfolio-solve-sweep.mjs`, `scripts/repair-direct-probe.mjs`). None of this substitutes for `solver:bench --check`'s regression-safety requirement above — it's the complementary "iterate fast" half of the same workflow. **A full corpus refresh (both corpus-1 and corpus-2) can be parallelized across GitHub Actions** — `.github/workflows/solver-stress-refresh.yml` (`workflow_dispatch`-only; see that directory's `README-solver-stress-refresh.md`) splits both corpora across one 20-shard matrix (each shard solves a slice of both, folded together 2026-07-23 to avoid a 21st job queuing behind the matrix — see that README's "Sharding corpus-1 into the matrix" section) and commits one combined result to `main`. This replaced the older 20-branch `solver-corpus2-batch-*.yml` scheme (deleted; `README-solver-corpus2-batches.md` is kept only as a historical record of that design and two stale-code/merge incidents worth reading once). Current known-solved count and refresh history: `data/stress/README.md`. **Any batch tool must report/persist results between levels (never only at the end) and default to the fastest configuration that still answers its question** — see `docs/solver-architecture.md`'s "Two requirements for any batch tool" section for the exact requirements and the incidents that prompted them, and [`reports/2026-07-23-solver-batch-speed-and-hint-provenance.md`](reports/2026-07-23-solver-batch-speed-and-hint-provenance.md) for the full 2026-07-23 batch-speed/provenance work (adaptive node budgets, mid-search budget enforcement, `--prime-winner`, the `scoreMove` hot-loop fix, and the beam connectivity-throttle experiment — tried, found to regress on a clean corpus-1 A/B, and reverted) and its follow-up list.

Cell-key & axis encoding (used throughout the domain/solver core):
```js
PACK(x, y) = ((y << 16) | x) >>> 0;  UNPACK(k) = { x: k & 0xFFFF, y: (k >>> 16) & 0xFFFF }
KEY_SPACE  = 1 << 20   // covers grids up to 15×15
AXIS_H = 1  // horizontal (dx≠0)   AXIS_V = 2  // vertical (dy≠0)   AXIS_NONE = 0
```

### Common gotchas
- **Portal forced-move**: at a portal cell when the last move was not a portal jump, `getNeighbors()` returns only `[portal.dest]`, bypassing static adjacency — portal entry forces the exit.
- **Gate cells cannot be re-entered**: excluded from `staticNeighbors` targets; `isValidMove` also guards this.
- **Must-cross lock**: turning at a 1st-pass must-cross cell consumes both H and V axis bits, blocking the required 2nd crossing. Dynamic check in `_isMoveDynValid`.
- **Flipping filters** are fully dynamic — current axis depends on `flipperUsedMask` parity, so they can't be precomputed into `staticNeighbors`.
- **Dense levels** (`navDensity ≥ DENSE_LEVEL_NAV_DENSITY`, named in `solver/prep.ts`): `mustMaskForDFS` is 0, not `initialMustMask`, to avoid disrupting near-Hamiltonian DFS ordering; must-pass correctness is enforced via `mpVisitedMask` instead.
- **Editor validator is a heuristic, not a solver**: `validateLevelDetailed()` inspects only nearby cells and can both false-positive and false-negative on real solvability — confirm with the solver when it matters (the function's own docstring says so).
- **Memoizing a lower bound (or any search-dependent value) is only sound if the cache key captures every state variable the value actually depends on — an under-keyed cache silently returns a WRONG bound, which can wrongly prune a reachable solution (a correctness bug, not just a missed optimization).** `mustPassLowerBound` is safely memoized on `(pos, mpVisitedMask)` alone because a must-pass cell only ever needs one visit, so that pair fully determines the bound. `mustCrossLowerBound` is **not** safely memoized the same way: a must-cross cell needing its 2nd visit has a bound that also depends on `crossCounts[i]` and *which axis* the 1st visit used (`edgeUsage`) — two states can share the same `(pos, mustCrossMask)` yet need different bounds. Its actual cache key (`lower-bounds.ts`) encodes a base-4 digit per must-cross index for exactly this reason; don't simplify it back to `(pos, mask)` without re-deriving why that's unsound. **This already caused a real bug** (undersized MST scratch buffer → silent TypedArray truncation → a bound computed from stale data came out tighter than mathematically valid, risking a false "unsolvable"); see [`docs/solver-architecture.md`](docs/solver-architecture.md#history-the-mst-bound-scratch-buffer-bug) for the full writeup. Any new memoization on solver state must ship with the same differential-testing rigor that fix did, not just "tests still pass."
- **`solver:bench --check`'s "no regressions" only means the solved/failed set is unchanged — it says nothing about cost.** A change that adds retries or extra attempt configs can pass it cleanly while making the corpus slower for the same outcome. **This happened** with an early version of the repair-probe multi-seed retry (`REPAIR_PROBE_ORDINARY_SEED_SALTS`, `orchestration.ts`): 160/160 on `solver:bench --check`, but ~14% slower full-corpus wall time from one level burning every retry seed for zero benefit. The retry width was narrowed once this was measured (current numbers in `orchestration.ts`'s own comment on the constant). Any future retry/multi-attempt widening needs a full-corpus before/after timing comparison, not just a solvability check — see `docs/testing.md`'s "Speed, separately from solvability" note. **Retroactively, `scripts/stress/hint-cost-drift.mjs` mines hint provenance for cost changes nobody measured at the time** — wherever the same attempt config found the same solution under the same budget at two different commits, provenance already holds a free before/after (949 such comparisons as of 2026-07-29: 800 byte-identical, 149 drifted). It covers all three corpora, where `--check`'s own cost delta covers only the published one; treat a drift row as a lead, not a verdict (see that doc's note for why).
- **A correctness fix in a shared code path can silently orphan a caller-specific mechanism that depended on the exact condition it removed.** The July 10 consolidation of `dfsFromGate`'s and repair-search's pruning gauntlets into `evaluatePrunedMove()` correctly closed a real bug (repair-search's random walk could illegally walk past a non-winning goal cell) — but that illegal case was also the only trigger for repair-search's near-miss bookkeeping (`computeBadness`, elite-pool splice), so the fix silently killed that whole rescue mechanism (full-corpus ~20% recovered once fixed by generalizing the bookkeeping to the `'deadend'` outcome too). **Lesson**: when a refactor's diff shows "reject a case that used to fall through to X," grep every place X's outcome was the trigger for something else. Full investigation: [`reports/2026-07-16-repair-search-elite-splice-regression.md`](reports/2026-07-16-repair-search-elite-splice-regression.md).
- **A scoring term tuned for the common case can become actively self-defeating on a rare, dense one — and whether it does can depend on grid orientation alone.** `scoring.ts`'s `SCORE_INTERSECTION_SETUP`/`SCORE_SURROUND_URGENCY` (and to a lesser extent `SCORE_PHASE_SCALING`/`SCORE_REVISIT_PENALTY`) can each individually lock in an unrecoverable early self-crossing on a near-Hamiltonian, high-`reqInt` level — which term dominates is level-specific, not one universally-broken term, so no global scoring change was made. Mitigated instead by a bounded, opt-out **attraction-diversity last-resort pass**: after the main loop and repair fallback both fail, `solveLevel()` reruns the attempt ladder once more with `SCORE_GOAL_ATTRACTION` disabled, in its own small additive budget, at zero cost to levels that already solve. This is an active research area (~7% of a `dfs-plain` sample are confirmed cases) — current state, mechanism, and the full case history (R02248/R01465/R00648 and others): [`docs/solver-architecture.md`](docs/solver-architecture.md#attraction-diversity-last-resort-pass-2026-07-16) and [`docs/solver-development-roadmap.md`](docs/solver-development-roadmap.md).
- **A timed-out beam or DFS attempt's `nodesExpanded` used to always read exactly 0 — a 100% structural instrumentation gap, not a search-quality signal.** Both `beamSearchFromGate` and `dfsFromGate` only credited `prep._metrics.nodesExpanded` on success/natural exhaustion, never on any timeout exit path — so a timed-out attempt's node count couldn't be used as a "how much did it search" proxy for anything (one corpus-wide clustering attempt built on that assumption produced a meaningless bucket). **Fixed 2026-07-16/17** for both search functions; verified via `solver:bench --check` (no regressions) and new regression tests in `modules/solver/search.test.ts`. Full writeup: [`reports/2026-07-16-beam-nodesexpanded-instrumentation-gap.md`](reports/2026-07-16-beam-nodesexpanded-instrumentation-gap.md).
- **`solveLevel()`'s worst-case wall time is up to `(1 + 6 + 1 + N) × timeBudgetMs`** (repair fallback's 6x, the attraction-diversity pass's 1x, and the admissible-order-search last-resort tier's own `N`× — `N` = `attempts.ts`'s `ADMISSIBLE_ORDER_PROFILES.length`, 5 as of 2026-07-24 (includes the `'none'` no-tie-break entry), since each entry now runs as its own sequential sub-pass with its own full `ADMISSIBLE_ORDER_BUDGET_FRACTION`, not one shared total — see that constant's own comment for why splitting one total across profiles was tried first and found to starve the tier's own best-performing profile below its validated condition), **controlled by THREE independent `SolveOpts` fields** — `repairBudgetFractionOverride`, `attractionDiversityBudgetFractionOverride`, and `admissibleOrderBudgetFractionOverride` (the last one scales ALL of the tier's per-profile sub-passes together, not per-profile individually) — **not one**. A batch tool that wants to honor the solver-testing-shouldn't-wait-on-extensions policy must set all three (or use the `disableExtraBudgetPasses: true` convenience, which sets every one of them to `0` unless overridden individually — the one field a new last-resort pass needs to be wired into so this doesn't have to be rediscovered per pass). The two interactive solve UIs (`solver-controller.ts`, `review-controller.ts`) use `disableExtraBudgetPasses: true` for exactly this reason. See [`docs/solver-architecture.md`](docs/solver-architecture.md#attraction-diversity-last-resort-pass-2026-07-16) for the attraction-diversity mechanism and the budget-composition bugs this shipped with and had fixed, and `modules/solver/orchestration.ts`'s `ADMISSIBLE_ORDER_BUDGET_FRACTION` for the admissible-order tier.
- **Those `timeBudgetMs` fractions are denominated in TIME, but what actually stops a level in a batch run is `nodeBudget` — ONE cumulative ceiling every tier checks against the same running `prep._metrics.nodesExpanded`. Provisioning a late tier in the first unit does not give it any of the second.** The admissible-order tier shipped with `ADMISSIBLE_ORDER_BUDGET_FRACTION = 1.0` per profile and still ran essentially never: on the 2026-07-30 typical-budget corpus-2 baseline, all **141** unsolved levels carrying a validated admissible-order hint terminated at exactly the 20M node cap after a mean of 14.4 ladder attempts, with a sub-pass from the tier recorded on **1** of them — the earlier tiers ate the whole ceiling, so the tier with plenty of clock got zero nodes. Same bug shape as the 2026-07-17 repair-probe node starvation. Fixed by `ADMISSIBLE_ORDER_NODE_RESERVE_FRACTION` (`orchestration.ts`, 0.25): a slice of the external `nodeBudget` withheld from the probe/main-loop/repair/diversity tiers via `earlyTierNodeBudget`, leaving the tier the difference — a reserve, **not** a reorder, since nothing measured says the technique should run earlier. Strictly a no-op when `nodeBudget` is `Infinity` (every production path) or the tier is suppressed; the reserve is computed from the tier's *real* run condition, because reserving for a tier that won't run would strand the nodes and shrink every `disableExtraBudgetPasses` caller's effective budget. Two things to keep in lockstep when touching this: the reserve's gating predicate and the tier's own loop condition (drift either way and the solve strands nodes or spends a reserve that was never withheld), and `nodeBudgetReached`, which must stay true when the ceiling truncated the *early* tiers even though the total lands under `nodeBudget` — otherwise a budget-limited level reports as searched-out. Results and per-level detail: [`reports/2026-07-30-admissible-order-node-reserve.md`](reports/2026-07-30-admissible-order-node-reserve.md).
- **A caller-supplied partial `ablation` config used to silently disable every OTHER unset flag.** Every ablation-gated read site checks `(!cfg || cfg.SOME_FLAG)` — a sparse object like `{ STRATEGY_REPAIR_PROBE: true }` made every *other* unset flag read `false` instead of its real default `true`. Fixed 2026-07-18 by `normalizeAblationConfig()` wrapping any externally-supplied `opts.ablation` in a `Proxy` at the only two places it becomes `prep._cfg`; see [`docs/solver-architecture.md`](docs/solver-architecture.md#ablation-laboratory) for the current mechanism. Don't hand-roll a merge with `defaultConfig()` elsewhere — the normalization at the boundary is what closes this everywhere at once.
- **Open board space is a puzzle variable in its own right, not inert scaffolding around the "real" puzzle** (objects + win metrics). A level with more navigable-but-unused space is not thereby an unchanged or strictly-easier puzzle from the solver's point of view — the raw search space changes even with `reqLen`/`reqInt`/object inventory held fixed, and several techniques key off it directly (`perimeterSweep` scans relative to the grid boundary; the repair probe's search order is empirically sensitive to it). **Confirmed empirically**: growing a repair-gated level's grid with only empty, untouched space flipped it between complete repair-probe failure and success across multiple sizes tested. Treat available space (navDensity, grid size relative to content) as a first-class dimension of a level's solver-difficulty profile. See [`reports/families/2026-07-15-re-embedded-cousin-grid-growth.md`](reports/families/2026-07-15-re-embedded-cousin-grid-growth.md) and [`docs/sibling-cousin-system.md`](docs/sibling-cousin-system.md).
- **Every batch tool's `--levels=<spec>` requires an explicit `pos:`/`id:` prefix on a bare number/range** (`pos:5`, `id:R00237` — a full id string needs no prefix). Fixed 2026-07-18: a bare number used to mean a literal array position in some tools and an ID-suffix lookup in others, and picking the wrong one silently selected a different real level rather than erroring. Full detail and the current shared-parser implementation: [`docs/solver-architecture.md`](docs/solver-architecture.md#--levels-selector-syntax--explicit-posid-prefix-required-fixed-2026-07-18).
- **"Leaving along a used axis is legal when going straight" is the single most repeat-offending trap in this codebase's connectivity/deadlock reasoning — assume any new "hard wall" check needs it, and prove that on paper before writing code, not after.** A cell whose `edgeUsage` reads both-axes-spent is NOT unconditionally unenterable: if the path is *currently standing on it*, having just arrived via one of those axes (possibly its second visit, so both bits are already set), it can still legally continue straight through on that same axis. This one exemption independently caused (1) `topology.ts`'s original flood-fill design (which is why `_floodFillBits`/`_floodFillAxis` force `pos` traversable "regardless of its own visit count"), (2) a 261-false-rejection near-miss in `mustCrossForcedNeighborDeadlocked` (`lower-bounds.ts`) caught before it ever shipped default-on by replaying every stored solution through real search state, and (3) two separate falsifications of "must-cross forced-edge propagation" (`reports/2026-07-31-mustcross-forced-structure.md`'s step 4) — first a broad version (63,496 violations over 1.1M edges), then the report's own narrower framing (5,206 violations over 225K edges), because each axis's "claim" can independently extend straight through to that axis's *other* side in the same motion. **Any new derivation of the shape "cell/edge X is provably unusable" must explicitly rule this out, and must be falsified against every stored solution before being trusted — a small hand-built test fixture is not enough**, per this same pattern's track record.
- **`PrepLevel`'s `mustPassIndex`/`mustCrossIndex` (and `flipperIndexMap`) use "index + 1, 0 = absent" encoding — the SAME zero-means-absent bias as `staticNeighborKeys` — not "-1 if absent."** The doc comments said "-1 if absent" for years; every real read site (`scoring.ts`, `search-state.ts`) already correctly undid the `+1` bias, but a new read site trusting the stale comment and checking `!== -1` against an `Int8Array` that is *never actually -1* in this encoding silently treats every cell as a hit — in one real case (2026-08-05, `prep.gateForcedFirstStepKey`'s first draft) this made a rule "force onto a gate's only neighbor" regardless of whether it was must-cross at all, and the resulting soundness pass ("90 instances, 0 violations") was **vacuous**, not reassuring — a gate's one-and-only neighbor can never be contradicted by a real solution no matter what the rule claims about it. Comments fixed in `types.ts`; the general lesson is that a soundness pass with suspiciously few/exactly-expected instances is itself a signal to double-check the derivation found what it claims to have found, not just that violations are zero.

## Level Stats
- **156 levels total** (test levels 148–150 use landmark mechanics).
- Max must-pass 4 · max must-cross 4 · max portals 3 pairs (6 keys) · max flipping filters 4 · grids up to 15×15, **always square** (`grid.w === grid.h` — every published level is square; no rectangular level has ever shipped). All masks fit in 32-bit integers (no BigInt).
- **Grids must be square.** Enforced by `validateRawLevel` (`domain/level-schema.ts`) — the same hard schema gate every level passes through regardless of authoring path, so a rectangular level can't reach any corpus. Don't infer from `PortalLike`/`CoordLike`-style loose typing elsewhere that grid shape is similarly unconstrained — it's the one dimension-shaped invariant that's hard-enforced. History of the 2026-07-11 corpus cleanup this required: `data/stress/README.md`'s "Square-grid cleanup" note.
- Level coordinates in `data/levels.json` are **1-indexed**; the solver normalizes to 0-indexed internally.
- ~9,600 hint paths total feed the in-game hint system; stored in the per-level `data/hints/<id>.json` artifact (split out of `levels.json` so the boot payload is the ~144 KB authored data, not the ~2.5 MB corpus) and **lazy-loaded per level** on first hint request via `data.getHints(level)` (the raw level object, not a number — see the Hint provenance section below). For the **published** corpus, `getHints` also merges in any Firestore-stored supplemental hints for that level (`data.ts`'s `withFirestoreHints`, keyed by the level's fingerprint — never for the stress corpora, which aren't real published levels) — see the Provenance section below for where those come from. `getHints` always returns the **full** (local + Firestore) hint set — curation and the heat-map are client-side derivations over it. In play mode the player cycles a **curated** mutually-distinct subset (not all of them) — the selection metric, coverage guarantees, and cap live in `modules/domain/hint-selection.ts` ([`docs/hint-curation.md`](docs/hint-curation.md)); the heat-map still uses the full set.
- **Every published level carries a persistent `id`** (`P00001`..`P00156`, backfilled 2026-07-15 — see `docs/archive/level-id-unification-plan.md`), matching the letter-prefixed ids both stress corpora already had. Player-submitted levels are imported from Firestore via `npm run levels:import-published` (runs under `tsx`; matches by the same canonical `domain/level-fingerprint.ts` fingerprint the app uses for submission/publish duplicate detection — a level already in `levels.json` has only its *new* hints merged in — deduped by path signature, capped at 1,000 — instead of being re-appended as a duplicate; a genuinely new level is appended and gets the next unused `P`-prefixed id, minted by `makeLevelIdMinter()` following the same never-reused idCounter pattern the stress generators use; regenerates `level-heatmaps.json` when anything changed). The script exports its pure helpers (`normalizeLevel`/`fingerprint`/`mergeNewHints`/`makeLevelIdMinter`, unit-tested in `scripts/import-published-levels-unit-tests.mjs`) and guards its network-touching `main()` behind an `import.meta.url` entrypoint check, so importing it never has side effects. A level only gets its permanent id at this graduation point (generation time for stress corpora, import time for published) — the Firestore `published_levels` staging collection itself stays keyed by Firestore's own opaque doc id + fingerprint, unaffected by this.

## Provenance

Two independent, deliberately-mirrored append-only provenance schemas — one per hint, one per level. Neither is ever overwritten; both only ever gain new history entries. Neither affects level fingerprinting (`level-fingerprint.ts` excludes both `hints` and `provenance` from its comparison fields), so provenance never creates a false "different level."

### Hint provenance
- Canonical type: `Hint = { path: number[]; provenance: HintProvenanceEntry[] }` in `modules/domain/hint-types.ts`. A hint's `provenance` array holds one entry **per discovery event** — if the same path is independently rediscovered by a different technique/run, that's a new entry appended to the same hint, not a new hint (never a rejected duplicate that silently loses its provenance — `scripts/hint-workbench.mjs`'s generators surface a rediscovery of an already-known path instead of dropping it, specifically to keep this invariant true end-to-end). Each entry nests `solver` (family/config), `search` (technique, termination reason, budget, seed, nodes expanded, elapsed ms), and `context` (hint-guided flag, level revision) sub-objects — see the type for the exact fields.
- **A repeat entry from the same technique is not redundant — it is usually the load-bearing one.** Measured 2026-07-29 over all three corpora: of 6,570 hints carrying multiple same-technique entries, only ~5% involved a genuinely different attempt config; the rest are the same config re-run, and what makes them valuable is the *difference* between the runs — overwhelmingly the solver commit, which is the sole input to `scripts/stress/hint-cost-drift.mjs`'s cross-commit cost signal. Do **not** collapse entries that share a technique/profile/budget but differ in `solver.version`, `attemptIndex`, or `nodesExpanded`; each is a distinct run. The only genuinely redundant shape is one run appending its result twice: an entry identical in every field except `foundAt` and the host-dependent `elapsedMs`/`cumulative*` measurements. 47 such entries existed corpus-wide (0.05% of 88,451), all `prefix-anchored`/`enumerate-targeted`, every one with a `foundAt` gap of 0–1ms; removed by `scripts/dedupe-hint-provenance.mjs` (idempotent, dry-run by default). Removing those *upholds* the one-entry-per-discovery-event rule rather than breaking append-only. **Wall-clock must be excluded from that identity check** — a first pass that required `elapsedMs` to match too found only 24 of the 47, missing every double-append whose two writes sampled the clock a millisecond apart.
- **After that, redundancy is zero and the remaining differences are each substantive.** Dropping one field at a time from the identity check shows what actually separates co-existing entries on a hint: `nodesExpanded` (11,061 entries differ *only* by it — the cost-drift signal), `solver.forcing` (2,290 — which technique deliberately pinned a gate/first-step), `solver.version` (287 — the cross-commit input to `hint-cost-drift.mjs`). Non-redundant is not the same as demonstrated-useful, though: so far only the ~949 cross-commit groups have a tool reading them. **The larger limitation is the opposite one — 7,270 of the published corpus's 12,517 hints (58.1%) carry no provenance at all** (they predate the schema; both stress corpora are at 0%), so more than half the regression-gate corpus is invisible to any provenance-derived analysis.
- **The hint corpus is valid solutions gathered by ANY means — NOT a measure of what the solver finds on its own.** `Solver.solve()` is always agnostic to saved hints (the orchestration search never reads them; `createVarietySearch` is a separate API). But hint-discovery *does* use existing hints: System B / `prefix-anchored` (`variety-search`'s `anchoredFromSeed`) starts from a known hint's prefix and completes it, deliberately "rescuing tight levels" — so it can produce *valid* solutions the cold solver would never reach. Such finds are marked `context.hintGuided: true` and `solver.technique: 'prefix-anchored'` (the flag's whole purpose: "not independent evidence the way a cold find is"). **If you ever use the corpus to ask "what can the solver find cold?" — solver-capability benchmarking, "is this level solver-solvable", regression baselines — you MUST exclude `hintGuided`/`prefix-anchored` entries** (and `witness`/`human-solved` ones); a level can carry hints yet be unsolvable by cold search. `check:hint-validity` only proves every hint is *PLAY-valid*, never that the solver can find it. The per-provenance-source bucketing in `docs/solution-profile.md` (`classifyProvenanceSource`) is the existing machinery for this split.
- **Dual-field storage pattern**: every place that carries hints keeps two parallel fields — a plain `number[][]` (`.hints` / `.foundHintsSinceLoad`) for existing path-geometry/dedup consumers that only care about the route, and a canonical `Hint[]` (`.hintRecords` / `foundHintsSinceLoadRecords`) carrying the provenance. The two are bridged only at storage/transport boundaries via `reconcileHints`/`mergeHints` (`modules/domain/hint-types.ts`) — don't hand-roll the merge elsewhere.
- **Provenance now captures which internal solver attempt config won, not just which discovery technique** (2026-07-23, `reports/2026-07-23-solver-batch-speed-and-hint-provenance.md`): `HintSolverProvenance` gained `beamWidth`/`diverseBeam`/`gateKey` (siblings of `profile`/`template` — "which config won," analogous to but distinct from `HintSolverForcing.gateKey`'s "a technique deliberately pinned this gate on purpose"); `HintSearchProvenance` gained `seedSalt` alongside the existing derived `randomSeed`; `HintSolverForcing` gained `repairMustTurnBiased`/`repairTurnBiased` (a repair winner's variant identity — previously every repair winner collapsed to the same flat `technique: 'repair'` string, which is what blocked asking "how often does the must-turn-biased attempt actually win" in the first place); an attraction-diversity-pass winner is recorded via the *existing* `disabledFeatures` field (`ATTRACTION_DIVERSITY_CANDIDATE_FLAGS`), not a new one. All of these are code fixes, not data backfills — hints stored before each fix simply lack the field until rediscovered, same as the pre-existing `randomSeed` gap.
- On disk, all 3 corpora use the same per-level artifact format (`{schemaVersion: 3, hints: Hint[]}`), read/written exclusively through `scripts/level-data-io.mjs` (`readLevelHints`/`writeLevelsWithHints`/`parseHintFileContents`/`stringifyHints`) — never hand-edit or re-serialize these files directly: published → `data/hints/<id>.json`; stress-corpus-1 → `data/stress/hints/<id>.json`; stress-corpus-2 → `data/stress/hints-random/<id>.json` (a sibling directory, not `hints/`, since corpus 1 and 2 share `data/stress/` as a parent but number levels independently — see `hintsDirFor` in `level-data-io.mjs`). The join key is `hintKeyForLevel()`'s job: a level's own persistent `id` string when it has one (every level in all 3 real corpora, post-2026-07-15 — used verbatim, not stripped to a bare number, since Corpus 1 mixes S-/R-prefixed ids whose numeric suffixes can collide), else its 1-based array position (a level with no id yet — an editor draft, or a Firestore staging doc not yet pulled in by `levels:import-published`; migration history in `docs/archive/level-id-unification-plan.md`). Runtime hint fetch (`modules/data-asset-loaders.ts`, `DataService.getHints` in `modules/data.ts`) is id-aware in lockstep with on-disk storage: `getHints` takes the raw level object itself (not a position), reads `level.id` to build the fetch URL, and falls back to a level's inline `.hints` otherwise.
- **A "which config won" field added to an *intermediate* provenance-building object is not the same as that field reaching the persisted `HintProvenanceEntry`** (2026-07-25, `reports/2026-07-25-hint-tool-comparison.md`'s "is persisted provenance actually complete" follow-up): the 2026-07-23 `admissibleOrder: winner?.admissibleOrder ?? false` fix to `hint-ablation-generator.ts`/`diversification.ts`'s baseline-phase `consider()` call was itself incomplete — `candidateEventFromDiscovery` (the function that actually builds the persisted event) never read `.admissibleOrder` back out, so it was silently dropped before ever reaching `makeProvenanceEntry`, the entire time the earlier fix was believed complete. A near-identical gap was found the same day in the new `hint-enumeration.ts` `orderBy: 'admissible-slack'` option: threaded correctly into search *behavior*, never wired into what gets persisted. Both fixed the same way — a `technique`-string colon-suffix (e.g. `'enumerate-targeted:admissible-slack'`, `'ablation-full:baseline-admissible-order'`) plus reusing the existing `profile` field for tie-break identity, following `HintSolverProvenance.technique`'s own doc comment's already-established convention, rather than adding a new boolean field. **Lesson**: when adding "which internal config won" to provenance, trace the value all the way to the `makeProvenanceEntry`/`hintProvenanceEntryForEvent` call site and confirm a field with that exact name is actually read there — an intermediate object holding the right data is not sufficient, and a plausible-looking fix that stops one layer short silently ships as a no-op. Also watch for exact-string technique comparisons (`=== 'prefix-anchored'`) breaking once a suffix is introduced — use `.startsWith` instead.
- Provenance is attached **at find-time**, regardless of whether the hint is ultimately submitted: `modules/solver/hint-provenance.ts`'s `deriveSolveAttemptInfo`/`provenanceFromSolveResult`/`hintsFromVarietyResult` are the single source for building entries, called from both the UI solver path and script tooling (`scripts/hint-workbench.mjs` and friends) so the two never drift into different shapes.
- Provenance persists through the editor → submission → review → publish pipeline unchanged except for appended entries; see `submission-controller.ts` and `review-controller.ts`.
- **A published level's hints aren't only ever local.** Firestore's `local_level_hints/{fingerprint}/entries/{entryId}` collection holds supplemental hints for a level that lives in `levels.json` (not Firestore) — any authenticated session (every player gets one at boot) may add an entry, and `data.getHints` merges it with the local set transparently (see the Level Stats section above). Two write paths feed it: a hints-only resubmission of an already-published level (`submission-controller.ts`'s local-corpus-match path) and an invisible auto-save on every ordinary Play-mode win (`win-controller.ts`'s `saveWinAsHintIfNovel`, fire-and-forget so a Firestore failure never affects the player) — both gated by the same novelty check against the merged local+Firestore set and a 5,000-hints-per-level soft cap. Full write-path/rules detail: [`docs/firestore-security-model.md`](docs/firestore-security-model.md).

### Level provenance
- Canonical type: `LevelProvenance = { history: LevelProvenanceEntry[]; origin; confidence }` in `modules/domain/level-provenance-types.ts`. Each `LevelProvenanceEntry` records one lifecycle event (`actor`, `action`, `method`, `detail`, `timestamp`) — e.g. `authored`/`generated`/`submitted`/`reviewed-approved`. `origin` and `confidence` are derived summaries (`deriveOrigin`) re-computed from `history` on every append via `appendProvenanceEntry` — never hand-set independently of the history that justifies them.
- Lives directly on the level object (`EngineLevel.provenance`, `modules/domain/level-schema.ts`) alongside the grid/hints/win-metrics — **not** in a separate report or doc. `null` (never silently omitted) means "no known provenance," e.g. very old pre-schema data.
- **Invariant: every newly-created level must include provenance.** It is stamped at the moment of creation, never backfilled after the fact for new levels:
  - Editor `createNewLevel()` (`modules/editor.ts`) stamps `{actor: 'human', action: 'authored'}`.
  - Both stress-corpus generators (`scripts/stress/generate.mjs`, `scripts/stress/generate-random.mjs`) stamp `{actor: 'procedural', action: 'generated', method: <generator id>, detail: {...batch/seed metadata}}`.
  - Submission (`submission-controller.ts`) appends `{actor: 'human', action: 'submitted'}` on top of whatever provenance the level already carried.
  - Review approval (`review-controller.ts`, non-hint-addition path) appends `{actor: 'human', action: 'reviewed-approved'}`.
- Carried through the wire format like any other level field: `domain/level-codec.ts`'s `normalizeMetadata` (parse + clone), `denormalizeLevel`, and `buildWireLevelData` all pass `provenance` through explicitly — it is **not** covered by any implicit "everything else" spread, so a new serialization boundary must add it by name or it silently drops (this exact class of bug previously hit `hints` before the dual-field pattern existed).
- **Enforced by `check:level-provenance`** (`scripts/check-level-provenance.mjs`, part of `npm run check`): hard-fails if any level in any of the 3 real corpora has a missing/empty `provenance.history`.
- All pre-existing levels (156 published + 450 stress-corpus-1 + 1700 stress-corpus-2) were one-time backfilled (`scripts/backfill-level-provenance.mjs`) rather than left without provenance. Published-corpus confidence tiers came from a retired classifier report that had already cross-referenced Firestore rating tags (`certain-human`/`certain-ai` from `great`/`common` tags, else `confidence: 'likely'` for untagged levels ≤130 — see the entry's own `detail.reason` for the exact tier reasoning); stress-corpus entries were built directly from each level's own `stressMeta` (`confidence: 'certain'`, since these are unambiguously generator output). This backfill fully replaced an earlier read-side-only classifier/report system (`docs/level-corpus-provenance.md` and friends, since deleted) that computed the same facts on demand instead of storing them on the level.

## Firebase Integration

The app reads/writes level submissions and player progress to Firestore. `firebase-config.js` is the **public client-side web config — safe to commit** (authorization lives in Firestore rules). Firebase uses the **modular SDK** (`firebase/app`/`auth`/`firestore`), bundled by Vite (no CDN compat scripts); there is no Firebase Hosting. `modules/persistence/` holds the client wrapper (`firebase-client.ts`, the typed seam) plus the submission/progress/review/rating repos and the offline `local-session-store`. ## Testing & Workflows

- **`npm run ci`** — required pre-merge gate: static checks + Vitest unit/integration + node validators (browser-free). **`npm run ci:full`** adds Playwright e2e. **`npm run test:visual`** is opt-in (environment-sensitive baselines). Tier map, filters, coverage, and e2e/visual detail: [`docs/testing.md`](docs/testing.md).
- **Solver hot-path change**, *when you go to report/merge it* (iterate on a small sample first — see docs/testing.md's "Iterating vs. gating") → `npm run solver:bench -- --check` (no regression vs `logs/solver-baseline.json`) **and** a before/after speed comparison (`nodesExpanded`/wall-time across the full corpus) — the former checks solvability only, the latter checks cost; a change needs both before it's reported as verified. Use **`npm run solver:speed-probe`** for the cost half. **Pass `--work-budget=<n>` with a generous `--budget-ms`**: the solver allocates in WORK units (`modules/solver/work-meter.ts`), so a pinned work budget makes a run bit-identical on any host under any load, and wall time then carries the entire speed signal. Never bound an A/B by wall clock — a faster solver simply does more inside the same window, so `nodesExpanded`/`elapsedMs` are not comparable across a speed change (`solver:bench --check`'s own cost line reports a large node *increase* precisely when the corpus got faster). Prefer `workSpent` over `nodesExpanded` for any cost comparison: it is host-independent, and it means the same amount of real work in dfs/beam/repair, which count 11-17x different work per "node". **The one carve-out: the work meter is a MODEL of cost, not a measurement of it — it charges each metered operation a fixed price (`CONNECTIVITY_WORK_UNITS` = 12 per `isConnected`, whatever that call actually floods), so it is blind to any change that alters what a metered operation COSTS rather than how often it runs.** `PRUNE_MC_RESERVED_WALL` shrinks the connectivity flood fill: `workSpent` reported **+11% work on a change that halved CPU** (89.4M vs 80.2M units for the same 20,000,000 nodes, at 36.0s vs 81.0s). For that class of change the right instrument is interleaved wall-clock at pinned `nodesExpanded`, not the meter — see [`reports/2026-07-31-reserved-intersection-wall.md`](reports/2026-07-31-reserved-intersection-wall.md). A genuine speed-only change must come out bit-identical on `nodesExpanded` under a pinned work budget — a check that catches order-changing bugs millions of differential comparisons can miss (see [`reports/2026-07-30-solver-hot-path-pure-speed.md`](reports/2026-07-30-solver-hot-path-pure-speed.md) and [`docs/solver-budget-determinism.md`](docs/solver-budget-determinism.md)). Compare medians of *interleaved* before/after runs; single runs vary ±5-10%. **A corpus-2 solved-count difference of ±5 is NOT distinguishable from noise**: two full typical-budget refreshes on solver code differing by nothing but a test file came back 506 vs 505 with 5 flipped levels (corpus-1 reproduced exactly). The cause is the refresh's own `--budget-ms`, which is the *binding* constraint on the slow tail rather than "non-binding by design" as its header used to claim — make the clock non-binding and repeat runs are bit-identical on nodes *and* work. For an A/B whose result matters, dispatch `solver-typical-budget-baseline.yml` with `deterministic: true` (or pass a large `--budget-ms` locally); see [`reports/2026-07-31-refresh-nondeterminism.md`](reports/2026-07-31-refresh-nondeterminism.md) and [`docs/solver-budget-determinism.md`](docs/solver-budget-determinism.md). A result flagged `deadlineTruncated` is indeterminate, not a negative — never record it as "unsolved". See the "Verify before you claim done" rule above and the Solver Architecture gotcha on this.
- **Adding a new level**: append to `data/levels.json` (1-indexed; give it the next unused `P`-prefixed id, e.g. `P00157`; hints, if any, go in `data/hints/<id>.json` — write them via `scripts/level-data-io.mjs`), run `npm run test:hint-path-oracle` (fails if any stored hint isn't PLAY-valid); debug with `npm run solver:direct -- --levels=<N> --verbose`.
- **Solver CLI, audit-JSON format, and debug/perf/archetype/trap recipes**: [`docs/solver-architecture.md`](docs/solver-architecture.md).

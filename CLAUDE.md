# Pathfinder Game — Developer Reference

## Project Overview

Pathfinder is a browser-based grid puzzle game. The player draws a continuous path on a rectangular grid from a starting **gate** to a **goal** cell. A solution is accepted only when all constraints hold simultaneously: exact path length, exact intersection count, and every object-specific obligation (must-pass, must-cross, portals, filters, landmarks, …).

`Solver.ts` generates the hint paths the in-game hint system serves. This file is the **current-state reference**: orientation, game rules, and the non-obvious rules/gotchas that prevent mistakes. Deep per-topic detail lives under [`docs/`](docs/README.md) (indexed in `docs/README.md`); the dated build history is in [`docs/history/development-journal.md`](docs/history/development-journal.md).

## Working in This Codebase

Rules earned by watching the same mistakes twice. The model is fast at producing *plausible* code and slow to notice that plausible ≠ correct, so the discipline lives in the process, not the generation.

- **Read before you write.** This repo is documented on purpose: the [`docs/`](docs/README.md) index + ADRs are the authoritative "why", and [`docs/architecture.md`](docs/architecture.md) says where new code goes. Read the doc *and* the files you're about to touch, then copy the pattern that's already there. Architecture invariants are machine-enforced (AST-based ESLint rules — see the Notes under Repository Layout); don't fight them, understand them.
- **Think, and state assumptions.** Many requests are underspecified ("add a constraint" is several different features). Name the interpretation you picked and the tradeoff. If a mechanic is genuinely ambiguous, ask — don't fill the gap with plausible code that passes a casual read and fails at the win-condition check.
- **Simplicity, minimal diff.** This codebase carries scars from past over-abstraction and haphazard growth. Write the smallest change the task allows; don't reformat untouched code; justify every changed line by the task. Abstract only after the third copy, never "in case we need it."
- **Verify before you claim done.** `npm run ci` must pass (static checks + Vitest + node validators). If you touched the solver's hot search path, `npm run solver:bench -- --check` must show **no regression vs the baseline** — the single hardest level can fail under sandbox CPU-throttling, which is *not* a code regression (confirm by re-running the pre-change code). **`solver:bench --check` only verifies the solved/failed set — it is silent on cost.** A change can pass it cleanly while making the corpus meaningfully slower (more nodes/wall-time per level, same outcome); always also compare `nodesExpanded`/total time before vs. after on the full corpus (a plain before/after `Solver.solve` sweep, ablation-gated if the change has an ablation flag, is enough — no dedicated tool exists yet). See the Solver Architecture gotcha below for the concrete case that caught this. Fixing a bug? Write the failing test first, watch it fail, then fix. Test behavior that can break, not that a constructor sets a field.
- **Debugging: investigate, don't guess.** Read the whole error, reproduce before changing anything, change one thing at a time. Don't silence an unexpected `null`/`undefined` with a guard — find *why* it's there or the bug just moves somewhere quieter.
- **Dependencies and platform constraints are load-bearing.** Every runtime dependency must be **bundled by Vite** (no new CDN `<script>`s) and survive `check:csp` + `check:third-party`. Prefer the stdlib or an existing utility over a new package; when you must add one, say why.
- **Solver strategy is keyed on level *features*, never level *identity*.** `check:no-solver-level-numbers` enforces this over the solver source and its docs — cite the feature regime ("navDensity ≥ 0.82", "≥3 must-pass"), not a level number, in code and comments.
- **New canvas-drawn visuals must be themed.** `check:canvas-theme-coverage` scans `modules/render/*.ts` and fails on any hex color literal that isn't sourced from `theme.colors.*` (see `theme-engine.ts`'s `deriveTokens` + `theme-normalizer.ts` for the fallback pattern) — a hardcoded color is invisible to every other check (not a CSS class, not banned syntax), which is exactly how the landmark objects and turn/satisfied badges shipped fully unthemed before this existed. A literal that must stay fixed regardless of theme (a universal hazard icon like the goose or the false-goal's bomb icon, an object's material cue like a fountain's water highlight, the intentional multi-color "rainbow" path style) needs a `// theme-exempt: <reason>` comment on the same line — the reason is the justification, not a rubber stamp.
- **Communicate precisely, especially uncertainty.** Say what you did and why, flag concerns even when you did exactly what was asked, and report what you did *not* run (e.g. the Playwright e2e/visual suites are not part of `ci`). "I'm not sure this path is CSP-clean" tells the reader what to check; "should be fine" does not.

## Pathfinder Game Rules

### Core Path Mechanics
- Path starts on a **gate** and ends on the **goal** (true goal, not a false goal).
- **Counted length** = number of nodes − 1 − portal jumps. Portals teleport for free.
- **Intersection** = entering a previously visited cell (excluding gate and goal revisits).
- The path must hit **exact** length (`reqLen`) and **exact** intersection count (`reqInt`).
- Moving diagonally or more than 1 step at a time is not permitted.

### Grid Objects
| Object | Behavior |
|---|---|
| **Gate** | Path start. Multiple gates possible (player picks one). Cannot be re-entered once left. |
| **Goal** | Path end (true win condition). Only one true goal per level. |
| **False goal** | Looks like a goal. Entering it triggers a trap (hazard) — path fails. Solver ignores false goals (MoveContext.SOLVER). |
| **Block** | Impassable. BFS distances and neighbors precomputed excluding blocks. |
| **Must-pass** | Cell that the path must visit at least once. Tracked via `mustMask` / `mpVisitedMask`. |
| **Must-cross** | Cell the path must enter from two opposite sides (i.e., cross through it at least twice). Uses `mustCrossMask` + `crossCounts`. |
| **Filter (regular)** | Forces entry along a fixed axis (axis=1 H, axis=2 V). Statically filtered out of `staticNeighbors` for wrong-axis neighbors. |
| **Flipping filter** | Starts with its declared axis; flips to the other axis each time the path uses it (based on `flipperUsedMask` count parity). Cannot turn on it. Fully dynamic — can't be precomputed. |
| **Portal** | Pair of cells. Entering a portal forces an immediate jump to the paired exit at zero path-length cost. Portals cannot be reused. When standing on a portal cell and the last move was NOT a portal jump, `getNeighbors()` returns only the portal destination — bypassing static adjacency entirely. |
| **Goose** | Hazard. Entering a goose cell in PLAY mode fails the path. The solver ignores geese (MoveContext.SOLVER). |
| **Surround landmark** | Impassable. Path must visit all reachable 8-adjacent cells before finishing. Tracked via `surroundMask` + `surroundNeighborRemainingMasks`. |
| **Must-turn landmark** | Passable. Path must make a turn (of required direction: `either`/`cw`/`ccw`, relative to the level's default unrotated/unmirrored orientation) at this cell. Tracked via `mustTurnMask`. |
| **Adjacent-turn landmark** | Impassable. Path must make a required turn at one of its 8-adjacent passable cells. Tracked via `adjTurnMask`. |
| **Decorative landmark** | Impassable. No path constraint — visual only. |

**Cell occupancy is an absolute invariant: every cell holds at most one object.** A portal's `dest` is always another portal terminal, never any other object type — entering a portal moves the line to the paired terminal cell *only*; it never additionally spits the line onto some other cell/object in the same step. This is not a soft convention: it's enforced by `validateRawLevel` (`domain/level-schema.ts`) — the hard schema gate every level passes through regardless of authoring path (editor export, hand-written JSON, stress-test generation, Firestore import) — and mirrored by `validateLevelDetailed` (`domain/level-validation.ts`, the editor/stress-generator heuristic layer) and the editor's own one-object-per-cell placement guard (`getOccupant`/`placeOccupant` in `editor-occupancy.ts`). **History**: a stress-corpus generator bug (`scripts/stress/witness.mjs`'s `chooseEnd`) once let a generated level's goal cell silently coincide with a portal's destination, because the witness-path referee only validates move legality along the path, not whether the level's object placements are individually well-formed — the schema layer had no general cross-object-overlap check to catch it either. Both gaps are now closed (see `validateRawLevel`'s cross-object occupancy check and `chooseEnd`'s `terminals.has(path[i])` guard), but the lesson generalizes: **don't infer this invariant might be soft from move-generation code that defensively checks a portal destination against block/goose/false-goal status** (`search-state.ts`'s `getNeighbors`, `move-rules.ts`, `step-processor.ts`, `path-state.ts` all do this) — those checks are intentional defense-in-depth against exactly this kind of validation gap, not evidence the interaction is expected to occur in valid data. Keep them; don't read them as a sign the invariant is only conventional. **Second history entry (2026-07-15)**: `validateRawLevel`'s occupancy check itself had a real gap in the opposite direction — a false positive, not a missed negative. `denormalizeLevel`'s wire output (`buildWireLevelData`, the real editor/submission export path) legitimately re-declares an impassable landmark's cell in `blocks` (and a mustPass/mustTurn landmark's cell in `mustPass`) alongside its own `landmarks` entry — a landmark and its own derived block/mustPass are the same conceptual object, not two objects contending for one cell, the same reasoning `domain/level-fingerprint.ts`'s `landmarkDerivedCoordSets` already applied when excluding those exact coordinates from its own comparison buckets. `validateLevelDetailed` (the normalized-layer heuristic validator) already had this exception; `validateRawLevel` didn't, so any level with a landmark that went through the real export path could never pass the raw-layer check — undetected until a real player submitted one through the in-game editor and `levels:import-published` tried to pull it in, because every landmark level in the corpus before that was hand-authored JSON that never introduced the redundant entry in the first place. Fixed by excluding landmark-derived coordinates from the block/mustPass occupancy claims (mirroring `landmarkDerivedCoordSets`'s categorization exactly, via the shared `baseLandmarkRole` helper) — a block/mustPass at a landmark cell with a *mismatched* role is still correctly rejected as a genuine conflict.

### Win Condition
All of the following must be true simultaneously when the path reaches the goal:
1. Counted length = `reqLen`
2. Intersection count = `reqInt`
3. All must-pass cells visited (`mustMask === 0` or `mpVisitedMask === initialMpMask`)
4. All must-cross constraints satisfied (`mustCrossMask === 0`)
5. All surround neighbor cells visited (`surroundMask === 0`)
6. All must-turn cells turned in required direction (`mustTurnMask === 0`)
7. All adj-turn constraints satisfied (`adjTurnMask === 0`)

### Landmark Wire Format
Landmarks are declared in the raw level JSON as a `landmarks` array; each entry has `x`, `y`, `objectType` (visual asset name), and `role` (`turn` optional for the non-suffixed turn roles):

```js
landmarks: [
  { x: 5, y: 5, objectType: 'park',     role: 'surround' },
  { x: 3, y: 3, objectType: 'library',  role: 'mustTurn',     turn: 'either' },
  { x: 2, y: 7, objectType: 'library',  role: 'mustTurnCcw' },
  { x: 7, y: 2, objectType: 'fountain', role: 'adjacentTurn', turn: 'cw' },
  { x: 9, y: 4, objectType: 'statue',   role: 'decorative' },
]
```

- **Passable** (path may enter): `mustPass`, `mustTurn`, `mustTurnCw`, `mustTurnCcw`.
- **Impassable** (added to `blockSet`): `surround`, `adjacentTurn`, `adjacentTurnCw`, `adjacentTurnCcw`, `decorative`.

`parseRawLevel` normalizes these into `surroundKeys`/`adjacentTurnKeys`/`adjacentTurnDirs` (parallel arrays), `mustPassTurnDirs: Map<key, TurnDir>`, and `landmarkMeta: Map<key, {objectType, role}>`. The coordinate-bearing field set has a single source of truth — `LEVEL_KEY_FIELDS` in `domain/level-codec.ts` (drives `remapLevelKeys`/`forEachLevelKey`), so shifts/resizes/bounds can't silently drop a field. The reverse direction has one too: **`buildWireLevelData()`** (same file) is the only normalized→raw serializer — used by editor export, submission, and review publish — so persisted levels always carry `landmarks` (a hand-rolled submission serializer formerly flattened them to plain `blocks`/`mustPass`, silently downgrading the mechanics on review). Duplicate detection (`domain/level-fingerprint.ts`, fingerprint **v2**) canonicalizes by landmark *mechanics*: landmark-derived coords are excluded from the generic buckets, so equivalent wire shapes fingerprint identically while a plain block ≠ a landmark at the same cell. Design record: [`docs/archive/landmark-submission-serialization-plan.md`](docs/archive/landmark-submission-serialization-plan.md).

**Fingerprint-version-bump gotcha**: the fingerprint doubles as the Firestore document key for Dev-Mode level ratings, and also feeds `scripts/import-published-levels.mjs`'s duplicate detection. Bumping `LEVEL_FINGERPRINT_VERSION` (last done v1→v2, 2026-07-03) therefore has ripple effects beyond the fingerprint module itself: it silently orphans every previously-saved rating unless the reader falls back to a frozen legacy fingerprint, and any script with its own structural-comparison logic (instead of importing `getLevelFingerprintSource`) will silently diverge. `level-rating-manager.ts` handles this via `getLegacyLevelFingerprints` (fall back to the old fingerprint on a miss, migrate forward on read) — treat this as the required pattern for any *future* version bump, not a one-off fix.

`TurnDir` (`'either' | 'cw' | 'ccw'`) is always relative to the level's default (unrotated, unmirrored) orientation — never to the path's travel direction or the currently displayed variant. Two independent transforms touch it, and must treat rotations and reflections differently because a reflection reverses chirality while a rotation preserves it: (1) the **editor's Rotate/Mirror buttons** (`input/editor-toolbar-controller.ts`) permanently rewrite the canonical level's coordinates via `levelUtils.applyCoordMapToLevel` → `remapLevelKeys` (`domain/level-codec.ts`) — Mirror passes `reflect: true`, which flips `mustPassTurnDirs`/`adjacentTurnDirs` values via `flipTurnDir` (`domain/landmark-rules.ts`); Rotate passes no reflect flag, correctly leaving them unchanged. (2) **Play-mode's random-per-load / "Whoa"-button display variant** (`engine/level-flow.ts`, `domain/geometry.ts`'s 8-way `transformPoint`/`transformAxis`) never touches the canonical level — only screen position and click-input are remapped — so the render layer applies `transformTurnDir(dir, variant)` (`domain/geometry.ts`) when drawing the mustTurn/adjacentTurn visual cue, flipping cw↔ccw for the 4 reflecting variants (4–7) so the on-screen arrow matches what's actually required in the displayed orientation.

## Solver Architecture

`modules/Solver.ts` is a thin facade over `modules/solver/*`. Strategy is selected by **level features, never identity** (see the Working rules). The full reference — core flow, archetypes, the declarative `ATTEMPT_POLICY`, DFS/beam mechanics, pruning, `prepLevel` data, plus CLI usage, the audit-JSON format, and debug/perf recipes — is **[`docs/solver-architecture.md`](docs/solver-architecture.md)**.

**Solution-space fingerprints** (`scripts/stress/solution-profile.mjs`/`solution-profile-lib.mjs`/`solution-profile-compare.mjs`, [`docs/solution-profile.md`](docs/solution-profile.md)): analysis tooling — not a production feature — that turns each known-solvable level's *accepted hint corpus* into an aggregate behavioral fingerprint (cell/edge/turn/portal/must-cross distributions, pairwise distinctiveness, discovery-saturation), so an as-yet-unsolved stress-corpus-2 level can be compared against known-solvable families via `npm run stress:solution-profile-compare -- --target-level=<n>` when the production solver fails on it. Distinct from `domain/level-fingerprint.ts` (shape/dedup hash) and `scripts/solver-fingerprint.mjs` (determinism hash) — this one hashes nothing about the level itself, only how its *solutions* behave. The committed libraries (`reports/stress/solution-profile-{published,corpus1}.json`) are **kept fresh automatically**: `solution-profile-compare.mjs` checks each library's stored hint-signature against the live corpus before every comparison and transparently regenerates it in place if stale (see the doc's Freshness section) — there is no separate "remember to rebuild this" step, and no need to hook regeneration into hint-discovery tooling.

**AI-assisted manual solving** ([`docs/ai-assisted-manual-solving.md`](docs/ai-assisted-manual-solving.md)): proposed methodology (one worked demonstration, not yet validated on a genuinely unsolved level) for whether an AI agent reasoning by hand about a level — no solver, no stored hints — can surface new solver heuristics. Verdict: mostly no, since the puzzle's "cleverness" is a property of its combinatorics, not of who's reasoning about it, so an AI's self-described strategy mostly reconstructs techniques the solver's scoring/attempt-policy code already encodes. The one recommended real use is **differential diagnosis**: hand-solve a level the solver currently fails on, then diff the accepted path against the solver's own search trace at each divergence point — the same instrumented-ablation model that found the real R02248/R01465 fixes, not narrative-mining. Includes the exact protocol for verifying (`validateCandidatePath`) and recording (`solver.id`, never reusing `SOLVER_ID`/`HUMAN_PLAYER_ID`; `getLevelFingerprint` not `getLevelFingerprintSource` for `levelRevision`) a manually-found hint's provenance correctly.

**Fast portfolio scheduler experiment** (`schedulerMode: 'portfolio-experiment'` in `modules/solver/orchestration.ts`'s `solveLevel`, config in `data/config/portfolio-experiment.js`, [`docs/fast-portfolio-scheduler-plan.md`](docs/fast-portfolio-scheduler-plan.md)): opt-in, **not the production default** — every live app code path (Play/Editor/Review/hint discovery) uses `schedulerMode: 'legacy'`; `portfolio-experiment` is set only by offline CLI tooling (`scripts/portfolio-scheduler-report.mjs`, `scripts/portfolio-solve-sweep.mjs`). Tests the hypothesis that a broad, cheap, timed-tier pass across every gate recovers most solves before the legacy ladder spends a large budget on any one attempt config, falling back to a full legacy solve if the portfolio tiers don't find one (so it can never solve *fewer* levels, only find the same solve slower or faster). **Current verdict (`reports/portfolio/portfolio-scheduler-decision.md`): not production-ready** — every measured variant is slower than legacy on the published corpus even where it retains full solvability. **Re-verified 2026-07-16 against the post-elite-splice-fix solver** (`reports/2026-07-16-portfolio-scheduler-reverification.md`): the decision doc's best stress-corpus number (0.57x, portfolio faster) was itself measured while the elite-splice regression was crippling legacy's repair search on the same repair-heavy levels; re-run today it's 1.45x (portfolio slower), confirming "not production-ready" more strongly, not less — a legacy-side speed change can silently invalidate a previously-recorded portfolio verdict with zero portfolio-side code change. See `docs/solver-architecture.md`'s "Fast portfolio scheduler experiment" section for the CLI usage and current-state summary.

**Batch-testing a solver change against the unsolved corpora** (recurring need, not a one-off): start from `docs/solver-architecture.md`'s "Which tool for a corpus/large-batch solve" table — it's the tool-selection index for every batch/CLI entrypoint (`stress:benchmark` variants, `solver:direct`, `scripts/portfolio-solve-sweep.mjs`, `scripts/repair-direct-probe.mjs`), not just the portfolio-scheduler-specific ones. `portfolio-solve-sweep.mjs` in particular exists for *repeated* iteration (not single runs): `--resume` checkpointing, `--attempt-cache` (skip a level your change provably can't affect, via a hash of the actual solver source files each attempt family depends on), `--priority`/`--baseline` (closest-to-solved first), and composed `--workers`/`--race-pool-size` parallelism (cross-level and within-level together — deliberately different from `stress:benchmark`'s mutually-exclusive `--parallel`/`--engine=raced`). None of this substitutes for `solver:bench --check`'s regression-safety requirement above — it's the complementary "iterate fast" half of the same workflow, not the "did I break anything" half. **A full corpus-2 refresh can also be parallelized across GitHub Actions** instead of tying up a local session for hours — `.github/workflows/solver-corpus2-batch-*.yml` (`workflow_dispatch`-only, one-off/on-demand infrastructure; see that directory's `README-solver-corpus2-batches.md`) splits the 1700 levels into 20 batches of `portfolio-solve-sweep.mjs --scheduler-mode=legacy --save-hints`, each producing badness/attempts/refereeValid telemetry (not just solved/failed) via the same enrichment covered above, combinable afterward via `npm run solver:combine-corpus2-batches`. First full run, 2026-07-16 (post elite-splice-fix): 236/1700 solved (~12.5 min/batch average), up from 152/1700 at the pre-fix 2026-07-12 baseline. **Second full run, 2026-07-17, INVALID — ran stale pre-fix code the whole time, discovered and fixed the same day.** Re-triggered after two repair-probe budget fixes + `node_budget` 8M→20M (PR #1237), ran 15-26 real min/batch and reported 286/1700 — but every batch branch from the *first* run still existed, and the workflow's checkout logic prefers an existing branch's own history over forking fresh from `main`, so this run silently executed each branch's stale 2026-07-16 solver code, never touching either repair-probe fix. **The archive-then-rerun pattern used to prep for this run (rename the old checkpoint files out of the way on both `main` and each batch branch, then let the branch write fresh ones at the original path) is necessary but not sufficient**: it clears checkpoint *data* but not *source code* — a branch left checked out at its own old commit still runs old code with new bookkeeping. Confirmed directly: a supposedly-fresh level's result was byte-identical to its pre-refresh archived entry, and `git merge-base --is-ancestor <fix-commit> <batch-branch>` returned false across every branch sampled. See [`reports/2026-07-17-corpus2-refresh-ran-stale-code-correction.md`](reports/2026-07-17-corpus2-refresh-ran-stale-code-correction.md) for the full diagnosis — **treat 286/1700 as never having existed, not as a stale-but-once-valid number.**

**Third full run, 2026-07-17 — genuine.** Fixed by force-resetting all 20 batch branches to `main`'s tip (bringing the real fixes onto them; these are disposable automation branches by design) with a fresh checkpoint-archive commit on each, then re-triggering. Verified the fix actually took effect *before* trusting the result: the canary level (`R01698`) flipped from `attemptCount: 3`/`nodesExpanded: ~10,000,000` (probe only) to `attemptCount: 7`/`nodesExpanded: 20,000,009` (genuinely exhausting the full budget across probe + main-loop + repair-fallback). Result: **295/1700 solved** — up from the last trustworthy 236/1700 baseline (not "9 more than 286," since 286 was measuring the wrong code entirely and has no evidentiary standing). Combining hit the same archive-vs-rename merge-conflict pattern the invalid run did (see below), plus **a second, distinct gotcha**: an initial merge attempt reused locally-cached branch refs fetched earlier in the session for several batches, silently merging their *own prior* stale content instead of the genuine commits the workflow runs had just pushed — caught by spot-checking a freshly-`git fetch`ed branch's HEAD commit message against the expected refresh timeframe, not by any automated check. **Lesson: always `git fetch` every batch branch explicitly, immediately before merging — never reuse refs fetched earlier in the same session**, even within the same investigation. `logs/stress-corpus2-baseline.json`/`reports/stress/dev-benchmark-corpus2.json` both regenerated from this genuine run.

**The underlying git-rename-detection gotcha** (relevant to both the invalid and genuine combines): the archive-then-rerun pattern confuses `git merge`'s rename detection — it pairs both sides' renames of the *same original file* as a rename/rename match, and when a branch's later commit re-populates the original path with genuinely new content, that content is misrouted into the rename-conflict resolution (or silently dropped if resolved naively via `checkout --ours`) instead of landing at the live path. Resolve by re-pulling each batch's live `batch-NN.*` files directly from the branch tip (`git show origin/<branch>:<path>`) after merging, never trusting the merge's automatic resolution for a path that was renamed on one side and modified-in-place on the other.

### Common gotchas
- **Portal forced-move**: at a portal cell when the last move was not a portal jump, `getNeighbors()` returns only `[portal.dest]`, bypassing static adjacency — portal entry forces the exit.
- **Gate cells cannot be re-entered**: excluded from `staticNeighbors` targets; `isValidMove` also guards this.
- **Must-cross lock**: turning at a 1st-pass must-cross cell consumes both H and V axis bits, blocking the required 2nd crossing. Dynamic check in `_isMoveDynValid`.
- **Flipping filters** are fully dynamic — current axis depends on `flipperUsedMask` parity, so they can't be precomputed into `staticNeighbors`.
- **Dense levels** (`navDensity ≥ DENSE_LEVEL_NAV_DENSITY`, named in `solver/prep.ts`): `mustMaskForDFS` is 0, not `initialMustMask`, to avoid disrupting near-Hamiltonian DFS ordering; must-pass correctness is enforced via `mpVisitedMask` instead.
- **Editor validator is a heuristic, not a solver**: `validateLevelDetailed()` inspects only nearby cells and can both false-positive and false-negative on real solvability — confirm with the solver when it matters (the function's own docstring says so).
- **Memoizing a lower bound (or any search-dependent value) is only sound if the cache key captures every state variable the value actually depends on — an under-keyed cache silently returns a WRONG bound, which can wrongly prune a reachable solution (a correctness bug, not just a missed optimization).** `mustPassLowerBound` is safely memoized on `(pos, mpVisitedMask)` alone because a must-pass cell only ever needs one visit, so that pair fully determines the bound. `mustCrossLowerBound` is **not** safely memoized the same way: a must-cross cell needing its 2nd visit has a bound that also depends on `crossCounts[i]` and *which axis* the 1st visit used (`edgeUsage`) — two states can share the same `(pos, mustCrossMask)` yet need different bounds. Its actual cache key (`lower-bounds.ts`) encodes a base-4 digit per must-cross index for exactly this reason; don't simplify it back to `(pos, mask)` without re-deriving why that's unsound. **This already caused a real bug** (undersized MST scratch buffer → silent TypedArray truncation → a bound computed from stale data came out tighter than mathematically valid, risking a false "unsolvable"); see [`docs/solver-architecture.md`](docs/solver-architecture.md#history-the-mst-bound-scratch-buffer-bug) for the full writeup. Any new memoization on solver state must ship with the same differential-testing rigor that fix did, not just "tests still pass."
- **`solver:bench --check`'s "no regressions" only means the solved/failed set is unchanged — it says nothing about cost.** A change that adds retries or extra attempt configs can pass it cleanly while making the corpus slower for the same outcome. **This happened**: an early version of the repair-probe multi-seed retry (`REPAIR_PROBE_ORDINARY_SEED_SALTS`, `orchestration.ts`, gated on the same repair-fallback feature regime as `needsRepairFallback` — mustCross ≥ `POLICY.REPAIR_MC_MIN`, mustPass ≥ `POLICY.REPAIR_MP_MIN`) passed `solver:bench --check` at 160/160 with zero regressions, but a direct before/after speed sweep of the full published corpus showed the run got ~14% slower overall (42.0s → 47.7s at `budgetMs=30000`) — almost entirely from one repair-gated level whose probe now burned every one of 4 extra retry seeds (full node budget each, ~2M nodes/seed) before falling through to the same fallback path that solved it before this feature existed, with zero net benefit on that level. The seeds that *do* rescue a level are not reliably cheap either — direct measurement across a calibration family (a parent plus 3 rotated siblings) found rescuing seeds costing anywhere from ~21% of the per-seed node budget up to ~94% of it, so a smaller per-retry node budget isn't a free way out: it would have missed most of the calibration set's own known rescues. The width was narrowed (fewer retry seeds) once this was measured, bringing the same full-corpus sweep back to roughly a wash (~0.5%) while keeping the one known rescue — see `orchestration.ts`'s own comment on the constant for the current numbers. Any future retry/multi-attempt widening needs a full-corpus before/after timing comparison, not just a solvability check — see the `docs/testing.md` "Speed, separately from solvability" note and CLAUDE.md's "Verify before you claim done" rule above.
- **A correctness fix in a shared code path can silently orphan a caller-specific mechanism that depended on the exact condition it removed — check for that, not just for slower search.** The July 10 consolidation of `dfsFromGate`'s and repair-search's pruning gauntlets into `evaluatePrunedMove()` (`prune-gauntlet.ts`) correctly closed a real bug: repair-search's random walk used to treat a non-winning goal-cell entry as an ordinary passable neighbor (could be selected and walked past), which `dfsFromGate` already forbade and which the real game rule forbids too (touching goal always ends the path — `domain/move-rules.ts`). But that was also the *only* way `repairSearchFromGate`'s `'goalInvalid'` outcome could ever fire, and `'goalInvalid'` was the sole trigger for its near-miss bookkeeping (`computeBadness`, the elite-pool splice candidates, `bestBadnessEver`) — so the fix silently made that whole outcome, and therefore the whole elite-splice mechanism `ELITE_POOL_SIZE`/`SPLICE_PROBABILITY` exist to drive, permanently dead (confirmed both by a code-path proof and empirically: `bestBadness` reported `Infinity` on every failed probe, never a real number). Every restart fresh-started from the gate with zero memory of prior near-misses from that point on — a large, uncredited share of the same July 10 regression `solver:bench --check` couldn't see (see the gotcha above). Fixed by generalizing the bookkeeping to the `'deadend'` outcome as well — the legal way the same "walk stalled without solving" event surfaces now — restoring the mechanism without reintroducing the illegal goal pass-through. Full investigation and verification numbers (full-corpus ~20% recovered, one stress-corpus subset 88.7s→7.9s with two outright solve failures fixed): [`reports/2026-07-16-repair-search-elite-splice-regression.md`](reports/2026-07-16-repair-search-elite-splice-regression.md). **Lesson**: when a refactor's own diff shows "reject a case that used to fall through to X," grep every place X's outcome was the trigger for something else — a consolidation can be behaviorally correct at the call site and still break a second-order dependency on the exact case it removed. The report's own "what remains to investigate" question (were `ELITE_POOL_SIZE`/`SPLICE_PROBABILITY`/the repair-probe node budgets miscalibrated against the broken mechanism?) has since been re-verified and closed as a negative result — see [`reports/2026-07-16-elite-splice-constant-reverification.md`](reports/2026-07-16-elite-splice-constant-reverification.md): 6 of 7 calibration-family levels now solve on the first seed using well under 13% of the ordinary probe's node budget, and the one that needs a retry (P00145) still needs ~40% of it for the rescue — the "headroom" in the easy majority doesn't mean the budget is oversized, it means the budget is correctly sized for the hard minority, exactly the same trap the seed-*width* constant's own calibration history already warns about. No constant changed.
- **A scoring term tuned for the common case can become actively self-defeating on a rare, dense one — and whether it does can depend on grid orientation alone.** `scoring.ts`'s `SCORE_INTERSECTION_SETUP` rewards revisiting a cell when the path still needs more self-intersections (`reqInt`) — a reasonable, generally necessary counterweight to the default revisit-aversion. On R02248 (stress-corpus-2, navDensity 0.886, near-Hamiltonian: `reqLen` covers ~88% of all open cells, `reqInt: 7`), this term combines with orientation-dependent early search trajectories (shaped by other position-dependent terms like goal-attraction/perimeter-bias) to lock in an early self-crossing the level's near-zero slack can't recover from — in exactly 4 of its 8 symmetry orientations (the ones whose rotation component is 180°/270°, independent of any reflection — a clean dihedral-group split, not a fuzzy correlation). Confirmed causal, not just correlated: disabling `SCORE_INTERSECTION_SETUP` alone (verified via direct ablation sweep) unlocks an immediate, valid beam solve in all 4 previously-stuck orientations. Full trace (attempt ladder, ablation sweep, mechanism): [`reports/2026-07-16-r02248-orientation-scoring-interaction.md`](reports/2026-07-16-r02248-orientation-scoring-interaction.md). **Not a one-off**: a targeted scan for the same profile (near-Hamiltonian + nontrivial `reqInt` + surround landmarks, no must-cross/pass/portal/filter confounds) found exactly one clean second match, R01465, which reproduces R02248's *exact* diagnostic signature (beam frontiers collapsing to single-digit node counts — genuine exhaustion, not timeout — plus repair's `bestBadness` plateauing across seeds) in 6 of its own 8 orientations. But its unlock is **`SCORE_SURROUND_URGENCY`, not `SCORE_INTERSECTION_SETUP`** — disabling the latter does nothing for R01465. Read together: this is a recurring failure mode drawn from a small family of related terms (`SCORE_INTERSECTION_SETUP`, `SCORE_SURROUND_URGENCY`, and to a lesser extent `SCORE_PHASE_SCALING`/`SCORE_REVISIT_PENALTY`, per both reports' ablation sweeps), not one universally-broken term — which term dominates is level-specific. Full scan methodology and results: [`reports/2026-07-16-r02248-pattern-scan.md`](reports/2026-07-16-r02248-pattern-scan.md). Every flag involved is very likely load-bearing elsewhere, so no global scoring change was made; any future change here needs the same corpus-wide solvability+speed verification as any other hot-path change (see the gotcha above). **A bounded, opt-out last-resort mechanism was implemented instead of a scoring change** (same day, after further diagnosis on 3 more levels found 4 distinct culprit terms with no shared fix — [`reports/2026-07-16-phase-d-fragile-group-ablation-diagnosis.md`](reports/2026-07-16-phase-d-fragile-group-ablation-diagnosis.md)): `solveLevel()` now reruns the main attempt ladder once more, with `SCORE_GOAL_ATTRACTION` disabled, in its own small additive budget, but ONLY after the main loop AND repair fallback have both already failed — zero cost to any level that already solves (verified: published corpus 160/160, no regressions). Verified rescuing exactly the variants the diagnosis predicted it should (4/4) and correctly failing on the 2/2 it predicted it shouldn't. See [`docs/solver-architecture.md`](docs/solver-architecture.md#attraction-diversity-last-resort-pass-2026-07-16) and [`reports/2026-07-16-phase-d-attraction-diversity-implementation.md`](reports/2026-07-16-phase-d-attraction-diversity-implementation.md) for the full implementation, two real bugs caught along the way, and scope/follow-ups. **A sixth confirmed case, R00648, found 2026-07-17 via level reduction (`stress:reduce-level`) rather than the pattern-scan methodology** — independent corroboration this is a recurring family, not a small closed set: the *original* level (portal-heavy, `reqLen` 141) is unlocked by `SCORE_GOAL_ATTRACTION` alone (matching a rescue already credited to the attraction-diversity pass); its *reduced* form (level-reducer stripped all 7 portals and shrank `reqLen` to 133, landing on a completely empty 15×15 grid — zero mechanics at all, purest possible reproduction of this pattern) is instead unlocked by `SCORE_INTERSECTION_SETUP` **or** `SCORE_PERIMETER_BIAS` — `SCORE_GOAL_ATTRACTION` does nothing for the reduced form. **New methodological caveat this surfaced**: `stress:reduce-level`'s contract (preserve the failure *signature* — `timeout` stays `timeout`) does not guarantee it preserves the failure's *root cause* for this fragile-scoring class — a minimized reproduction can end up needing a different rescuing flag than the original even though the surface signature label is identical. Anyone using level reduction to investigate a flagged fragile-scoring level should re-run the ablation sweep on the *reduced* candidate, not assume it inherited the original's culprit. See [`reports/2026-07-17-r00648-fragile-scoring-family-and-reduction-caveat.md`](reports/2026-07-17-r00648-fragile-scoring-family-and-reduction-caveat.md). **A per-flag census across a 100-level `dfs-plain` sample, same day**: combining Task 3's single-flag/widened-flag sweeps (`reports/2026-07-17-attraction-diversity-fraction-and-flag-widening-evaluation.md`) with correctly-isolated individual-flag attribution finds **7/100 (7%) confirmed fragile-scoring cases** — `SCORE_GOAL_ATTRACTION` rescues 5 of the 7 (R00648, R01903, R03025, R03250, R02959), `SCORE_INTERSECTION_SETUP` rescues 2 (R02480, R02959), `SCORE_OBJECTIVE_ATTRACTION` rescues 2 (R02921, R02959 — one, R02921, dramatically: 81 nodes vs. ~20M for every other config). R02959 alone has 3 independent redundant rescue paths. This corroborates `SCORE_GOAL_ATTRACTION` as a reasonable sole production candidate (it's the majority rescuer) while showing real value left on the table: `SCORE_INTERSECTION_SETUP`/`SCORE_OBJECTIVE_ATTRACTION` each uniquely rescue a level the current candidate set never touches. Strengthens (with real attribution data, not just speculation) the case for a **sequential per-flag sub-pass** design over the combined-single-pass shape Task 3 measured (which only reached 5/7, losing the 2 `SCORE_GOAL_ATTRACTION`-only cases when disabling all flags together) — cost (~5x this pass's budget) still unmeasured, so no change made. See [`reports/2026-07-17-dfs-plain-fragile-scoring-census.md`](reports/2026-07-17-dfs-plain-fragile-scoring-census.md).
- **A timed-out beam attempt's `nodesExpanded` is always exactly 0 — this is a 100% structural instrumentation gap, not a search-quality signal.** `search.ts`'s `beamSearchFromGate` only increments `prep._metrics.nodesExpanded` on finding the goal or on the frontier naturally emptying (`timedOut: false`) — never on any of its three timeout exit paths (per-phase budget check, mid-phase 256-node check, `maxPhases` limit). Verified corpus-wide (2026-07-16, corpus-2 refresh): 1681/1681 timed-out beam attempts show `nodesExpanded === 0`, 951/951 non-timed-out ones show `> 0` — zero exceptions. Confirmed not a CPU-contention artifact from the source run's `--workers=2`: reproduces identically on a clean local single-threaded re-solve, while the *same level's* plain-DFS attempts (no `beamWidth`) show hundreds of thousands of real nodes — the search is doing real work, the counter just never gets credited before a short time slice runs out mid-phase. **Do not use a timed-out beam attempt's `nodesExpanded` as a "how much did it search" proxy for anything** (a corpus-wide clustering attempt built on exactly this assumption produced a meaningless 285-level "beam-collapse" bucket that was actually just "had a beam attempt that timed out"). R02248/R01465's own diagnosis (the gotcha above) is unaffected since it used the unconditional `_BEAM_DEBUG` introspection counters, not this field. **Fixed same day**: `beamSearchFromGate` now credits `frontierIndex` on all three timeout exit paths, not only at full-phase completion — verified as pure telemetry (`solver:bench --check` 160/160 no regressions; the one behavioral risk surface, `adaptiveGateWeight`'s use of `nodesExpanded` for cross-gate budget allocation, only engages at ≥4 active gates, which only 2 non-published stress-corpus-1 levels have, and both solve in <1s post-fix, nowhere near where that mechanism would ever engage). New regression test in `modules/solver/search.test.ts`. Full writeup + fix details: [`reports/2026-07-16-beam-nodesexpanded-instrumentation-gap.md`](reports/2026-07-16-beam-nodesexpanded-instrumentation-gap.md). **A DFS analog of the same bug was found and fixed the same day, in a follow-up audit prompted by this one**: `dfsFromGate`'s own timeout exit path (the `(++nodesExpanded & 255) === 0` budget check) had the identical gap — set `out.nodesExpanded` but never incremented `prep._metrics.nodesExpanded`. This one is arguably more consequential: `dfsFromGateLDS`'s probe waves (k=0,1,2,4,8) are specifically designed to often hit their own bounded node/time budget — that's the whole point of cheap-then-escalating LDS probing — so a large fraction of real DFS attempts' `nodesExpanded` were silently zeroed, not an edge case. The "same level's plain-DFS attempts show hundreds of thousands of real nodes" evidence cited above for ruling out a DFS-side bug turned out to only ever have sampled *exhausted/solved* DFS attempts, never *timed-out* ones specifically — a timed-out DFS attempt is a different code path with its own separate (and, it turned out, separately broken) crediting logic; general "DFS looks fine in aggregate" evidence doesn't cover a bug that's conditional on the specific exit reason. Confirmed via direct before/after comparison on the same level/budget shape used for the beam fix (`STRATEGY_LDS: false` bypasses the probe-wave ladder down to one plain `dfsFromGate` call, avoiding the wave-mixing noise a raw LDS run would add): every `timedOut: true` trial reported exactly `nodesExpanded: 0` pre-fix, real nonzero counts post-fix — same 100%-correlated pattern as the beam case. Fixed by crediting `prep._metrics.nodesExpanded` before the `return null` in that one branch (`search.ts`). Verified the same way: `solver:bench --check` 160/160 no regressions, `adaptiveGateWeight`'s ≥4-gate risk surface re-checked and still moot (S00103/S00108 solve in <200ms). New regression test alongside the beam one in `modules/solver/search.test.ts`. **Lesson generalizes**: "aggregate looks fine" evidence about a code path doesn't cover a specific conditional branch within it — when auditing an instrumentation gap, check every *exit reason* of a related function, not just whether the function as a whole seems to produce reasonable numbers.
- **`solveLevel()`'s worst-case wall time is now up to 8x nominal `timeBudgetMs`, not 6x — and it's controlled by TWO independent, non-coupled overrides, not one.** The 2026-07-16 attraction-diversity last-resort pass (previous gotcha) adds its own separate additive budget (`ATTRACTION_DIVERSITY_BUDGET_FRACTION`, default 1.0x) on top of repair fallback's own `REPAIR_EXTRA_BUDGET_FRACTION` (default 6x) — so a level that fails everything now costs up to `(1 + 6 + 1) × timeBudgetMs`, not `(1 + 6) ×`. Deliberately a **separate** override (`SolveOpts.attractionDiversityBudgetFractionOverride`, not reusing `repairBudgetFractionOverride`): an early version of this gated the new pass on `repairBudgetFraction > 0` to reuse the existing override, which meant a solver-testing sweep trying to disable ONLY repair's 6x extension (per this session's own repair-budget-fraction policy above) silently re-enabled the diversity pass's own extra cost too — the opposite of a "solver-testing shouldn't wait on extensions" sweep's intent. **Any tool that solves a batch of levels and wants to honor the solver-testing policy must now pass BOTH `--repair-budget-fraction=0` AND `--attraction-diversity-budget-fraction=0` (or the equivalent `SolveOpts` fields), not just the first one** — `scripts/stress/benchmark.mjs`, `scripts/portfolio-solve-sweep.mjs` (both its sequential and `--workers`/worker-process paths), and `scripts/solver-parallel/race.mjs`'s raced engine all support both flags/fields as of 2026-07-16; a future new batch tool needs to wire up both from the start, not just the historically-older repair one. The two interactive solve UIs (`solver-controller.ts`'s "Find 1 Hint", `review-controller.ts`'s review-approval) already pass `0` for both. See [`reports/2026-07-16-phase-d-attraction-diversity-implementation.md`](reports/2026-07-16-phase-d-attraction-diversity-implementation.md) and [`docs/solver-architecture.md`](docs/solver-architecture.md#attraction-diversity-last-resort-pass-2026-07-16). **A real `nodeBudget` composition bug was found and fixed the next day, while writing the first test that actually exercised `opts.nodeBudget` against this pass**: it computed a *remaining* budget (mirroring the repair loop's own pattern) and passed that into `runInterleavedAttempts`/`runGateSerialAttempts` — but those two functions check `nodeBudget` directly against the *global cumulative* `prep._metrics.nodesExpanded` (correct for the main loop's own call, since that counter is 0 when it runs first), not a local-relative counter the way `repairSearchFromGate`'s own `nodeBudget` param is. A remaining value read against an absolute check meant the pass could silently skip itself even with plenty of absolute budget left, whenever the main loop's own spend already exceeded the (much smaller) remainder. Fixed by passing the same absolute `nodeBudget` the main loop already uses; see the report's follow-up section for the two regression tests. **A third, more severe budget-composition bug was found and fixed 2026-07-17, while auditing an "unexplained" wall-time overshoot flagged in a dose-response experiment** ([`reports/2026-07-17-attraction-diversity-dose-response.md`](reports/2026-07-17-attraction-diversity-dose-response.md)'s "unexplained observation"): the early repair *probe* (`runRepairProbe`, tried before the main loop on any repair-gated level) has its own fixed node budgets (`REPAIR_PROBE_ORDINARY_NODE_BUDGET` × up to `REPAIR_PROBE_ORDINARY_SEED_SALTS.length` seeds, plus `REPAIR_PROBE_BIASED_NODE_BUDGET` on must-turn levels) that were **completely unaffected by `repairBudgetFractionOverride`, even at `0`** — those node budgets were calibrated only against levels where the probe *wins* quickly, never against a level where repair never succeeds at all and the probe burns its *full* node budget as dead search every single solve; on a heavily-constrained level that dead search alone can cost several real seconds. Confirmed directly on corpus-2's R02401 (repair-gated, never solved by repair): `repairBudgetFractionOverride: 0` correctly zeroed the *later* full-budget fallback loop, but the probe still ran to completion — two ordinary-tier attempts at ~5.5s and ~5.2s, exactly the ~10.7s the overshoot traced to. Fixed by resolving `repairBudgetFraction` before the probe (not just before the later fallback loop) and skipping the probe outright when it resolves to exactly `0`, the same "no repair-related cost, period" signal the later loop already honored; every other value (production default, or any nonzero override) leaves the probe's behavior unchanged. **Trade-off measured, not assumed**: on the 4 real repair-gated published levels (P00136/P00144/P00145/P00146), the interactive-UI path (`repairBudgetFractionOverride: 0`) previously solved all 4 via the probe (70–3528ms); post-fix they solve via the main loop instead (393–8113ms, one case ~100x slower) — still solvable, still far under the 30s promise, but no longer for free. `solver:bench --check` (160/160, no regressions) only covers the *default*-override production path, which this fix leaves byte-identical — it does not by itself demonstrate the interactive-UI trade-off is acceptable; that was checked separately by direct measurement. Two new regression tests in `orchestration.test.ts` cover both directions (override exactly `0` skips the probe; the production default still reaches it). **2026-07-18: added `SolveOpts.disableExtraBudgetPasses`**, a purely-additive convenience that sets both `repairBudgetFractionOverride` and `attractionDiversityBudgetFractionOverride` to `0` in one boolean — an explicit value on either individual override still wins, so a sweep can still isolate one pass's cost via `disableExtraBudgetPasses: true` plus an explicit override on just that one field. Doesn't retire the two individual overrides (still needed for that isolation case) or retroactively fix any tool that already hardcodes both flags — it's there so a *future* batch tool only has to wire up one option instead of remembering both.

- **A caller-supplied partial `ablation` config used to silently disable every OTHER unset flag — now normalized at the boundary instead of relying on every caller to remember `defaultConfig()`.** Every ablation-gated read site in the solver (`scoring.ts`, `prune-gauntlet.ts`, `search.ts`, `repair-search.ts`, `orchestration.ts`, `attempts.ts` — 60+ call sites) checks `(!cfg || cfg.SOME_FLAG)`: "no ablation config at all" is the only way an unset flag defaults to `true`. A sparse object like `{ STRATEGY_REPAIR_PROBE: true }` makes `cfg` non-null, so every *other* unset `STRATEGY_*`/`SCORE_*`/`PRUNE_*` flag now reads as `undefined` (falsy) — this is the exact bug `repairBudgetFractionOverride`'s own field comment already documents shipping to production once (fixed by moving that override, and `attractionDiversityBudgetFractionOverride`, out of `ablation` entirely into dedicated `SolveOpts` fields — see the gotcha above), and the reason the attraction-diversity pass builds its own overlay config through a hand-rolled `Proxy` instead of a plain `{ ...cfg }` spread. Those two production-path instances were already fixed, but the underlying trap in the general `(!cfg || cfg.FLAG)` read-site contract was not — confirmed still live in `orchestration.test.ts` itself, which had two tests passing sparse `ablation` objects (`{ STRATEGY_REPAIR_PROBE: true, STRATEGY_REPAIR_PROBE_MULTI_SEED: false }`, `{ STRATEGY_ATTRACTION_DIVERSITY: false }`) with comments explicitly noting the side effect and arguing it happened not to matter for those particular assertions — correct, but exactly the kind of memorized-workaround CLAUDE.md's own working rules warn against relying on. **Fixed 2026-07-18** by adding `normalizeAblationConfig()` (`orchestration.ts`) at the only two places an externally-supplied `opts.ablation` ever becomes `prep._cfg` (`solveLevel`, `runPortfolioExperiment`) — every downstream read site (all 60+, plus any future one) gets `prep._cfg` from nowhere else, so normalizing exactly there closes the trap everywhere at once without touching any read site's code. Returns `null` unchanged (the production/default fast path, byte-for-byte preserved — confirmed via `solver:bench --check`, 160/160 no regressions, since this path never even constructs the wrapper); for a non-null config, returns a `Proxy` that reads the caller's own keys where present and defaults every other flag to `true` — *except* `ATTEMPT_ORDER`/`_randomSeed` (attempts.ts's two non-boolean fields, which must stay `undefined` when absent, not `true` — a naive one-Proxy-fits-all version was caught defaulting a missing `_randomSeed` to `true` instead of falling through to `?? 42`, corrupting `shuffleAttemptConfigs`'s seed). The Proxy also implements `has`/`getOwnPropertyDescriptor`/`ownKeys` so `'PROFILE_x' in cfg` and `Object.prototype.hasOwnProperty.call(cfg, ...)` — which `attempts.ts`'s `PROFILE_*`/`TEMPLATE_*` checks and the diversity-pass's own `Proxy` both already rely on to distinguish "explicitly set" from "absent" — keep reflecting the caller's real object instead of the Proxy's own (always-empty) target. Deliberately not a plain merged object: the flag registry (`scripts/ablation-config.mjs`'s `FEATURES`) is Node-tooling-only, and duplicating it into this browser-bundled runtime module would be a second list to keep in sync on every new flag — the exact class of drift `LEVEL_KEY_FIELDS`/fingerprint-version-bump gotchas elsewhere in this file warn about; the Proxy needs no flag list at all, so a newly-added `SCORE_FOO` flag defaults correctly with zero extra wiring. Verified via the full existing test suite (919/919 across the repo) plus `solver:bench --check`.
- **Open board space is a puzzle variable in its own right, not inert scaffolding around the "real" puzzle** (objects + win metrics). A level with more navigable-but-unused space is not thereby an unchanged or strictly-easier puzzle from the solver's point of view, even though every one of the game's own scoring fields (`reqLen`, `reqInt`, object inventory) can hold perfectly fixed while that space changes — the raw size of the search space the solver actually explores changes anyway, and several solver techniques key off it directly (`perimeterSweep`-family profiles scan relative to the grid boundary by construction; the early repair probe's search order is sensitive to it empirically, not just in theory). **Confirmed empirically, not hypothetically**: growing a repair-gated level's grid — adding only empty, untouched space, zero object or witness changes — flipped it from complete repair-probe failure to complete repair-probe success at 3 different grid sizes tested, while a different level in the same test switched which winning technique it used (`perimeterSweep` → `objectiveFirst`) purely from the same manipulation. See [`reports/families/2026-07-15-re-embedded-cousin-grid-growth.md`](reports/families/2026-07-15-re-embedded-cousin-grid-growth.md) (part of [`docs/sibling-cousin-system.md`](docs/sibling-cousin-system.md)'s research program). Treat available space (navDensity, grid size relative to content, how much of the grid the witness never visits) as a first-class dimension of a level's solver-difficulty profile — something to consider and report on deliberately — not a neutral backdrop that placement and metrics happen to sit in.
- **FIXED 2026-07-18 — a bare number in any batch tool's `--levels=<spec>` used to mean one of two incompatible things depending on the tool, and picking the wrong one silently selected a different real level rather than erroring.** Some tools (`solver:bench`, `solver:direct`, `portfolio-solve-sweep.mjs`, `portfolio-scheduler-report.mjs`, `solver-fingerprint.mjs`, `hint-candidate-search.mjs`, `hint-path-oracle.mjs`, `trap-search-audit.mjs`) treated it as a literal 1-indexed array position; others (`hint-workbench.mjs`, `stress:benchmark`, `stress/witness-divergence.mjs`, `stress/missing-levels.mjs`) treated it as an ID-suffix lookup. **This caused two real mistakes in one session** (a sharded `hint-workbench.mjs` run misrouted an entire worker's batch; `stress:benchmark` solved the wrong level), plus a separately-discovered live bug in `run-ablation.mjs`'s own bespoke stress-corpus parser (hardcoded to `S`-prefix/5-digit-width, silently matching nothing at all against corpus-2's `R`-prefixed ids). **Fixed by requiring an explicit `pos:`/`id:` prefix on every bare number/range** in both shared parsers (`scripts/level-data-io.mjs`'s `parseLevelPositions`/`parseLevelSelector`, used by every tool listed above) — a bare unprefixed number now throws `AmbiguousLevelSpecError` instead of silently picking a convention. A full id string (e.g. `R00237`) still needs no prefix (inherently unambiguous). `run-ablation.mjs` was migrated off its own bespoke copy onto the same two shared parsers as part of this fix, closing both its drift from the rest of the tooling and its live `S`-prefix bug. This is a **breaking change** to every documented `--levels=<bare-number>` example/invocation — every npm-script usage comment, `docs/ablation.md`, and the one CI workflow that passed a bare range (`solver-stress-refresh.yml`) were updated to the new `pos:`/`id:` syntax as part of the same fix. Full detail: [`docs/solver-architecture.md`](docs/solver-architecture.md#--levels-selector-syntax--explicit-posid-prefix-required-fixed-2026-07-18).

## Level Stats
- **156 levels total** (test levels 148–150 use landmark mechanics).
- Max must-pass 4 · max must-cross 4 · max portals 3 pairs (6 keys) · max flipping filters 4 · grids up to 15×15, **always square** (`grid.w === grid.h` — every published level is square; no rectangular level has ever shipped). All masks fit in 32-bit integers (no BigInt).
- **Grids must be square.** Enforced by `validateRawLevel` (`domain/level-schema.ts`) — the same hard schema gate every level passes through regardless of authoring path (editor export, hand-written JSON, stress-test generation, Firestore import), so a rectangular level can't reach any corpus. **History**: this wasn't checked until 2026-07-11 — both stress generators (`scripts/stress/generate.mjs`, `generate-random.mjs`) independently drew grid width and height as two separate random rolls, so most generated levels silently drifted non-square (348/450 in stress-corpus-1, 1372/1700 in stress-corpus-2) with nothing catching it; see `data/stress/README.md`'s "Square-grid cleanup" note for the corpus surgery that followed. Don't infer from `PortalLike`/`CoordLike`-style loose typing elsewhere that grid shape is similarly unconstrained — it's the one dimension-shaped invariant that actually is hard-enforced.
- Level coordinates in `data/levels.json` are **1-indexed**; the solver normalizes to 0-indexed internally.
- ~9,600 hint paths total feed the in-game hint system; stored in the per-level `data/hints/<id>.json` artifact (split out of `levels.json` so the boot payload is the ~144 KB authored data, not the ~2.5 MB corpus) and **lazy-loaded per level** on first hint request via `data.getHints(level)` (the raw level object, not a number — see the Hint provenance section below). For the **published** corpus, `getHints` also merges in any Firestore-stored supplemental hints for that level (`data.ts`'s `withFirestoreHints`, keyed by the level's fingerprint — never for the stress corpora, which aren't real published levels) — see the Provenance section below for where those come from. `getHints` always returns the **full** (local + Firestore) hint set — curation and the heat-map are client-side derivations over it. In play mode the player cycles a **curated** mutually-distinct subset (not all of them) — the selection metric, coverage guarantees, and cap live in `modules/domain/hint-selection.ts` ([`docs/hint-curation.md`](docs/hint-curation.md)); the heat-map still uses the full set.
- **Every published level carries a persistent `id`** (`P00001`..`P00156`, backfilled 2026-07-15 — see `docs/archive/level-id-unification-plan.md`), matching the letter-prefixed ids both stress corpora already had. Player-submitted levels are imported from Firestore via `npm run levels:import-published` (runs under `tsx`; matches by the same canonical `domain/level-fingerprint.ts` fingerprint the app uses for submission/publish duplicate detection — a level already in `levels.json` has only its *new* hints merged in — deduped by path signature, capped at 1,000 — instead of being re-appended as a duplicate; a genuinely new level is appended and gets the next unused `P`-prefixed id, minted by `makeLevelIdMinter()` following the same never-reused idCounter pattern the stress generators use; regenerates `level-heatmaps.json` when anything changed). The script exports its pure helpers (`normalizeLevel`/`fingerprint`/`mergeNewHints`/`makeLevelIdMinter`, unit-tested in `scripts/import-published-levels-unit-tests.mjs`) and guards its network-touching `main()` behind an `import.meta.url` entrypoint check, so importing it never has side effects. A level only gets its permanent id at this graduation point (generation time for stress corpora, import time for published) — the Firestore `published_levels` staging collection itself stays keyed by Firestore's own opaque doc id + fingerprint, unaffected by this.

## Provenance

Two independent, deliberately-mirrored append-only provenance schemas — one per hint, one per level. Neither is ever overwritten; both only ever gain new history entries. Neither affects level fingerprinting (`level-fingerprint.ts` excludes both `hints` and `provenance` from its comparison fields), so provenance never creates a false "different level."

### Hint provenance
- Canonical type: `Hint = { path: number[]; provenance: HintProvenanceEntry[] }` in `modules/domain/hint-types.ts`. A hint's `provenance` array holds one entry **per discovery event** — if the same path is independently rediscovered by a different technique/run, that's a new entry appended to the same hint, not a new hint (never a rejected duplicate that silently loses its provenance — `scripts/hint-workbench.mjs`'s generators surface a rediscovery of an already-known path instead of dropping it, specifically to keep this invariant true end-to-end). Each entry nests `solver` (family/config), `search` (technique, termination reason, budget, seed, nodes expanded, elapsed ms), and `context` (hint-guided flag, level revision) sub-objects — see the type for the exact fields.
- **Dual-field storage pattern**: every place that carries hints keeps two parallel fields — a plain `number[][]` (`.hints` / `.foundHintsSinceLoad`) for existing path-geometry/dedup consumers that only care about the route, and a canonical `Hint[]` (`.hintRecords` / `foundHintsSinceLoadRecords`) carrying the provenance. The two are bridged only at storage/transport boundaries via `reconcileHints`/`mergeHints` (`modules/domain/hint-types.ts`) — don't hand-roll the merge elsewhere.
- On disk, all 3 corpora use the same per-level artifact format (`{schemaVersion: 3, hints: Hint[]}`), read/written exclusively through `scripts/level-data-io.mjs` (`readLevelHints`/`writeLevelsWithHints`/`parseHintFileContents`/`stringifyHints`) — never hand-edit or re-serialize these files directly: published → `data/hints/<id>.json`; stress-corpus-1 → `data/stress/hints/<id>.json`; stress-corpus-2 → `data/stress/hints-random/<id>.json` (a sibling directory, not `hints/`, since corpus 1 and 2 share `data/stress/` as a parent but number levels independently — see `hintsDirFor` in `level-data-io.mjs`, which derives the directory name from the levels-json basename). The join key is `hintKeyForLevel()`'s job: a level's own persistent `id` string when it has one (every level in all 3 real corpora, post-2026-07-15 — `P00042.json` published, `S00028.json`/`R00028.json` stress, used verbatim, not stripped to a bare number, since Corpus 1 mixes S-/R-prefixed ids whose numeric suffixes can collide), else its 1-based array position (a level with no id yet — an editor draft, or a Firestore `published_levels` staging doc not yet pulled in by `levels:import-published`; see `docs/archive/level-id-unification-plan.md`). **History**: this was position-only for all 3 corpora until 2026-07-12 (stress corpora) / 2026-07-15 (published), when it turned out the stress corpora's `id` field was never actually used for hint storage — meaning reordering either stress corpus's array would have silently misattributed every hint file, despite an `id` field existing specifically to prevent exactly that; the published corpus never had an `id` field at all until the 2026-07-15 migration (`scripts/backfill-level-ids.mjs`) gave it one. Both migrated via `scripts/migrate-hint-files-to-id-keys.mjs` (one-time; verified lossless by summing hint counts per-file before/after the rename, not just trusting the file count). Runtime hint fetch (`modules/data-asset-loaders.ts`'s `createDefaultHintsSource`) and `DataService.getHints` (`modules/data.ts`) are id-aware in lockstep with on-disk storage: `getHints` takes the raw level object itself (not a position), reads `level.id` to build the fetch URL when a network fetch is needed, and falls back to a level's inline `.hints` (always present for Firestore-staged levels that have no `id` yet) otherwise — so there's never a call site with an id/position but no level object to get it from. The one-time bare-array/`hintMetadata`-wrapper → `schemaVersion: 2` backfill (`scripts/migrate-hint-schema-v2.mjs`, already run) is now redundant with `parseHintFileContents`'s on-read auto-upgrade of any legacy shape (including the later v2 → v3 nested-provenance step) — kept only as a historical record, not something to re-run.
- Provenance is attached **at find-time**, regardless of whether the hint is ultimately submitted: `modules/solver/hint-provenance.ts`'s `deriveSolveAttemptInfo`/`provenanceFromSolveResult`/`hintsFromVarietyResult` are the single source for building entries, called from both the UI solver path and script tooling (`scripts/hint-workbench.mjs` and friends) so the two never drift into different shapes.
- Provenance persists through the editor → submission → review → publish pipeline unchanged except for appended entries; see `submission-controller.ts` and `review-controller.ts`.
- **A published level's hints aren't only ever local.** Firestore's `local_level_hints/{fingerprint}/entries/{entryId}` collection holds supplemental hints for a level that lives in `levels.json` (not Firestore) — any authenticated session (every player gets one at boot) may add an entry, and `data.getHints` merges it with the local set transparently (see the Level Stats section above). Two write paths feed it: a hints-only resubmission of an already-published level (`submission-controller.ts`'s local-corpus-match path) and an invisible auto-save on every ordinary Play-mode win (`win-controller.ts`'s `saveWinAsHintIfNovel`, fire-and-forget so a Firestore failure never affects the player) — both gated by the same novelty check against the merged local+Firestore set and a 5,000-hints-per-level soft cap. Full write-path/rules detail: [`docs/firestore-security-model.md`](docs/firestore-security-model.md).

### Level provenance
- Canonical type: `LevelProvenance = { history: LevelProvenanceEntry[]; origin; confidence }` in `modules/domain/level-provenance-types.ts`. Each `LevelProvenanceEntry` records one lifecycle event (`actor`, `action`, `method`, `detail`, `timestamp`) — e.g. `authored`/`generated`/`submitted`/`reviewed-approved`. `origin` and `confidence` are derived summaries (`deriveOrigin`) re-computed from `history` on every append via `appendProvenanceEntry` — never hand-set independently of the history that justifies them.
- Lives directly on the level object (`EngineLevel.provenance`, `modules/domain/level-schema.ts`) alongside the grid/hints/win-metrics — **not** in a separate report or doc. `null` (never silently omitted) means "no known provenance," e.g. very old pre-schema data.
- **Invariant: every newly-created level must include provenance.** It is stamped at the moment of creation, never backfilled after the fact for new levels:
  - Editor `createNewLevel()` (`modules/editor.ts`) stamps `{actor: 'human', action: 'authored'}`.
  - Both stress-corpus generators (`scripts/stress/generate.mjs`, `scripts/stress/generate-random.mjs`) stamp `{actor: 'procedural', action: 'generated', method: <generator id>, detail: {...batch/seed metadata}}`.
  - Submission (`submission-controller.ts`) appends `{actor: 'human', action: 'submitted'}` on top of whatever provenance the level already carried.
  - Review approval (`review-controller.ts`, non-hint-addition path) appends `{actor: 'human', action: 'reviewed-approved'}`.
- Carried through the wire format like any other level field: `domain/level-codec.ts`'s `normalizeMetadata` (parse + clone), `denormalizeLevel`, and `buildWireLevelData` all pass `provenance` through explicitly — it is **not** covered by any implicit "everything else" spread, so a new serialization boundary must add it by name or it silently drops (this exact class of bug previously hit `hints` before the dual-field pattern existed).
- **Enforced by `check:level-provenance`** (`scripts/check-level-provenance.mjs`, part of `npm run check`): hard-fails if any level in any of the 3 real corpora has a missing/empty `provenance.history`.
- All pre-existing levels (156 published + 450 stress-corpus-1 + 1700 stress-corpus-2) were one-time backfilled (`scripts/backfill-level-provenance.mjs`) rather than left without provenance. Published-corpus confidence tiers came from a retired classifier report that had already cross-referenced Firestore rating tags (`certain-human`/`certain-ai` from `great`/`common` tags, else `confidence: 'likely'` for untagged levels ≤130 — see the entry's own `detail.reason` for the exact tier reasoning); stress-corpus entries were built directly from each level's own `stressMeta` (`confidence: 'certain'`, since these are unambiguously generator output). This backfill fully replaced an earlier read-side-only classifier/report system (`docs/level-corpus-provenance.md` and friends, since deleted) that computed the same facts on demand instead of storing them on the level.

## Firebase Integration

The app reads/writes level submissions and player progress to Firestore. `firebase-config.js` is the **public client-side web config — safe to commit** (authorization lives in Firestore rules). Firebase uses the **modular SDK** (`firebase/app`/`auth`/`firestore`), bundled by Vite (no CDN compat scripts); there is no Firebase Hosting. `modules/persistence/` holds the client wrapper (`firebase-client.ts`, the typed seam) plus the submission/progress/review/rating repos and the offline `local-session-store`. See [`docs/firebase-config-and-secret-hygiene.md`](docs/firebase-config-and-secret-hygiene.md) and [`docs/firestore-security-model.md`](docs/firestore-security-model.md).

## Testing & Workflows

- **`npm run ci`** — required pre-merge gate: static checks + Vitest unit/integration + node validators (browser-free). **`npm run ci:full`** adds Playwright e2e. **`npm run test:visual`** is opt-in (environment-sensitive baselines). Tier map, filters, coverage, and e2e/visual detail: [`docs/testing.md`](docs/testing.md).
- **Solver hot-path change** → `npm run solver:bench -- --check` (no regression vs `logs/solver-baseline.json`) **and** a before/after speed comparison (`nodesExpanded`/wall-time across the full corpus) — the former checks solvability only, the latter checks cost; a change needs both before it's reported as verified. See the "Verify before you claim done" rule above and the Solver Architecture gotcha on this.
- **Adding a new level**: append to `data/levels.json` (1-indexed; give it the next unused `P`-prefixed id, e.g. `P00157`; hints, if any, go in `data/hints/<id>.json` — write them via `scripts/level-data-io.mjs`), run `npm run test:hint-path-oracle` (fails if any stored hint isn't PLAY-valid); debug with `npm run solver:direct -- --levels=<N> --verbose`.
- **Solver CLI, audit-JSON format, and debug/perf/archetype/trap recipes**: [`docs/solver-architecture.md`](docs/solver-architecture.md).

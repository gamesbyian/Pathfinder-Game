# Production-search sibling construction result 001

> **Status:** concluded-positive
> **Last evidence:** 2026-09-17 — multi-pick frontier resample (50 cases, 2 parents) finding 2 exact-LIVE, referee-verified Class-5 siblings on `R03147`, current HEAD.
> **Decision:** the naive goal-distance-greedy walk's 0/75 (+0/24 shallow) LIVE result was **not** a residual-structure finding, but it was also **not simply fixed by using the real production search** as first assumed. Swapping in the actual production `beamSearchFromGate`/`intersectionHarvest`/width=5000 (via the already-audited `pauseAfterPhases`/`resumeFrom` research primitive, zero solver-internal changes) and drawing ONE seeded-random sibling per checkpoint still found 0/98 LIVE across every depth tested (0.1/0.35/0.55/0.75) -- matching the naive walk's own negative almost exactly. The actual missing ingredient was **sampling power, not search quality**: a follow-up drawing 25 *distinct* nodes from the same real production frontier (instead of one) on the two parents independently known to be feasible from the gate found `R03147` has a real, if low (~8%), live fraction in its depth-11 frontier -- 2/25 samples came back exact-LIVE and referee-verified -- while `R01600`'s frontier stayed 0/25 even at this larger sample. **The production-search-quality constructor works; single-draw-per-checkpoint sampling does not.**
> **Remaining gate:** a decision-bearing matched-LIVE/DEAD population needs multi-pick-per-parent sampling (many draws from one frontier), not the wide-parent/single-sample design tried here and in the original naive-walk harvest. `R01600`'s continued 0/25 also leaves open whether some parents have a genuinely much lower (or zero) live fraction under this specific technique/width -- untested whether a larger sample or a different profile/width would change that.
> **Evidence role:** closes the handoff gate `docs/solver-fresh-dead-sibling-harvest-preflight.md` named ("a production-search-quality sibling constructor... a separate, larger implementation task") that has been blocking Lanes B, D1, E, and G1-stage2 all session, with an important methodology correction attached.
> **Population identity:** same 25 parents/seed (`class5-fresh-sibling-pilot-001`) as the naive-walk harvest, for direct construction-method comparability, plus a targeted 50-case multi-pick follow-up on `R01600`/`R03147`.

## Why this ran

Every lane this session that reached the fresh-sibling-harvest handoff gate (Lane B's DEAD-core, Lane D1's matched-pair realizability, Lane E's dependency-defined revision, Lane G1-stage2) stopped there: the naive goal-distance-greedy walk found 0/99 LIVE Class-5 siblings across every tested depth, and the result report explicitly named the fix -- "a materially better sibling-construction method... using the real production search technique/scorer" -- as a separate, larger implementation task, not attempted in that pass. This picks that up.

## What was built

`scripts/stress/class5-production-search-sibling-harvest.mjs`: runs the REAL, unmodified production `beamSearchFromGate` (`intersectionHarvest`, width=5000/`BEAM.WIDE` -- the single most-tried production beam config in `modules/solver/attempts.ts`) via the already-audited, already-tested `pauseAfterPhases`/`resumeFrom` continuation primitive (`docs/solver-search-resumability.md` -- proven to reproduce uninterrupted execution exactly). No solver-internal code was touched: this is a pure external caller of a stable, existing API built for a different research line (beam-continuation pilots) and simply pointed at this problem. One continuous beam trajectory per parent is chained across the same three depth-fraction checkpoints (0.35/0.55/0.75) the naive walk used; at each checkpoint one candidate is drawn via a seeded uniform pick over the ACTUAL live frontier the production coarse-state-merge/score-width cull retained, then reconstructed into a full legal prefix by walking its parent-pointer chain (mirroring `search.ts`'s own internal, unexported `_reconstructBeamPath`).

`scripts/stress/class5-production-search-frontier-multi-pick.mjs`: the statistical-power follow-up -- instead of one seeded pick per frontier, samples K distinct nodes (Fisher-Yates, no replacement) from the same captured frontier, to directly estimate a frontier's live fraction rather than infer it from a single Bernoulli draw.

## Result

**Main harvest (25 parents, checkpoints 0.35/0.55/0.75):** 73/75 sibling draws (2 parents naturally exhausted -- frontier collapsed to empty -- before reaching 0.75), 0 solved outright during construction. Exact labels: **0 live / 72 dead / 1 abstain**. `inputAlarms: 0` on both this harvest and the shallow follow-up below -- every prefix independently confirmed native-legal before CP-SAT ran, ruling out a reconstruction bug.

**Shallow follow-up (25 parents, checkpoint 0.1, matching the naive walk's own shallow check):** 25/25 draws. Exact labels: **0 live / 16 dead / 9 abstain** (the higher abstain rate is expected -- a shallower prefix leaves a much larger CP-SAT search space, so more 60s timeouts). `R01600` and `R03147` -- the two parents an earlier gate-only feasibility check independently confirmed genuinely CP-SAT-feasible from just the 1-cell gate prefix -- both still labelled DEAD at this single-pick depth-0.1 draw.

At this point the production-search constructor's single-pick results (0/98 across all depths) looked like a near-exact replay of the naive walk's own negative (0/99), which would have meant the construction-method hypothesis was wrong and something more fundamental was going on (e.g., genuine early self-trapping under real production search). Before accepting that conclusion, one gap stood out: **every result so far, on both constructors, drew exactly one candidate per frontier per checkpoint.** If a frontier's true live fraction were low but nonzero -- plausible on levels this hard -- a single draw could easily miss it by chance; 98 consecutive single-draw misses at a true live rate of even 3% has roughly 5% probability under a naive binomial model, not decisive.

**Multi-pick follow-up (25 distinct frontier samples each on `R01600`/`R03147`, depth-fraction 0.1):** **2 live / 48 dead / 0 abstain.** Both LIVE cases are `R03147` (2/25 = 8%), both `cpSatStatus: OPTIMAL`, both `refereeValid: true` (independently verified by the native PLAY referee, not just trusted from the CP-SAT witness). `R01600` stayed 0/25 even at this larger sample.

## What this proves and what it leaves open

**Proven:** the production-search-quality constructor is not broken and the original 0/99 naive-walk negative was correctly diagnosed as a construction-method artifact -- just not fixed by switching construction method alone. `R03147` now has a clean, non-confounded matched contrast: 2 exact-LIVE and 23 exact-DEAD siblings, all drawn from the SAME real production search frontier at the SAME depth -- a better-controlled matched pair than any prior population this investigation produced (B2's matched pairs needed post-hoc scalar matching; these come from one shared frontier by construction).

**Left open:** `R01600`'s frontier stayed 0/25 despite being independently gate-feasible. Whether its true live fraction is much lower (needs more samples), zero under this specific technique/width (a real per-level finding, not a bug), or recoverable under a different profile/width is untested. Scaling this into a larger matched population needs a **multi-pick-per-parent** design (many draws, few parents) rather than the wide-parent/single-sample design both harvests here used -- more CP-SAT cost per parent, but now known to be worth paying rather than wasted, which the pre-multi-pick evidence could not have told us.

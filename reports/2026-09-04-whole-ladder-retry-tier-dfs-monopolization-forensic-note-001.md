# Whole-ladder retry tiers: fresh confirmation that first-config monopolization is still the load-bearing mechanism

> **Status:** concluded-positive
> **Last evidence:** 2026-09-04 — local re-analysis of `reports/portfolio/static-portfolio-entrypoint-production-ab-001/production-arm.json` (the same 40-level production A/B lifecycle data this session's marginal-value-tail-audit used), no new dispatch
> **Decision:** current-HEAD data reproduces the exact mechanism `STRATEGY_RETRY_TIER_NODE_STAIRCASE` was built to fix and was closed negative for on 2026-08-19: within each of four whole-ladder ablation-disabled retry tiers, DFS configs consistently fail to naturally exhaust (0/60 to 0/125 per tier, 435/435 across all four) while consuming 29-49% of that tier's total work, because one non-terminating config runs long enough to consume most/all of the tier's shared reserve before later configs get a real turn. Per that 2026-08-19 evidence ("the division defect is real as a mechanism and simultaneously load-bearing in effect" — 8 of 9 real production wins that depended on this exact behavior were lost when it was "fixed"), **this is confirmatory/forensic evidence that the closed-negative disposition still holds at current HEAD, not a new finding that reopens it.**
> **Remaining gate:** none. This does not reopen `STRATEGY_RETRY_TIER_NODE_STAIRCASE` — no materially different protection mechanism is proposed here, which is what its own reopen condition requires.
> **Evidence role:** forensic — replay/diagnosis of an already-closed mechanism at current HEAD on fresh data, establishing the mechanism still holds, not new capability evidence
> **Selection:** the 40-level population is the existing disjoint draw from `2026-09-04-static-portfolio-entrypoint-production-ab-001.md` (prespecified there, reused here); this report's question (does the 2026-08-19 monopolization mechanism still appear at current HEAD) was formed before inspecting the data, but the specific numbers below are observational, not a prespecified confirmation test

## Why this report exists

While tail-auditing `must-cross-neighbor-prune-disabled-retry` and `connectivity-axis-prune-disabled-retry` (both explicitly flagged in `docs/solver-opt-in-experiment-ledger.md` as "material cost makes it a scheduler tail-audit candidate" / "retain as baseline but reprice residual value") using the same already-committed 40-level A/B lifecycle data as `2026-09-04-production-ladder-marginal-value-tail-audit-001.md`, a striking pattern emerged: DFS attempts inside these tiers **never** naturally exhaust, while consuming a large share of each tier's work. Before writing that up as a new repricing candidate, a search of prior evidence (`docs/archive/snapshots/solver-opt-in-experiment-ledger-2026-08-20.md`) found this exact mechanism already investigated, named, and closed negative as `STRATEGY_RETRY_TIER_NODE_STAIRCASE` on 2026-08-19. This report exists to state that connection explicitly, with fresh numbers, rather than let a superficially "new" pattern get re-investigated as if it were unstudied — exactly the failure mode `docs/solver-optimization-workstreams.md`'s standing rules and `solver-research-data-assets.md`'s existing-data-preflight are meant to prevent.

## What `STRATEGY_RETRY_TIER_NODE_STAIRCASE` already established (2026-08-19)

Quoting the archived ledger directly: applying a per-config node staircase (so a non-terminating first config cannot consume a whole-ladder retry tier's entire reserve) to `goal-attraction-disabled-retry`, `coarse-state-near-tie-retention-disabled-retry`, `connectivity-axis-prune-disabled-retry`, and `guidance-goal-distance-retry` **eliminated starvation as measured** (coverage `1/16→16/16`, `1/7→7/7`, `5/6→6/6`) but was **decisively negative** on the real outcome: 0 solves gained on a 14-level gain sample, and **8 of the 9** Corpus-2 levels whose retry-tier win depended on the monopolizing first config **lost** their solve, at +72.7% wall time for −1.4% nodes. The archived conclusion: "giving the first config the whole reserve is not an accident to be fixed — it is what produces these tiers' wins." `STRATEGY_MC_NEIGHBOR_BUDGET_RETRY` (a fifth tier, `must-cross-neighbor-prune-disabled-retry`) keeps the same staircase unconditionally for a different reason — without it, that specific tier recovers nothing at all.

## Fresh evidence at current HEAD

Estimated per-attempt `workSpent` for each tier the same way this session's marginal-value-tail-audit did (median `workSpent`/`nodesExpanded` ratio per family/config, derived from `static-portfolio-arm.json`'s real per-attempt data, applied to `production-arm.json`'s `nodesExpanded`). Sanity check: aggregate estimates reproduce the tail-audit's own independently-reported per-stage totals to within 0.1% in every case below.

| stage | total attempts | DFS attempts | DFS work share | DFS naturally exhausted | beam naturally exhausted |
|---|---:|---:|---:|---:|---:|
| `must-cross-neighbor-prune-disabled-retry` | 146 | 60 | 29.0% | **0/60** | 62/86 |
| `connectivity-axis-prune-disabled-retry` | 247 | 125 | 48.1% | **0/125** | 70/122 |
| `guidance-goal-distance-retry` | 247 | 125 | 48.9% | **0/125** | 70/122 |
| `coarse-state-near-tie-retention-disabled-retry` | 247 | 125 | 47.8% | **0/125** | 68/122 |

**435/435 DFS attempts across all four tiers never naturally exhaust** (100% timed-out), while beam attempts naturally exhaust 53-57% of the time in every tier. Direct inspection of individual levels' attempt sequences (e.g. `R00893`, `R00923`) shows the mechanism concretely: cheap beam configs run first and exhaust quickly (each consuming 90K-400K nodes), then DFS configs run — one of them (which specific config varies by level) consumes whatever remains of the shared reserve (observed up to 6.5M nodes in one case) and still times out, while every DFS config positioned after it in that level's sequence gets a few hundred nodes and is immediately cut off. This is exactly the "non-terminating first config" pattern the 2026-08-19 evidence named, just with the specific monopolizing config identity apparently having drifted since then (plausibly through the intervening naming-cleanup/mechanic-buckets rename work), not a structurally new phenomenon.

## Interpretation

This is not a repricing opportunity, and this report does not nominate one. The 2026-08-19 evidence already established, on a real population-scale A/B, that removing this exact monopolization behavior costs real, load-bearing production wins (8/9 of the at-risk population) for a nontrivial wall-time cost, in exchange for eliminating a starvation pattern that "looks like" waste under a coverage-only or node-only metric — precisely the failure mode `CLAUDE.md`'s own standing warning about node/work counts being blind to real cost describes. The 0-solve outcome for these tiers on this session's 40-level population is consistent with, not contradictory to, that evidence: the archived risk-arm population found only 9 of 55 real ladder-rerun wins depended on this mechanism, a real but modest per-population hit rate at which a 40-level draw showing zero hits from these four tiers specifically is unsurprising, not disqualifying — the same base-rate logic this session already applied to `admissible-order-alternate-tiebreak-retry`'s tie-break profiles.

## What this does not establish

- Not a new repricing candidate for `must-cross-neighbor-prune-disabled-retry`, `connectivity-axis-prune-disabled-retry`, `guidance-goal-distance-retry`, or `coarse-state-near-tie-retention-disabled-retry`. `STRATEGY_RETRY_TIER_NODE_STAIRCASE`'s reopen condition explicitly requires "a different protection mechanism," and none is proposed here.
- Does not identify which specific DFS config monopolizes each tier's reserve on this population, or whether it matches the 2026-08-19 evidence's named configs (`dfs:perimeterSweep/cornerHarvest`, `beam:perimeterSweep/perimeterCW@beam2000`) — plausible given naming continuity, not directly verified.
- Single population, no independent confirmation needed or sought — this report's purpose is continuity/mechanism verification against already-decisive prior evidence, not a new claim requiring its own confirmation tier.

## Value of this report

The 2026-08-19 evidence is now over two weeks old relative to a solver codebase that has changed substantially since (naming cleanup, budget-model migration, multiple promoted mechanisms). Confirming the load-bearing mechanism it identified still reproduces at current HEAD, on fresh data, is a small, cheap, useful piece of continuity evidence: it means `STRATEGY_RETRY_TIER_NODE_STAIRCASE`'s closed-negative disposition does not need re-litigating, and it heads off a plausible future session independently rediscovering "DFS never exhausts in these tiers, might be wasteful" and spending real effort proposing the same already-tested-and-rejected fix.

# The admissible-order-reserve caveat is resolved by construction under the fixed-cap portfolio design, not an independent blocker

> **Status:** concluded-positive
> **Last evidence:** 2026-09-03 — code reading of `modules/solver/orchestration.ts`/`stage-budget.ts`/`attempts.ts` at current head, cross-checked against `reports/stress/capability-runs/33588487486/equal-work-production-reach.md`'s already-collected real production join (1,802 rows, corpus1+corpus2)
> **Decision:** `docs/solver-optimization-workstreams.md`'s item (a) ("resolving the admissible-order-reserve question, or building a `portfolio-18-specialists` variant that swaps `mustCrossFirst` for a non-reserve-gated substitute, is a prerequisite for (d)") is not an independent prerequisite. The starvation is a structural property of the *current ladder's* single-shared-nodeBudget execution model, not of the three tie-break profiles themselves. A fixed-menu/per-technique-work-cap scheduler — the exact model `technique-census-cell.mjs` already uses for every static-portfolio-confirmation result — gives every technique, including each `admissible-order` tie-break profile, its own independent capped share by construction. Adopting that design (item (d)) resolves the caveat as a side effect; it does not need its own separate fix, reopened experiment, or a substitute-technique search.
> **Remaining gate:** none for this exact question. (b)/(c)/(d) from the workstream doc's own list remain open and are unaffected by this finding.
> **Evidence role:** development/clarifying analysis — corrects a serial-dependency claim in `docs/solver-optimization-workstreams.md` and `reports/2026-09-02-static-portfolio-confirmation-003-preflight.md`'s correction note. Not itself a scheduler promotion or a new experiment.

## Context

`static-portfolio-confirmation-003`'s corrected disposition (2026-09-02) established that `portfolio-18-specialists` — the curated 18-technique menu that Pareto-dominates every same-cardinality/larger alternative tested so far — includes `admissible-order|tieBreak=mustCrossFirst|lds=off`, one of three tie-break profiles (`mustCrossFirst`, `intersectionHarvest`, `nearClosureRescue`) that the already-closed-negative opt-in `STRATEGY_ADMISSIBLE_ORDER_PROFILE_NODE_RESERVE` was meant to protect. `docs/solver-optimization-workstreams.md`'s "Immediate execution priority" section framed resolving this caveat (or swapping out `mustCrossFirst` for a substitute) as a **prerequisite** for item (d), the real production-wiring design — "start there if this thread is picked back up."

This report is that starting point. It finds the prerequisite framing itself was not quite right: the caveat doesn't need its own resolution track because the specific design already nominated for (d) removes it automatically.

## The mechanism, read from current code

`orchestration.ts`'s admissible-order-fallback tier runs `ADMISSIBLE_ORDER_PROFILES` (`attempts.ts:226`, `['default', 'none', 'mustCrossFirst', 'intersectionHarvest', 'nearClosureRescue']`) in that fixed array order, unconditionally generated by `STRATEGY_ADMISSIBLE_ORDER` (default-on, not gated by the closed reserve flag — `attempts.ts:685-690`). Two separate reserve mechanisms exist, easy to conflate:

1. **`ADMISSIBLE_ORDER_NODE_RESERVE_FRACTION`** (0.25, unconditional, not an opt-in) withholds a slice of `nodeBudget` from every *earlier* tier (main loop, repair) so the admissible-order-fallback tier as a whole gets *some* guaranteed room (`earlyTierNodeBudget = nodeBudget - admissibleOrderNodeReserve`, `stage-budget.ts:1261`). This one is fine and unrelated to the caveat.
2. **`ADMISSIBLE_ORDER_PROFILE_NODE_RESERVE_FRACTION`** (0.15, the closed-negative opt-in `STRATEGY_ADMISSIBLE_ORDER_PROFILE_NODE_RESERVE`) would additionally reduce `'default'`'s *own* node ceiling within the tier, withholding room specifically for the other four profiles. **This is the one that's closed** (`docs/solver-opt-in-experiment-ledger.md`: "CLOSED NEGATIVE, POPULATION-VALIDATED. Corpus-2 validation lost four solves with essentially flat work.").

With that opt-in off (production default), `orchestration.ts:2166-2168` sets every non-`'default'` profile's own break condition (`profileCeiling`) to the **full, unreduced `nodeBudget`** — the same cumulative ceiling the whole solve shares, not a slice reserved for this tier's later profiles. Since `'default'` runs first in array order and checks that same shared ceiling, a `'default'` attempt that fails but expands many nodes can leave `mustCrossFirst`/`intersectionHarvest`/`nearClosureRescue` with `prep._metrics.nodesExpanded` already at or near `nodeBudget` by the time their turn arrives — not because they're disabled, but because the *node* dimension of their shared ceiling is already spent by a sibling that runs earlier in the same list.

This is real and already measured directly: `reports/stress/capability-runs/33588487486/equal-work-production-reach.md`'s joined production-reach table (1,802 real attempt rows across corpus1/corpus2, current head) shows `admissible-order|tieBreak=default|lds=off` reaching 922 levels with 48 wins, `tieBreak=none` reaching 836 with 29 wins — while all three reserve-gated profiles show **0 reached, 0 wins, 0 work, 0 missing-attempt-work**, i.e. never dispatched at all under today's finite-nodeBudget batch orchestration. This is real production telemetry, not a research-harness artifact, and it is fully explained by the mechanism above without needing the (already-closed) profile reserve.

(Separately, and not load-bearing for this finding: the live single-solve interactive UI (`solver-controller.ts`/`review-controller.ts`) passes `disableExtraBudgetPasses: true`, which zeroes `admissibleOrderBudgetFraction` entirely — `stage-budget.ts:1022-1026` — so the *whole* admissible-order-fallback tier, including `'default'`, never runs there at all. "Production" in this caveat's sense, and throughout this research line, means the offline/batch orchestration path corpus regression, hint generation, and capability sweeps use — the same path the equal-work-production-reach join measured. This isn't a new finding, but it's worth stating explicitly since "production orchestration" is used without this distinction in the prior reports and could otherwise read as claiming something about the live UI that isn't true either way.)

## Why the fixed-cap design sidesteps this by construction

`technique-census-cell.mjs`'s `runCell` — the exact harness every `static-portfolio-confirmation-00N` result was measured with — never shares a node ceiling across techniques at all. Each `cell.techniqueKeys` entry (each admissible-order tie-break profile is its own entry, distinct from `'default'`) gets `Math.min(remaining, cell.perTechniqueWorkCap)` of the gate's remaining *work*, independently, regardless of list position (`technique-census-cell.mjs:120-157`). `'default'` finishing its own bounded share and failing does not touch `mustCrossFirst`'s separately-bounded share — there is no shared depleting pool for the fixed-cap model to starve in the first place. This is precisely why the census results found `mustCrossFirst` as a genuine, if rare, sole rescuer of `R02971`/`R03338`/`R02055`/`R02450`/`R03071` in various confirmation populations: the harness gave it a real, protected shot that the current ladder's shared-`nodeBudget` semantics do not.

So: if (d)'s real implementation follows the design already characterized (a fixed ordered menu where every technique — including each admissible-order tie-break profile as its own independent list entry — gets its own bounded work share, exactly as `technique-census-cell.mjs` already executes it), the profile-starvation problem is not present in that design. There is nothing to "resolve" about the closed reserve mechanism, because the new design doesn't route these profiles through the old ladder's shared-pool tier at all; and there is no need to hunt for a non-reserve-gated substitute for `mustCrossFirst`, because the new design doesn't gate it on node reserve in the first place.

## What this does not establish

- This does not reopen or contradict `STRATEGY_ADMISSIBLE_ORDER_PROFILE_NODE_RESERVE`'s own closure — that mechanism, evaluated on its own terms (a node-ceiling reduction inside the *current* ladder), remains closed negative and should not be revisited without materially new evidence.
- This does not by itself confirm `portfolio-18-specialists` (or any fixed-cap menu) is safe to promote to real production — (b) production-envelope confirmation and (c) rare-capability retention auditing are untouched by this finding and remain open.
- This does not design the fixed-cap scheduler itself (stage coexistence, how repair's non-natural-termination interacts with a hard per-technique cap in a *live* ladder rather than a research harness, how the current tier/reserve architecture would be replaced or wrapped) — that is still (d)'s own, larger, unstarted question.

# The `-002` planner fix was necessary but insufficient — no-telemetry advisory-only dispatches need solo-sharding, not just a bigger wall-time estimate

> **Status:** inconclusive
> **Last evidence:** 2026-09-04 — control run [`33921242910`](https://github.com/gamesbyian/Pathfinder-Game/actions/runs/33921242910) (fraction=1.0 default), dispatched on `main` at `9eae0e6a` (includes the `-002` planner fix), combine-job log pulled via `get_job_logs`; treatment run [`33921247769`](https://github.com/gamesbyian/Pathfinder-Game/actions/runs/33921247769) cancelled before starting once the control result made the outcome clear, to avoid spending another ~80 minutes reproducing the same non-diagnostic truncation
> **Decision:** the `-002` fix (size the planner's wall-time estimate off `work_budget` instead of raw `node_budget` when `node_budget_advisory_only=true`) was a real improvement but did not fix the underlying problem: this run *still* only completed 88/150 (58.7%) of the population — the exact same count, the exact same 88 level ids, and the exact same `workSpent`/`nodesExpanded` totals as the previous (pre-`-002`-fix) treatment attempt's partial result. The root cause is one level deeper than `-002` diagnosed: this workflow dispatches `plan-highbudget-shards.mjs` with **no `--telemetry`** (documented in the workflow's own comments — an ad-hoc id list has no standing EMA history), so *every* id gets the exact same uniform fallback prediction (`targetWallMinutes`, always, regardless of the id) — the planner cannot tell an easy level from a hard one at all. Combined with this workflow's default **non-strict** work budget (`strict_total_work_budget` defaults `false`, preserving legacy additive-tier semantics where a stage can spend well beyond its nominal share — measured 1.5x-467x overrun in `2026-08-28-additive-tier-participation-audit.md`), a level's true worst-case wall time is effectively unbounded by either `node_budget` or `work_budget` here — only the 24-hour `budget_ms` safety deadline bounds it, which no practical per-shard job timeout can accommodate. Any single-number wall-time estimate — whether based on `node_budget` (`-001`/`-002`) or `work_budget` (`-002`'s fix) — is defeated by this blindness, because bundling several unpredictable-duration levels into one shard means one slow level's shard timeout drops every other level bundled with it too, not just the slow one.
> **Remaining gate:** re-dispatch with per-level isolation (solo-shard every id, since the planner's own solo-threshold mechanism already exists and works correctly once triggered) so that a slow level's shard timeout only costs that one level's result, not its shard-mates'. See dispatch-input change below — no further workflow-code change needed, since the mechanism already exists and was simply never triggered under the default `solo_threshold_multiplier=2.5` (which is always `> 1.0`, and every id's uniform, no-telemetry prediction never exceeds `targetWallMinutes * 1.0`, so nothing was ever routed to a solo shard).
> **Evidence role:** forensic — refines `-002`'s diagnosis one layer deeper, using the same corrected-dispatch's own result as evidence that the fix was incomplete
> **Selection:** the control run's full result (not a sample of it)

## Method

Pulled `33921242910`'s (post-`-002`-fix control run) "Combine shard results" job log and found `88/88 solved` again — the same shortfall shape as `-002`'s pre-fix runs. Diffed its solved-id set and `workSpent`/`nodesExpanded` totals against `-002`'s treatment run's (`33856607156`) partial result: **identical in every digit** (same 88 ids, `work=14349987212`, `nodes=9552142678`). Given the fraction override under test only affects `admissible-order-alternate-tiebreak-retry`'s shared work pool — a late-ladder tier this corpus's real production win rate puts at only 2.9% of solves — this exact equality is explained, not suspicious: the truncated 88-level subset is dominated by levels that resolve via cheap early-ladder stages before ever reaching the tier under test, and the solver is deterministic for those paths regardless of the fraction. That in turn means the *systematic* truncation is not incidental noise — it is specifically dropping the slower, harder-to-solve levels, which correlates with exactly the population most likely to depend on late-ladder tiers like the one under test. A truncated sample built this way would be structurally biased against ever observing the effect this confirmation exists to measure, even if it looked superficially "complete" (0 recorded unsolved).

Traced why `-002`'s fix didn't help by reading `scripts/plan-highbudget-shards.mjs` directly: without a `--telemetry` argument (never passed by this workflow), `knownPredictions.length` is always 0, so **every** id receives the identical `fallbackMs = targetWallMinutes * 60_000` — the planner has no per-level signal to work with at all, independent of whether the base figure fed into it is `node_budget` or `work_budget`. `-002`'s fix changed the *size* of that uniform number but not its fundamental uniformity. Then confirmed the solo-shard escape valve exists but was never used: `soloThresholdMs = targetWallMinutes * 60_000 * soloThresholdMultiplier` (default multiplier 2.5) is always strictly greater than the uniform `fallbackMs` (multiplier 1.0 equivalent), so `predictedMsById.get(id) >= soloThresholdMs` never holds for any id under the default multiplier — nothing ever gets solo-shard treatment, and the observed shard job logs confirm typical shards packed roughly 150/38 ≈ 4 ids together.

## Interpretation

`-002`'s fix was correct as far as it went (a bigger, more honest single number for the wall-time estimate) but the real defect is structural: a *uniform* per-level estimate cannot size shard packing sensibly when actual per-level cost is this workflow's whole *research question* — variance in how long a level takes precisely because some levels depend on retry tiers others don't. Bundling multiple such levels into one shard under a single shared timeout means any one slow level silently costs its shard-mates their results too, and — because "reaches a late-ladder tier at all" and "takes a long time" are correlated — this failure mode systematically discards exactly the sub-population this line of research needs to observe. This is a more fundamental point than `-002`'s framing suggested, worth keeping distinct from it: `-002`'s fix remains directionally correct and is kept in the workflow, but it is not sufficient by itself for a no-telemetry, non-strict, advisory-only dispatch.

The fix that follows from this diagnosis does not require another workflow-code change — `plan-highbudget-shards.mjs` already has a working solo-shard mechanism, it was simply never triggered by this workflow's default inputs. Re-dispatching with `solo_threshold_multiplier=1.0` (making the uniform no-telemetry prediction, which always equals `targetWallMinutes` exactly, satisfy the solo threshold's `>=` comparison) forces every one of the 150 ids into its own dedicated shard, so a slow level's timeout can only ever cost that one level's result. Pairing this with a larger `target_wall_minutes` (40, up from the default 20 — giving each solo shard a `max(30, ceil(40*1.5)+10) = 70`-minute window instead of 40) gives genuinely slow levels a fairer chance to finish without materially changing what is being tested (production's real additive-tier semantics remain untouched; `strict_total_work_budget` is deliberately left `false` so this dispatch keeps testing the actual production-representative mode, not a hypothetical strict-cap mode).

## What this does not establish

- Does not confirm or refute the `admissible-order-alternate-tiebreak-retry` repricing question — still untested in a complete run. Disposition unchanged (default-ON, full fraction).
- Solo-sharding with a 70-minute window is still a bounded accommodation, not a guarantee — a level whose real worst-case time under non-strict additive semantics is many multiples of that (the documented 467x tail case would be many hours) would still come back missing from even this corrected dispatch. If the next attempt still shows a meaningful shortfall, the missing ids themselves (not just the count) should be checked for whether they cluster on a recognizable structural signature, since that would itself be informative about which levels this workflow's ad-hoc/no-telemetry mode cannot practically confirm at all.
- Single diagnostic pass; the fix is untested by an actual complete dispatch as of this report.

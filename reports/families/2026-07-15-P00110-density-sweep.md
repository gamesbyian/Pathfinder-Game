# Density-sweep finding: P00110 family (2026-07-15)

First real use of `scripts/family-generate.mjs --mode=density-sweep`, built specifically to test
whether the solver's two independently-chosen "is this level dense" thresholds —
`DENSE_LEVEL_NAV_DENSITY = 0.70` (`modules/solver/prep.ts`) and `POLICY.NEAR_HAMILTONIAN_DENSITY =
0.82` (`modules/solver/attempts.ts`) — actually correlate with a real behavior transition, or are
two independently hand-picked numbers with no empirical relationship to each other.

## Setup

- Parent: P00110 (10×10, reqLen 63, reqInt 4, 16 blocks), navDensity 0.747 — deliberately chosen to
  sit between the two thresholds.
- 16 siblings generated via `--mode=density-sweep --block-delta-min=-6 --block-delta-max=10`: each
  adds or removes ONLY blocks (never relocates anything), so the witness, grid, reqLen, and reqInt
  are held exactly fixed while navDensity sweeps from 0.697 to 0.849 — crossing both named
  thresholds. All 16 passed the full integrity validator (schema/structural/witness).
- Solved via `portfolio-solve-sweep.mjs --scheduler-mode=legacy` (see "Methodology correction"
  below for why `legacy`, not the tool's own default).
- Family + manifest + hints committed at `data/families/family-P00110-density.json` /
  `-manifest.json` / `data/families/hints/F00110-*.json`.
- Raw solve-result JSON for both scheduler modes committed alongside this report
  (`2026-07-15-P00110-*-solve-legacy.json`, `-solve-portfolio-experiment.json`) — reproduce via
  `node scripts/run-bundled.mjs scripts/portfolio-solve-sweep.mjs --corpus=data/families/family-P00110-density.json --scheduler-mode=legacy --budget-ms=20000 --out=<path>`
  (parent: `--corpus=data/levels.json --levels=110`), then
  `node scripts/family-analyze.mjs --manifest=data/families/family-P00110-density-manifest.json --solve-result=<path> --parent-solve-result=<parent-path>`.

## Methodology correction (worth remembering for future runs)

The first pass used `portfolio-solve-sweep.mjs`'s **default** scheduler mode
(`portfolio-experiment`) — the fixed-timed-tier experimental scheduler, not `legacy` (what
production/players actually run under). Under that default, the result was messy: no clean
transition at either threshold, high-density variants solved cheaply about half the time via an
early beam tier that doesn't consult the archetype-conditioned attempt ordering the same way
`legacy` mode does. Re-run with `--scheduler-mode=legacy` and the picture changed substantially
(see below) — **`portfolio-solve-sweep.mjs`'s default mode is the wrong tool for questions about
production solver behavior; use `--scheduler-mode=legacy` explicitly.**

**`NEAR_HAMILTONIAN_DENSITY` (0.82): real, fairly clean signal.** Every variant above 0.82
(0.827/0.838/0.849) costs 2.0–2.7M nodes — roughly double the parent's own 1.16M, and far above
every variant below 0.82 (max 1.1M, most under 100). No variant below 0.82 exceeds the parent's
cost by more than a small margin; every variant above it does, substantially.

**`DENSE_LEVEL_NAV_DENSITY` (0.70): no visible effect.** 0.697 and 0.705 (straddling it) both cost
3 nodes — indistinguishable. This constant governs a different, narrower mechanism
(`mustMaskForDFS` in `prep.ts`, not archetype/config selection), so a null result here doesn't
impugn it — it just means this family didn't exercise the code path it actually gates.

**Secondary finding, arguably more interesting than the threshold question:** the parent itself
(1.16M nodes) is dramatically more expensive than 12 of its 16 minimal single-density-step
neighbors (many solve in single-digit nodes). This is a "hostile-parent" family in
`docs/sibling-cousin-system.md`'s vocabulary (section 17) — P00110's specific arrangement is an
unusually bad draw for its own regime, not representative of typical difficulty at navDensity≈0.75.

## Caveats

- One family, one witness, one level, one grid size. This shows the 0.82 threshold isn't obviously
  *wrong* for this family and the 0.70 threshold's silence here is explained rather than damning —
  it is not yet evidence the thresholds are *right* in general. Repeating this on 2–3 more
  density-crossing families (different grid sizes, different witness geometries) before drawing any
  conclusion that changes production code.
- `nodesExpanded` is the primary signal per CLAUDE.md's own guidance (more stable than wall-clock);
  elapsed-ms mostly agrees here but is noisier at the low end (single-digit-ms overhead dominates
  sub-100-node solves).

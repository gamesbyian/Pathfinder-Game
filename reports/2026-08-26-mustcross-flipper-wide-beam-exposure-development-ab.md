The other two must-cross-heavy sibling rules' identical exposure gap (32/62 of the original mined population) remains open and unclaimed by this candidate; reopening it needs either accepting displacement of an already-validated protected config or a further `MAIN_LOOP_LATE_RESERVE_CONFIG_COUNT` increase, which this pilot deliberately did not test (a second, un-prespecified dimension).

## Confirmation attempts: `confirm-broad-003`, `confirm-broad-004`, and `confirm-residual-001` (2026-08-26, all three inconclusive, three distinct mechanisms)

### `confirm-broad-003` (256 levels)

Per the frozen candidate above, `confirm-broad-003` (256 fresh uniform-random raised-cap levels, master seed `2026082601`, id prefix `G`, sha256 `443b05e40809466aea7bd6280664e7b4ebd7cf2cd3283d6bf40970a7519b9c2d`) was generated and sealed via the new [`solver-broad-confirmation.yml`](../.github/workflows/solver-broad-confirmation.yml) workflow, then run control vs. `enable_flags=STRATEGY_MUSTCROSS_FLIPPER_WIDE_BEAM_EXPOSURE` treatment at the same `node_budget=50,000,000` envelope as development (run [`32940910715`](https://github.com/gamesbyian/Pathfinder-Game/actions/runs/32940910715), commit `36c0744a`).

**Result:** control 159/256 solved, `workSpent=29,676,406,171`; treatment 159/256 solved, `workSpent=29,676,406,171` — the identical number, not just the identical count. 0 gained, 0 lost (exact solved-id-set equality, not merely equal counts).

**This is not a normal clean null.** `confirm-broad-002`'s clean null (0/0 gains/losses) still showed real participation — treatment `workSpent` differed from control by about +0.01%, meaning the new config actually executed on some levels even though it never changed an outcome. Here, aggregate work is bit-for-bit identical across all 256 rows, which is only possible if the two new trailing configs never executed on a single row of the cohort.

**Diagnosis: repair-fallback saturation, compounding an already-low base rate.** A local calibration run of the same generator (same commit, different independent seed — not the sealed cohort itself, since regenerating with the *same* seed reproducibly does NOT reproduce the sealed artifact byte-for-byte even at the same commit, confirming [`solver-confirmation-transfer-cohort-reservation.md`](2026-08-24-solver-confirmation-transfer-cohort-reservation.md)'s own reproducibility warning — this calibration is illustrative of the generator's typical output, not a stand-in for the actual sealed rows) found `isMustCrossFlipperHeavy` *archetype-eligible* levels at roughly 5.5% prevalence (14/256). That number alone understates how rare a *participating* row is, though: eligibility for this candidate's new configs additionally requires surviving the early repair probe **and** the rule's four existing main-loop configs before ever reaching the two new trailing ones — exactly the compound condition the post-976 rejoin already measured directly, at **30 of the full 1,700-level Corpus 2** (≈1.76%), since that 30 *is* the count of current-production misses matching this rule. At that measured rate, `P(zero participating rows | n=256, p=0.0176) ≈ e^(-256×0.0176) ≈ 1.1%` — unlikely, and consistent with the mechanism below, but not literally impossible by chance alone; this run cannot rule out an unlucky draw on top of the structural effect. The mechanism itself is independently well-supported regardless: `attempts.ts`'s own comment on this rule notes `isMustCrossFlipperHeavy`'s gate (`mustCross≥2`, `mustPass≥OBJECTIVE_HEAVY_MUSTPASS=3`) is a strict superset of `needsRepairFallback`'s gate (`REPAIR_MC_MIN=2`, `REPAIR_MP_MIN=3`) — **every** eligible level also qualifies for the early repair probe, which "now solves nearly everything in this archetype via its own early probe before this main loop even runs."

The development population was not a fresh sample — it was drawn from Corpus 2's **already-known current production misses** (the post-976 rejoin's residual failure set), i.e. exactly that measured ≈1.76% repair-resistant tail. Every development-eligible row was, by construction, a participating row. A fresh uniform-random cohort is not: at ≈1.76% true prevalence, `confirm-broad-003`'s 256 rows were simply not enough to reliably contain any.

**Consequence for the confirmation protocol.** This is a structural gap in using a plain broad/fresh cohort to confirm a candidate whose entire premise is "helps solve levels that already survive the whole current ladder including repair" — which describes essentially every candidate mined from Priority 1's residual-miss analyses, not just this one. `confirm-broad-001` and `confirm-broad-002`'s candidates evidently had reachable participation on fresh cohorts (small but nonzero `workSpent` deltas even in their clean nulls) and so were not affected the same way, but a future residual-mined candidate could hit the identical wall. Two concrete fixes:

1. a much larger fresh cohort, now directly sizeable from the measured ≈1.76% rate rather than guessed — e.g. `count≈1,200` puts the expected participating-row count around 21, the same order as development's own 30-row population; or
2. a two-phase "control-failure residual" cohort: generate a large fresh pool, run the *control* ladder alone across it, freeze the subset it fails to solve (mirroring exactly how the original 724-level Corpus-2 residual population was defined, just on fresh generated levels instead of the existing corpus), then run both arms only on that frozen residual — still a legitimate pre-outcome-neutral selection rule (filtering by whether *control* solves it, decided before either arm's real comparison run, is not the same as selecting by whether *treatment* solves it).

Option 1 is simpler and immediately actionable now that the rate is measured; option 2 remains available if a future candidate's true rate turns out lower still or option 1's cohort proves under-powered in practice.

`confirm-broad-003` is spent (one-use, already inspected) but its verdict is **inconclusive/non-participating**, not a negative confirmation. The candidate remains at "development-positive, awaiting a confirmation design that can actually exercise it." Do not promote `STRATEGY_MUSTCROSS_FLIPPER_WIDE_BEAM_EXPOSURE` to default-on on the strength of this run, and do not close it as a confirmed negative either — per the research operating model's own rule, absence of a solve gain when participation is near zero is not evidence of no mechanism.

### `confirm-broad-004` (1,200 levels — option 1, sized from the measured rate)

**Result:** control 674/1,200 solved, `workSpent=149,686,882,168`; treatment 674/1,200 solved, `workSpent=149,686,882,168` — bit-for-bit identical again. 0 gained, 0 lost.

At the measured 1.76% base rate, `count=1,200` was sized for an expected ≈21 participating rows. `P(zero participating rows | n=1,200, p=0.0176) ≈ e^(-1,200×0.0176) ≈ 7×10⁻¹⁰`. Two consecutive byte-identical results is unusual enough to first rule out a wiring regression rather than accept "the base rate is even lower than thought" at face value. | treatment | `STRATEGY_MUSTCROSS_FLIPPER_WIDE_BEAM_EXPOSURE` | **3/3** |

The flag mechanism is confirmed intact and functioning as designed — the byte-identical broad-cohort results are not a bug, they are a genuine, severe sampling gap between Corpus 2's naturally-occurring repair-resistant population and what this generator's raised-cap stratum produces.

### Next step: two-phase control-failure-residual design

Per the contingency already specified above, scaling `count` a third time is not the prescribed response to a decisive (not marginal) zero-participation result. The next step is option 2: generate a fresh pool, run the *control* ladder alone across it, freeze the subset it fails to solve (this control-failure population, unlike raw archetype eligibility, requires no separate rate estimate — it is directly the fresh-generated analogue of Corpus 2's own 724-level current-miss residual that produced this candidate in the first place), then run both arms only on that frozen residual.

### `confirm-residual-001` (520-level control-failure residual — a second, distinct non-participation mechanism)

Built and dispatched via the new [`solver-residual-confirmation.yml`](../.github/workflows/solver-residual-confirmation.yml) workflow: phase 1 generated a fresh 1,200-level pool (master seed `2026082701`, id prefix `J`, sha256 `352aa29229c80db9be58ed941b4e86c3fff68973d8e8243c3b44e5753230214d`) and ran the *control* ladder alone across it; control solved 680/1,200, leaving a 520-level control-failure residual (sha256 `fae1b9f05199bc2219deddcd44f85b12f919365f3ce977bd15bba03c48051e5b`); phase 2 ran control vs. `enable_flags=STRATEGY_MUSTCROSS_FLIPPER_WIDE_BEAM_EXPOSURE` treatment on that frozen 520-level residual, same `node_budget=50,000,000` envelope (run [`32979222722`](https://github.com/gamesbyian/Pathfinder-Game/actions/runs/32979222722), commit `ca3f18af1d2d2e8e9ba6e5b8e90e38fff131b1b5`).

**Result:** control 0/520 solved, `workSpent=123,835,203,269`; treatment 0/520 solved, `workSpent=123,835,203,269` — bit-for-bit identical yet again. 0 gained, 0 lost.

**This time the population genuinely contains eligible participants — and the identical-work result is not a repeat of the repair-fallback-saturation diagnosis.** A one-off audit (`scripts/stress/confirm-residual-001-archetype-audit.mjs`, built specifically to answer this) computed `isMustCrossFlipperHeavy` directly against the sealed pool and phase-1 report, using the real production `extractFeatures`/`isMustCrossFlipperHeavy` functions (exported from `attempts.ts` for exactly this purpose, eliminating any reimplementation drift): **60/1,200 (5.00%) of the pool is archetype-eligible, of which 35 were solved by control and 25 are in the residual** — a substantial, real population, on the same order as the original 30-row development population, not the near-zero draw that plagued `confirm-broad-003`/`004`. Raw-vs-mechanics-only-reduced classification was also checked directly (the level-blind sweep strips each level to a fixed field set before solving) and found **zero mismatches across all 1,200 pool levels** — the archetype gate itself is not the problem.

Yet every one of the 25 archetype-eligible-and-residual rows shows **zero attempts of the new candidate configs** in the treatment arm's own recorded attempt list, despite running 25-26 total attempts each. Calling the real `getConfiguredAttemptConfigs(level, {STRATEGY_MUSTCROSS_FLIPPER_WIDE_BEAM_EXPOSURE: true})` directly against one such row (`J00035`: `arch=must-cross-heavy, mustPass=6, flippers=7` — well clear of the `mustPass≥3`/`flippers≥2` thresholds) **confirms the config list itself is correct**: it includes both new plain WIDE beam configs at positions 5-6, in the identical shape verified against a known-working Corpus-2 level (`R00817`) moments earlier. The bug is not in classification or config generation — it is somewhere in scheduling. `J00035`'s actual recorded attempt sequence shows exactly 4 `main-loop`-stage attempts (matching the rule's base list) before the stage transitions straight to `repair-fallback`, never reaching the two new trailing configs, even though `MAIN_LOOP_LATE_RESERVE_CONFIG_COUNT` (5, `stage-budget.ts`) is specifically designed to guarantee the trailing 5 of a rule's config list get attempted. Each row's actual `nodesExpanded` (~225,000,000, e.g. `J00035`'s 225,000,125) vastly exceeds the run's nominal `node_budget` (50,000,000) — a ~4.5x overshoot, consistent with the sweep's default "legacy additive-pass" (non-strict) budget semantics rather than a hard per-level ceiling (confirmed separately: `Strict total work ceiling: no` appears in every local sweep summary this session that didn't pass `--strict-total-work-budget`, which this workflow never does). The working hypothesis — not yet traced to a specific line of `stage-budget.ts`'s reserve arithmetic, so stated as a hypothesis, not a proven root cause — is that the late-reserve guarantee is computed as a fraction/ceiling relative to the *nominal* budget and does not survive intact once actual consumption overshoots that nominal figure by this much, on every level in this specific population uniformly (all 25 rows show the identical 4-of-6 truncation pattern, ruling out a level-specific fluke).

**This is a second, independently discovered non-participation mechanism, distinct from `confirm-broad-003`/`004`'s repair-fallback saturation.** That first mechanism was "repair solves the level before the new configs ever get a turn" — ruled out here by construction, since every residual row is a control-failure (repair does not solve it, full stop). This new mechanism is instead "the whole ladder's actual resource consumption so overshoots its nominal budget that even a config explicitly protected by a late-reserve mechanism never gets attempted." The two-phase design successfully solved the problem it was built for and then surfaced a second, previously-unknown scheduling gap in its place — evidence that this rule's very-high-difficulty archetype-eligible population (both the naturally-occurring Corpus-2 kind and this freshly-generated kind) is unusually prone to exactly the kind of extreme per-level resource consumption that breaks assumptions elsewhere in the scheduling stack.

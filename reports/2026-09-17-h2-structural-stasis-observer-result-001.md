# H2 structural-stasis observer result 001

> **Status:** concluded-negative
> **Last evidence:** 2026-09-17 — offline re-analysis of two already-committed matched-work repair-elite censuses (30,000 and 300,000 node budgets), current HEAD, zero new solver compute.
> **Decision:** H2's premise ("canonical work can continue increasing after a search action has stopped buying materially new structural information") is **not supported as a predictive signal** on this population. Two compact, cheap-to-observe within-run stasis signals — how early in a 30k-node run the best badness stopped improving, and how many distinct badness values a run's sampled elites showed — both fail to predict whether a fresh, 10x-larger-budget (300k-node) run finds materially better badness: correlation is indistinguishable from zero on the 14-level dev sample (r=-0.16, r=-0.04) and on the untouched 14-level confirmation sample (r=+0.02, r=+0.06). This is not a case of "no signal to find" from lack of variance in the outcome: 22/28 levels (78.6%) *did* find strictly better badness with 10x more work (mean improvement 4.96 badness points), so there is real marginal value to predict — the tested stasis signals simply do not track it.
> **Remaining gate:** none for these two specific signal formulations. Per H2's own advancement bar ("a positive result can earn an allocation/continuation premise... it does not authorize generic restart, early termination, bandits, or dynamic scheduling without a matched-work counterfactual"), this closes early-stasis-fraction and distinct-badness-count as allocation signals on this population; it does not test other structural-response dimensions from H2's candidate list (mechanic-progress/obligation-order signature, canonical state-family/branch-decision signature) or other populations.
> **Evidence role:** discovery/confirmation over an already-committed population. The 30k/300k censuses and the dev/confirmation split were already fixed by an earlier, unrelated program (`reports/2026-09-11-repair-side-first-loss-exposure-001.md` and its two source phenotyping/confirmation reports); this report only computes new derived signals from already-recorded per-elite `(arrivalNodes, badness)` pairs and correlates them against an already-implicit marginal-outcome contrast (best badness at 30k vs. at 300k). No new labelling, no new solver compute, no new selection pressure on which levels to include.
> **Population identity:** the same 28-level first-loss-frontier population as the Sept exposure report (`reports/stress/first-loss-frontier-repair-rollback-census-001.json` at 30k, `...-300k-001.json` at 300k), reused unmodified. Its own dev(14)/confirmation(14) split is reused unmodified: dev ids from `reports/2026-09-11-bounded-class4-class5-first-loss-phenotyping-001.md`, confirmation ids from `reports/2026-09-11-ws2-independent-first-loss-confirmation-001.md`.
> **Selection history:** both censuses were generated once, at two fixed node budgets, specifically to test "inadequate work" vs. "genuine exposure limit" for a different question (natural-exposure common-prefix depth, not badness-based information velocity). This report adds no new selection pressure — it recomputes different derived quantities (badness-based best-so-far curves, distinct-badness counts) from the same already-recorded per-elite rows.
> **Inference scope:** this establishes that two specific, cheaply-observable within-run stasis signals do not predict the marginal value of a 10x work escalation on this population, using badness (a finer-grained continuous proxy) rather than the coarser common-prefix-depth metric the Sept report used for its own (different) question. It does not test other stasis-signal formulations, other repair-stage populations, or the mechanic-progress/canonical-state-family dimensions H2's own candidate list also names.

## Why this ran

`reports/2026-09-16-class5-cross-resource-hypothesis-harvest-001.md` names H2 as a bounded next-in-order composition/allocation premise (queue item 5 in `docs/solver-optimization-workstreams.md`, after H1/DEAD-core/H3). Its "smallest falsifying observer" calls for compact, legal, checkpointed summaries of newly-reached search structure at prespecified `workSpent` points, with the quantity of interest being "new decision-relevant structural response per unit of additional `workSpent`, joined to marginal outcome." A scoping pass found no committed artifact with fine-grained prespecified-checkpoint telemetry (`PF_REPAIR_SIGNATURE_DEBUG` output was never saved as raw JSON), but did find that the Sept first-loss exposure program's two matched-work censuses (30k/300k node budgets, same 28 levels, same harness) already record `(arrivalNodes, badness)` pairs for ~5 sampled elites per level per budget — exactly the "(work, structural-response)" pairs H2 asks for, just coarser (5 samples, clustered by arrival rather than evenly spaced) than an ideal prespecified-checkpoint design. Reusing this avoids the GHA-offload lesson learned earlier this session (favor reuse of already-committed evidence over new compute when the existing artifact is adequate) and directly inherits a genuine dev/confirmation split already earned by an unrelated program, satisfying H2's own "independent rows" requirement for free.

## What was implemented

**`scripts/stress/h2-structural-stasis-observer.mjs`**: loads both already-committed censuses, and for each of the 28 levels computes two compact within-run stasis signals from the 30k run alone (observable before ever paying for the 300k run): `stasisFraction` (1 minus the fraction of the 30k budget elapsed before the best-badness elite arrived — high means the run "went stale" early) and `distinctBadness` (count of distinct badness values across the run's ~5 sampled elites, a raw structural-novelty-count proxy). It then computes the marginal outcome — `delta = best30 - best300`, whether a fresh unmodified 300k run found strictly better badness than the 30k run — and correlates each signal against `delta`, reporting separately for the dev and confirmation splits.

## Result

| Split | n | Levels improved at 300k | Mean badness delta | corr(stasisFraction, delta) | corr(distinctBadness, delta) |
|---|---:|---:|---:|---:|---:|
| Dev | 14 | 10/14 (71.4%) | 3.79 | -0.16 | -0.04 |
| Confirmation | 14 | 12/14 (85.7%) | 6.14 | +0.02 | +0.06 |
| All | 28 | 22/28 (78.6%) | 4.96 | -0.04 | -0.01 |

Both correlations are near zero and inconsistent in sign between dev and confirmation — neither signal shows a real, reproducible relationship to marginal value on the independent confirmation half.

## Interpretation

The premise that "work can keep increasing after a stage stops buying new structure" is not falsified in general by this result — it is the specific, testable claim that a *compact, cheaply observable, within-run* stasis signal *predicts* that outcome which fails here. In fact the opposite pattern dominates: on 78.6% of levels, a 10x larger repair-restart budget bought a real (if modest, mean ~5 points) badness improvement, meaning marginal value is common, not rare, once measured on a continuous scale rather than commonPrefixSteps' coarser resolution (see "Relation to existing evidence" below). Whatever determines which levels get that marginal payoff, it is not visible in either how early the cheap run's own best badness stopped improving or how many distinct badness values that cheap run's small elite sample showed.

## What survives

Nothing from this pass is preserved as a positive or partial signal — both candidate stasis formulations are genuinely uninformative here, not weakly informative. The badness-based marginal-improvement finding itself (78.6% of levels gain from 10x work, mean ~5 badness points) is preserved as capability-memory context for future repair-allocation questions, but it argues against rather than for an early-stasis-based allocation rule on this population.

## Relation to existing evidence

This does not reopen or contradict `reports/2026-09-11-repair-side-first-loss-exposure-001.md`'s own conclusion (10x work bought zero improvement in common-prefix depth on 26/28 levels) — that report measured a coarser, more discrete metric (longest common prefix against a *known-live* trajectory) for a different question (natural exposure to known-solution states), while this report measures continuous badness (a general structural-deficit proxy, `computeBadness`/`structuralDeficit` in `modules/solver/solution.ts`) for a different question (information velocity/stasis). Both are simultaneously true: repair's natural search almost never gets measurably closer to a *specific known-live trajectory* with more work, while it does often find a *lower-badness* (less structurally deficient, but differently-shaped) elite somewhere else. Neither finding licenses a production allocation change; per H2's own advancement bar, only a signal that predicts near-zero marginal value on independent rows would, and neither tested signal does.

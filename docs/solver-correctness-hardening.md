# Solver correctness hardening reference

> **Status:** current invariants distilled from fixed correctness failures.
> **History:** [`archive/snapshots/solver-correctness-archaeology-2026-08-20.md`](archive/snapshots/solver-correctness-archaeology-2026-08-20.md).

Use when changing hard prunes, state identity, solver/runtime rules, reusable scratch, budgets, experiment plumbing, or persisted telemetry. This is a review checklist, not a defect list; current optimization work is in [`solver-optimization-workstreams.md`](solver-optimization-workstreams.md). The August 2026 hardening pass found no newly demonstrated production hard prune rejecting a valid solution.

## Standing failure classes

| # | Failure class | Required invariant |
|---:|---|---|
| 1 | Incomplete future-state identity | Cache/memo/`seen`/dedup/dominance/signature equivalence includes every property affecting future legality, constraints, or cached value. Add counterexamples varying omitted fields. |
| 2 | Sentinel / packing / representation drift | Decode documented contracts, not remembered sentinels. Fixed-width packing needs enforced cardinality proof across producers/consumers; audit consumers when caps change. |
| 3 | Reusable scratch lifecycle leakage | Test heterogeneous call sequences, capacity boundaries, shifted regions, reset assumptions, nesting, and generation-counter rollover where relevant. |
| 4 | Approximation in the wrong direction | Hard-prune approximations declare allowed error direction. Lower bounds may be low, never high; reachability over-approximations may admit impossible states, never exclude possible ones; deadness tests may miss dead states, never invent them. |
| 5 | Heuristic evidence promoted to proof | Correlation, witness regularity, score preference, or intuition cannot become a hard reject without rule-derived proof and counterexample-oriented validation. |
| 6 | Independent rule implementations drift | Preserve useful independence among live/domain rules, referee, solver transitions, and reference oracle; differentially test move legality and final acceptance. New mechanics reach every arbiter/fixture. |
| 7 | Pre-move / post-move state confusion | Search/scoring APIs state whether candidate state is already applied. Check this before porting quantities among DFS/beam/repair. |
| 8 | Programming failure becomes a plausible mathematical value | Distinguish failed computation from legitimate `Infinity`, unreachable, empty, or infeasible values; assert finite/defined values where required. |
| 9 | Configuration/default propagation | Extend canonical ablation normalization and opt-in registry; do not create a second sparse-default system. Test default-on and default-off polarity. |
| 10 | Nested budget/resource semantics | Budget boundaries state absolute vs remaining, per-attempt vs cumulative, allocation currency vs deadline, and whether additive passes share the envelope. Test zero/tiny/boundary/infinite cases. |
| 11 | Telemetry/provenance projection drift | Persisted telemetry is scientific correctness. Shared projections and maximal round-trip fixtures must fail when persistent fields are dropped. |
| 12 | Exceptions/errors converted into ordinary negatives | Keep exhaustion, timeout/deadline truncation, unsupported input, execution error, and genuine no-solution evidence distinct through workers/reports/artifacts. |
| 13 | Workflow/ref/SHA/checkpoint staleness | Serious results record measured SHA/ref and corpus/config identity at the worker boundary. Resume identity includes every meaning-changing setting. |
| 14 | Incomplete or contaminated populations | Combine steps assert expected coverage. Partial/missing/stale shards are labelled partial or rejected, never silently treated as regression evidence. |
| 15 | External-model validation in only one direction | Validate real witnesses in the model and model witnesses with the real referee; include a positive search control. UNSAT/proof claims require explicit approximation-direction reasoning. |
| 16 | Identifier/namespace ambiguity | Corpus identity is part of level identity for files, caches, reports, checkpoints, and cross-corpus analysis. Reuse shared selectors/parsers. |
| 17 | Stale documentation | Current behavior belongs in current contracts/queues; reports/snapshots preserve evidence. Update/archive status when implementation or promotion state changes. |
| 18 | Unmodelled stage-history dependence | Given the same explicit level/action/config/seed and deterministic work budget, unrelated predecessor stages must not silently change search semantics, ordering, randomness, or capability. Any intended handoff must be explicit typed action state. Cache warming may change wall cost only unless a different contract is documented. Add fresh-vs-preceded differential tests for affected stages before treating sequence effects as causal evidence. |

## Closed correctness defect: 31-32 flipping-filter beam identity (fixed 2026-09-02)

`validateRawLevel` permits up to 32 flipping filters because `flipperUsedMask` legitimately uses all 32 int32 bits. The underlying transition state is sound at that boundary: bit 31 is a negative signed int32 value but nonzero membership checks, `popcount`, apply, and undo handle it correctly; `flipper-cardinality.test.ts` pins that behavior.

Beam's numeric state-identity fast path did **not** previously share that full-domain guarantee. `search.ts` derived `_flipperBase` as `1 << prep.flipperKeys.length`. JavaScript bitwise shifts are int32: at 31 filters this became `-2147483648`, and at 32 the shift count wrapped so it became `1`. `flipperUsedMask` itself is also signed when bit 31 is set. The mixed-radix coarse-state key and mechanic-bucket-retention `(mustCrossMask, flipperUsedMask)` bucket encoding were therefore not collision-free on schema-valid 31/32-filter levels even though their comments claimed cardinality-derived exactness.

Fixed by following the required repair exactly:

1. `_flipperBase` now derives the radix arithmetically (`2 ** flipperCount`), never with a bitwise shift;
2. every numeric composition normalizes the 32-bit flipper mask to its unsigned value (`c.flipperUsedMask >>> 0`) first;
3. the existing safe-integer overflow fallback to the exact delimited-string representation (`beamStateKey`) is unchanged and untouched by this fix;
4. `search.test.ts` adds four 31/32-filter counterexamples (two per numeric key: `_mechanicBucketSelect` and the newly-extracted, directly-testable `_composeBeamNumericCoarseStateKey`) that each pin the OLD formula's real aliasing before proving the fixed formula keeps the states distinct;
5. the ordinary small-cardinality numeric path is unchanged: `2 ** n === 1 << n` bit-for-bit for every `n <= 30`, confirmed byte-identical (160/160 solved, identical node count) on the full published-corpus regression.

This was a representation correctness bug, not evidence that any existing corpus result was wrong: no affected production/corpus population was ever established, and the published corpus (which has no 31/32-flipping-filter levels) is unaffected either way. See [`../reports/2026-09-02-beam-31-32-flipper-filter-identity-fix.md`](../reports/2026-09-02-beam-31-32-flipper-filter-identity-fix.md) for the full account.

## Closed correctness defect: raced-solve SolveOpts silently dropped (fixed 2026-09-09)

2026-09-09 historical regression-risk audit (bug family #10/#11/#13 above: nested budget semantics, telemetry/provenance drift, staleness of a worker-boundary's recorded config): `scripts/portfolio-solve-sweep.mjs` and `scripts/portfolio-solve-sweep-worker.mjs` each hand-reconstructed a subset of `SolveOpts` at their own `createRacePool().solveLevel()` call site to dispatch under `--race-pool-size`/worker racing. `scripts/solver-parallel/race.mjs` reimplements only `main-search` + `repair-fallback` + `goal-attraction-disabled-retry` (its own `RACE_SUPPORTED_STAGE_IDS`) and has no `nodeBudget`/`workBudget`/static-portfolio/admissible-order/main-search-late-reserve concept at all — a field outside that reimplemented subset simply had no reader in `race.mjs`, so a caller who passed it (via `--node-budget`, `--work-budget`, `--admissible-order-*`, `--main-search-late-reserve-*`, or `--disable-extra-budget-passes`) got it silently ignored under racing. Two of those (`--node-budget`, the admissible-order fractions) at least printed a `console.error` warning and continued; `--work-budget` and the main-search-late-reserve overrides had **no** warning at all. Every affected sweep's own `--out` report still recorded the *requested* `nodeBudget`/`workBudget` unconditionally, so a combined report or A/B artifact from a raced run could describe a budget that was never actually enforced.

A sibling instance of the identical class was found and fixed in the same pass: `scripts/stress/benchmark.mjs`'s raced dispatch (the tool's *default* engine) threaded `--work-budget` straight into `racePool.solveLevel()` too (with an accidental duplicate-line copy-paste of the same spread on top of it) even though this file's own header comment promises `--work-budget` makes a run's solved set reproducible — silently false under the default engine.

Fixed by introducing one canonical typed transport boundary, `scripts/solver-parallel/race-opts.mjs`'s `toRaceLevelOpts(solveOpts)`: an explicit allowlist of the exact `SolveOpts` fields `race.mjs` consumes (`timeBudgetMs`, `ablation`, `repairAdditiveBudgetMultiplierOverride`, `goalAttractionDisabledRetryBudgetFractionOverride`/its legacy alias), plus an explicit "implied-constant, not silently dropped" allowance for `schedulerMode` (validated elsewhere as always `'production'` before racing is attempted). Any other field present with a defined value now **throws** — every one of `scripts/portfolio-solve-sweep.mjs` (single-worker inline path, validated once up front against the whole run's shared `solveOpts` before any level dispatches), `scripts/portfolio-solve-sweep-worker.mjs` (forked-worker path), and `scripts/stress/benchmark.mjs` (validated once up front, matching the CLI's default-raced-engine behavior) now dispatch through this one function instead of independent hand-picked literals. `scripts/portfolio-solve-sweep.mjs`'s own `--out` report now records `engine` (`'raced'`/`'sequential'`) and `racePoolSize` alongside `nodeBudget`/`workBudget`, so a reader can tell whether those budgets were the run's actual effective configuration (sequential) or are structurally guaranteed `null` (raced — the up-front validation refuses to combine racing with either option at all, so a raced report can never again claim an unenforced budget).

Regression coverage: `scripts/portfolio-solve-sweep-worker-node-test.mjs` gained a test asserting both raced call sites dispatch through `toRaceLevelOpts` (replacing a narrower test that only grepped for one hardcoded field name at each site) and a direct unit test of `toRaceLevelOpts` itself covering the reject-workBudget, reject-nodeBudget, reject-non-production-schedulerMode, and accept-supported-fields-only cases. See `scripts/solver-parallel/race-opts.mjs` for the full transport contract and its own header comment.

## Closed correctness defect: provenanceEventIdentity() property-order fragility (fixed 2026-09-09)

2026-09-09 historical regression-risk audit (bug family #11 above: telemetry/provenance projection drift). `scripts/hint-provenance-identity.mjs`'s `provenanceEventIdentity()` — the single shared definition of "what makes two provenance entries the same discovery event", used identically by `scripts/hint-capture-lib.mjs`'s write-time duplicate guard and `scripts/dedupe-hint-provenance.mjs`'s cleanup pass — built its identity string with plain `JSON.stringify()` after stripping the deliberately-excluded host/wall-clock fields. `JSON.stringify` preserves each object's own key insertion order, so two entries that are semantically identical discovery events could hash to two different identity strings purely because they were built with the same fields in a different order (e.g. a freshly constructed `makeProvenanceEntry()` object vs. a legacy record round-tripped through `upgradeProvenanceEntry()`'s `{ ...raw, solver, search }` spread pattern, or any producer/library that happens to serialize keys differently) — silently defeating the duplicate guard both consumers rely on this function to share exactly.

Fixed by adding a recursive `stableStringify()` that sorts every plain object's own keys at every nesting level (`solver.forcing` included) while preserving array element order (array order is semantically meaningful here — e.g. `forcingDisabledFeatures`), then serializing through it instead of raw `JSON.stringify`. `scripts/hint-provenance-identity-node-test.mjs` (new, wired into `test:node` as `test:hint-provenance-identity`) adversarially covers: whole-object and nested-object reverse-key-order permutations, a legacy-round-trip-shaped rebuild, that the deliberately-excluded fields (`foundAt`, `elapsedMs`, the cumulative fields, `budgetMs`) still do not affect identity, that a genuinely different discovery (`nodesExpanded`) or commit (`solver.version`, deliberately not excluded) still produces a different identity, and non-object/missing-`search` edge cases.

## Closed correctness defect: unenforced BeamContinuation ownership (fixed 2026-09-09)

2026-09-09 historical regression-risk audit (bug family #18 above: unmodelled stage-history dependence, and #10: nested budget/resource semantics). `search.ts`'s `BeamContinuation` (the `resumeFrom`/`pauseAfterPhases`/`captureContinuationOnBudgetExit` research mechanism, docs/solver-search-resumability.md) carries the actual LIVE mutable `ws`/`liveUndo` objects a paused call was using — its own header comment already required "only `startKey`/`level`/`prep` must stay the same instance" for a resume to be valid, since reusing them against a different level/prep would replay moves against the wrong grid or double/under-charge the wrong `prep._workMeter`. Nothing enforced that requirement at runtime: a caller passing a continuation captured against a different `startKey`/`level`/`prep` would silently corrupt the resumed search's state and work accounting rather than failing immediately — the exact "misuse corrupts an experiment plausibly" risk this class of bug produces. Auditing every current in-repo call site (the beam-resumability/policy-switch/staged-three-policy/alternating-policy-schedule pilots and the vitest suite) found all of them already pass a consistent `startKey`/`level`/`prep` — except two tests in `beam-resumability-pilot.test.ts` that resumed a synthetic continuation against a freshly-`prepLevel()`'d `prep`, approximating a work-cap threshold via the ORIGINAL prep's `nodesExpandedTotal` (a node count) rather than the resumed prep's own `_workMeter.units` (a different metric) purely because a fresh prep starts both at effectively zero — itself a latent instance of this exact bug shape that the new assertion catches.

Fixed by adding explicit reference-identity sentinels to `BeamContinuation` (`_ownerStartKey`/`_ownerLevel`/`_ownerPrep`, set once by a shared `captureBeamContinuation()` builder at both capture sites) and a `assertBeamContinuationOwnership()` check at the top of any `resumeFrom` call, throwing a descriptive error naming exactly which of the three mismatched rather than silently proceeding. The two latent-bug tests were fixed to reuse the same `prep` they captured against, sizing their work-cap headroom off that prep's own current `_workMeter.units` (strictly more correct than the old node-count approximation, not just a workaround). Three new adversarial tests in `beam-resumability-pilot.test.ts` prove the assertion actually fires for each of the three possible mismatches (different `prep`, different `level`, different `startKey`).

## Closed gap: check-workflow-actions.mjs did not catch dead workflow_dispatch inputs (fixed 2026-09-09)

2026-09-09 historical regression-risk audit item #6 asked for a review of `check-workflow-actions.mjs` and `check-solveopts-transport-parity.mjs` for semantic blind spots, improving only where a cheap durable guard catches the actual historical bug shape (explicitly not a brittle mega-checker).

`check-workflow-actions.mjs` validated action versions, literal path filters, and local script entrypoints all exist, but never checked whether a declared `workflow_dispatch.inputs.*` is actually consumed anywhere in the same workflow — exactly the "workflow inputs that do not reach execution" shape the same audit's item #2 calls out (a `node_budget_advisory_only`/`strict_total_work_budget`-shaped input accepted by the dispatch form but never read by any step would previously pass silently). Added `extractDispatchInputNames()` (indentation-based, no new YAML dependency, matching this file's existing regex approach) plus a per-workflow check that every declared input name appears at least once elsewhere as `inputs.<name>` or `github.event.inputs.<name>`. Same coarse, whole-file-co-occurrence scope as `check-solveopts-transport-parity.mjs`'s own documented limits (cannot prove the referencing step is the *right* consumer, or that the value survives correctly once read — indirect consumption via an intermediate `env:` alias is an accepted false-negative, never a false positive): cheap and mechanical, catching a forgotten input by name, not proving full wiring correctness. Verified against the real repo (all 28 current workflows pass with zero dead inputs) and against a synthetic fixture workflow with one genuinely-dead input (caught correctly).

`check-solveopts-transport-parity.mjs`'s own documented scope (canonical/legacy override-field co-occurrence, not full transport-object completeness) was left unchanged: the deeper "hand-reconstructed SolveOpts subset" bug shape it cannot catch is the one item #1's `toRaceLevelOpts()` fix (see the raced-solve closed-defect entry above) addresses structurally, by removing the per-call-site hand-reconstruction entirely rather than trying to check it after the fact — the stronger fix for that specific shape, and out of scope for this checker to duplicate.

## Closed research-integrity risk: unbounded advisory-node-budget timeout sizing (fixed 2026-09-09)

2026-09-09 historical regression-risk audit item #3 (bug family #10 above: nested budget/resource semantics). `.github/workflows/solver-level-blind-targeted-sweep.yml` (the only workflow carrying both `node_budget_advisory_only` and `strict_total_work_budget` as independent dispatch inputs — the other six workflows referencing `strict_total_work_budget` have no advisory-node-budget concept at all, and always pass `--node-budget` as a genuine hard ceiling) legally allowed `node_budget_advisory_only=true` together with the default `strict_total_work_budget=false`. With `node_budget_advisory_only=true`, `--node-budget` is never passed to the solve at all (`nodeBudgetReached` can never bind), so `work_budget` becomes the sole nominal constraint — but with `strict_total_work_budget` left at its default `false`, `work_budget` is only a STARTING allocation: additive fallback/retry tiers can spend 1.5x-467x beyond it (measured, `reports/2026-08-28-additive-tier-participation-audit.md`). `scripts/plan-highbudget-shards.mjs` sizes each shard's job `timeoutMinutes` from that same nominal work-budget-derived EMA estimate with only a flat 1.5x safety margin — nowhere near enough headroom for the measured worst-case multiplier — so this combination recreates the exact timeout/selective-censoring mechanism found during the admissible-order confirmation work: some levels get killed by the GitHub Actions job timeout non-uniformly (biased toward levels that actually need the additive tiers), which looks like ordinary "unsolved" solver evidence but is really wall-clock censoring.

Fixed by rejecting the dangerous combination outright: a new early step in the workflow's `plan` job (`Reject the advisory-node-budget / non-strict-work-budget combination`) fails the dispatch with an explanatory message before any planning or solving happens if `node_budget_advisory_only=true` and `strict_total_work_budget != true`. A caller needing `node_budget_advisory_only` for its own documented purpose (isolating a work-budget-share comparison) must also pass `strict_total_work_budget=true`, which makes `work_budget` an actual whole-solve ceiling and makes the planner's timeout estimate bounding again. Both inputs' own descriptions were updated to state this requirement up front. Sibling workflows carrying `strict_total_work_budget` alone (no advisory-node-budget input) were checked and confirmed not to have this combination available at all.

## Added: effective-configuration contract for decision-bearing solver runs (2026-09-09)

2026-09-09 historical regression-risk audit item #2. `scripts/combine-solver-sweep-reports.mjs` already had real, tested shard-agreement machinery (`EXECUTION_CONFIG_FIELDS`, a hard-fail check for `budgetMs`/`corpus`/`schedulerMode`, and a deliberate `distinct()`-based mechanism specifically for `nodeBudget`/`workBudget`/`repairBudgetFraction` that records legitimate per-shard variation — e.g. adaptive baseline budgets — as a recorded set rather than erasing or throwing) — confirmed by running its existing test suite before assuming a gap and nearly introducing a regression (an initial attempt to add `nodeBudget`/`workBudget` to the hard-fail list broke the very test asserting that deliberate per-shard variation is supposed to be tolerated and recorded, not rejected; reverted once the existing design was understood). That existing machinery has no way to compare TWO SEPARATE runs (a control dispatch and a treatment dispatch) against each other at all — it only ever combines shards belonging to one arm.

Added the actual missing piece: `scripts/level-blind-capability-sweep.mjs`'s report now emits `summary.effectiveConfig`/`summary.effectiveConfigDigest`, computed from the literal `solveOpts` object handed to `Solver.solveLevel()` (the actual execution boundary) plus the corpus's own content hash — not re-derived from argv, so a bug causing `solveOpts` to diverge from apparent CLI intent still shows up. New `scripts/check-effective-config-agreement.mjs` consumes this in two modes: `--mode=agree` (every shard/report in one arm must share the identical effective configuration — catches a shard silently receiving different flags than its siblings, which population-identity checks like `validate-solver-sweep-integrity.mjs` cannot see, since they only check WHICH levels ran, not WHAT CONFIG) and `--mode=compare --control=... --treatment=... --allowed-diff=field1,field2 [--require-actual-diff=true]` (a control/treatment pair must differ ONLY in the caller's prespecified dimensions, and — with `--require-actual-diff` — must actually differ in at least one of them, catching the "control-vs-control" dispatch mistake where two arms end up identical). Verified end-to-end against real solver output (two identical dispatches agree; one with `--enable-flags` differs correctly and only in `ablation`) and with 8 unit tests (`scripts/check-effective-config-agreement-node-test.mjs`, wired into `test:node` as `test:effective-config-agreement`) covering both modes' pass/fail paths. Deliberately scoped narrowly (same "coarse mechanical check, not a completeness prover" caveat as `check-solveopts-transport-parity.mjs`): this is a standalone tool for ad hoc A/B analysis, not force-wired into every existing workflow — `solver-level-blind-targeted-sweep.yml`'s shards were independently confirmed (by reading the workflow) to already receive identical `${{ inputs.* }}`-derived config mechanically, since it has no per-shard config override mechanism at all, so wiring the `agree` check into that one workflow's `combine` job would add cost without covering a bug shape that workflow can currently produce.

## Closed gap: GHA shard-timeout estimation and correctness-vs-timeout conflation (fixed 2026-09-10)

Bug family #10 (nested budget/resource semantics), #13 (workflow/checkpoint staleness), and #14 (incomplete/contaminated populations) above. 2026-09-10 `connectivity-volume-portal-ab-001` produced three distinct, non-repeating real dispatch failures in one day (a canary-vs-plan-job-timeout bug, a canary-picks-a-hard-population-id bug, and a systemic telemetry-vs-real-cost mismatch across the whole treatment arm), echoing the same shape as the 2026-09-05 admissible-order confirmation timeout investigation (`reports/2026-09-05-admissible-order-non-default-retry-repricing-confirmation-005.md`: 58/76 hard shards ran past timeout with zero output). Two compounding root causes: `scripts/plan-highbudget-shards.mjs` estimated a shard's wall time as `sum(predicted)/workers` (only correct when every id's duration is identical — a real `workers`-way queue is bottlenecked by its single largest job) over telemetry linearly extrapolated across a 24x node-budget scale change with no ablation-flag provenance at all (see `docs/solver-scheduling-policy.md`'s "Shard-level runtime estimation, uncertainty, and timeout recovery" for the full mechanism). Manual gap-fill dispatches after each such failure also could not distinguish "this population is missing ids only because of a timeout" from "this population has a genuine correctness problem" — the same conflation bug family #14's invariant exists to prevent, just not yet mechanized for this specific recovery decision.

Fixed with four changes, none of which make solo-sharding (one id per shard) the default or broadly raise any global timeout:

1. `plan-highbudget-shards.mjs` replaced `sum(predicted)/workers` with `simulateMakespan()`, a real longest-processing-time-first simulation of the `workers`-way concurrent queue, used for both bin-packing capacity checks and the reported/timeout wall time.
2. Unknown/weak telemetry is now explicitly uncertainty-tiered (`classifyTelemetry`: confident / scale-mismatch / config-mismatch / none) rather than treated as an ordinary median, with two multipliers calibrated from real backtest cases (`scripts/backtest-shard-runtime-policy.mjs` against `data/stress/shard-runtime-backtest-cases.json`), guarded against inflating an already-unevidenced placeholder fallback into an unbounded number.
3. `--max-uncertain-group-size` (default `workers*3`) bounds how many low-confidence ids can share one shard regardless of makespan headroom, while confident-telemetry shards can still pack larger — small multi-wave shards instead of one-level solo shards as the default response to uncertainty.
4. `scripts/derive-timeout-recovery-population.mjs` (new) mechanizes the "missing ids only vs. genuine correctness problem" decision bug family #14 requires: exit 0 only when the only integrity issue is missing ids (no duplicates/unexpected/malformed rows), never inspecting *why* ids are missing itself — the calling workflow independently confirms every shard job succeeded (`needs.solve-shards.result == 'success'`) before treating a missing-ids-only population as timeout-caused. `solver-level-blind-targeted-sweep.yml`'s job graph now runs this automatically (`combine-first-pass` → `plan-recovery` → `solve-recovery-shards` → `combine-final`, gated by the new `auto_recover_timeouts` dispatch input, default `true`), re-planning only the missing ids with `--fixed-group-size=workers` and a doubled timeout floor, then re-validating the union of both passes with the same hard, must-pass population-completeness check the original single-pass `combine` job always ran.

`scripts/update-highbudget-telemetry.mjs` also gained a `configKey` field (via the planner's own `canonicalConfigKey`) and stopped EMA-blending across a config change — closing the "no config provenance" half of the telemetry root cause for its future callers, even though its one current caller (`solver-highbudget-unsolved-sweep.yml`) never varies ablation flags today. `solver-level-blind-targeted-sweep.yml` was deliberately left un-wired to telemetry writing: it is documented artifact-only / never-commits-to-main, and is exactly the workflow most likely to vary flags, making its telemetry the highest-risk contamination source rather than a safe learning source.

Regression coverage: `scripts/combine-solver-sweep-reports-node-test.mjs` gained tests for `simulateMakespan`/`packByMakespan`/`classifyTelemetry`/`calibrateMultipliers`, an explicit `shard-plan.json` output-shape assertion (every field the GHA matrix and its steps read off `matrix.shard.*`, with the documented type/range), and an end-to-end test tying the planner and `derive-timeout-recovery-population.mjs` together: a simulated timeout-truncated first pass plus its derived recovery pass reconstruct the exact original population with no id duplicated or dropped. `scripts/derive-timeout-recovery-population-node-test.mjs` (new) covers the recovery-eligibility gate's own six cases (missing-only, already-complete, duplicates, unexpected, malformed, no-result-file). None of this has yet been exercised by a live GHA dispatch under the new logic — only local unit/CLI tests and the existing per-step patterns it reuses (matrix `fail-fast: false`, the timeout-wrapper accepted-exit-code convention, the git-commit-with-retry pattern from `solver-highbudget-unsolved-sweep.yml`).

## Open research-integrity blocker: fresh vs preceded stage behavior

Historical reverse-oracle/admissible-order evidence has cases where an isolated action does not reproduce a win that occurred after earlier ladder activity. Until a specific explicit handoff, mutable field, cache semantic, randomness path, or work-accounting effect explains such a difference, treat it as an **unresolved correctness/experimental-integrity issue**, not as a useful scheduler feature.

**2026-09-03:** ran the required-handling reproduction below for real (15 cases, `main-search`-stage winners, predecessor depth up to 18 prior attempts on the same `prep`, current HEAD) — no discrepancy found; see [`../reports/2026-09-03-fresh-vs-preceded-main-search-reproduction-check.md`](../reports/2026-09-03-fresh-vs-preceded-main-search-reproduction-check.md) for method, scope limits, and results. Status remains "no known current instance," now backed by an actual empirical sweep rather than code-reading confidence alone.

**2026-09-10:** attempted to extend this to `admissible-order-fallback`/`admissible-order-alternate-tiebreak-retry` (reached only after `*-disabled-retry` override stages run) and found the naive extension methodologically invalid, not evidence of a discrepancy: any stage reachable only after a `*-disabled-retry` tier requires reconstructing that tier's hand-rolled ablation-config Proxy overlay for every preceding attempt in the chain, which no diagnostic round did — see [`../reports/2026-09-10-fresh-vs-preceded-late-ladder-extension-attempt-001.md`](../reports/2026-09-10-fresh-vs-preceded-late-ladder-extension-attempt-001.md) for the full diagnosis (predecessor-replay fidelity as low as 6/22 once one `goal-attraction-disabled-retry` override went unreconstructed). `main-search` stays the only stage this blocker's status actually covers; every other stage remains untested by this method.

Required handling:

1. reproduce the action from a freshly prepared state and from the predecessor-stage sequence with identical explicit action/config/seed/work limits;
2. diff every mutable/prepared field or generation-owned cache reachable by the action, plus work-meter and PRNG state;
3. identify whether the difference is wall-only, work-accounting, search-order, legality, cached-value, or randomness behavior;
4. if the predecessor contributes useful information intentionally, promote that information into a bounded typed producer -> consumer contract and add an independent control path;
5. otherwise reset/isolate the leaked state and re-derive any isolated cap/routing conclusions that depended on the contaminated behavior.

Do not tune scheduler caps or technique value around unexplained stage-history dependence. See [`solver-research-operating-model.md`](solver-research-operating-model.md), [`solver-mutable-storage-inventory.md`](solver-mutable-storage-inventory.md), and [`technique-census-analysis.md`](technique-census-analysis.md).

## Workstream-wide rules

Every active item follows **premise → smallest value-of-information pilot → explicit success/stop gate → bounded implementation → confirmation → broader integration**.

- Use `workSpent` for cross-technique allocation; raw nodes are within-technique diagnostics. `baseWorkBudget` is the preferred name for deterministic base allocation; `strictTotalWorkBudget` is the current true whole-solve work envelope.
- New actions/configs expand the menu, not the default total budget.
- Selected/tuned treatments need independent confirmation proportional to selection pressure; cross-generator transfer is reserved for broad/high-selection-risk claims. See [`solver-evaluation-evidence.md`](solver-evaluation-evidence.md).
- Level-blindness is not generalization.
- A clear negative closes the tested form unless materially new evidence changes its premise.
- Prefer locked confirmation pools partitioned into one-use blocks when repeated selected candidates are expected. Spend the block whose outcomes influence design; untouched sibling blocks remain available. A fresh one-off cohort is still fine when cheaper.
- Major capability refreshes should emit an output-only delta digest: gain/loss IDs, winner stage/action, per-level work/attempt deltas, and aggregate work split across prior solves/new solves/still-unsolved.
- Treat the current technique-capability/niche map as a **standing decision input**, not a separate numbered workstream. Before repricing, routing/action-selection, repair, retention, or exact-model work, classify the target population where evidence permits as broadly supported, thin/rare capability, specialist-only, production-allocation/exposure failure, or outside demonstrated frozen capability. Use [`../reports/2026-09-01-technique-niches-and-unsupported-level-anatomy.md`](../reports/2026-09-01-technique-niches-and-unsupported-level-anatomy.md) and its machine-readable artifact as the current baseline, preserving its caveat that `no frozen T1 winner` is not `no current technique`.
- Scheduler/repricing experiments must report rare-capability retention, not only aggregate solves/work. In particular, audit singleton/doubleton and specialist-only cohorts so a cheaper portfolio does not silently erase distinct capability.
- After a major solver capability change, meaningful census refresh, or current-head reach/work refresh, rejoin/rebuild the capability map and use the delta to update hypotheses. Do not let the September-1 snapshot become a frozen historical curiosity. **2026-09-03: a 12-cell spot-check found real motivation for this** — the underlying T1 census (`32240161854`) was generated 2026-08-20, and 3/12 spot-checked cheap frozen wins no longer solve at current HEAD within the same node budget (ordinary two-week heuristic drift, not a correctness bug; see [`2026-09-03-frozen-technique-census-staleness-spotcheck.md`](../reports/2026-09-03-frozen-technique-census-staleness-spotcheck.md)). A full re-census (78,553 cells) is not dispatched yet — it needs its own scoping decision — but any session leaning on `frozenT1SupportClass`/singleton-doubleton claims or the post-976 rejoin's specific residual counts should treat them as dated, not current.
